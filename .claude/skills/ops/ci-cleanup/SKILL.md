# CI cleanup

Three jobs on one method, `~/.local/src/docs/analysis-streams.md` (finding shape, in flight, baseline, one lever per PR, re-measure, report, proposals, next pass); read it first. **Reds** turns "CI keeps going red" into a counted list of causes, each with one owner. **Cost** turns "CI is slow" into a measured lever and its before/after. **Pass** combines both into a cleanup that leaves CI greener because causes were fixed, not hidden. Each section below holds only what is specific to CI.

The doctrine (gate, tiers, budgets, speed levers, red handling, quarantine, reruns, stop-the-line) is `~/.local/src/docs/ci.md`; the repo's CI doc owns its specifics (unity-core-playground: `docs/operations/ci.md`, `docs/operations/ci-cost.md`, `docs/operations/ci-benchmark.md`, `scripts/ci/ci-cost.py`). Running or gating playground tests is `playground-headless-test`. When this file and a doc disagree, the doc wins and this file is fixed in the same turn.

## Scope and triggers

- Reds: why CI is red so often, what keeps failing, whether something is flaky; a nightly or main red whose cause is not obvious from one log; before choosing which red to fix first, or when a red has no owner; after a fix lands, to show its signature stopped.
- Cost: why CI, a gate or a dispatch takes as long as it does; choosing the next harness change to cut CI time; proving what a landed harness change saved; a long runner pool queue nobody can attribute.
- Pass: the human asks to clean up CI, raise the pass rate, or run "CI cleanup pass N"; nightlies stay red for days and single-red triage has not moved them; a low local or gate pass rate nobody can split into tests and harness.

Not for a red CI run on a PR or on main, the nightly included (`fix-ci`), agent-session ETAs (`fleet-bench`), or running tests (`playground-headless-test`).

## Reds: why CI is red

Explains and routes; it fixes nothing.

1. **Scope the window.** Repo, workflows, base branch, days. Default: every workflow, 3 days, base `main`. Say the window in the answer.
2. **Count with the script, never by hand:** `~/.claude/skills/ci-cleanup/ci-failures.py --repo OWNER/NAME [--workflow test.yml]... --days 3`. It prints red rate per workflow, red runs per bucket, a "where" table (workflow file / job / failed step) and the signature table; `--json` has every record. Runs come from the run ledger (`schedules-sync runs`, synced every 10 minutes, the repos `schedules-sync repos` lists), so a repo outside that list reads as PARTIAL; jobs come from the job archive (`schedules-sync jobs`; an earlier attempt of a re-run is read from gh and counted in `jobs_from_gh`), and annotations and logs of red runs from gh. Its counts are reds by cause; the pass rate is `hub ci pass` (hub_core `builds::verdict`). The first pass costs about three API calls per failed job (the account shares 5,000 an hour across sessions); after it, pass `--until <the first pass's end>` with `--offline` and reuse the cache. A failed job GitHub stored no log for is read from its annotations and step, marked `(no log on GitHub)` and listed in `logs_missing`; that alone is not PARTIAL. It exits 3 and says PARTIAL when any other gh call failed, the job archive cannot be read, the ledger is stale, or a past `--until` is after its last sync (`--json` names the first such read in `partial_why`): report that, never low counts as the answer.
3. **Read the buckets.** `infra` (runner lost or killed, disk, network, rate limit, host key), `timeout`, `test`, `check` (lint, docs, build, a PR-body check), `derived` (failed only because an earlier job did, never counted), `pending` (red by design until another run finishes, such as the playground's gate line on a PR pushed before its gate; a run red only on those is not red). The patterns sit at the top of `ci-failures.py`; when a bucket is wrong, fix the pattern there (with a fixture in `tests/fixtures/ci-failures/`), not the count in your answer. A `test` red's assertion text is in the run's test-runs artifacts, not the job log: read it with the repo's reader (unity-core-playground: `scripts/test/red-causes.py reds --since <date>`). Write down the suspects you ruled out.
4. **Base-branch reds come first.** A signature with `main: yes` fails every branch. Find the first bad commit: `schedules-sync runs <repo> --branch main | jq -c '.[] | select(.path | endswith("/<file>")) | [.sha, .conclusion, .created_at]'` gives the last green and first red, and `git log <green>..<red>` the PRs between them. `ci.md` "Tiers" says what happens next.
5. **Flaky needs evidence.** `green@sha: yes` (the same job went green on the same commit) is a lead, not a verdict: rule out a changed PR body, variable, secret, test pick or moving base between the two runs first. Never rerun a job to find out; quarantine only by `ci.md` "Red handling".
6. **One owner per cause.** For each signature that recurs or sits on main: an open PR, a board row (grep the board first), or a session already on it. No owner: post one proposal, `agent-propose add --stream ci-failures --project <project> --verb row --arg "ci(<area>): <signature>, <runs> runs, sample <url> #size/s #tier/3" --why "<runs> runs<, red on main>" --evidence <url> "<signature>"`. Dedupe and the cap are the method's. It expires on its own once older than the stream's window (`AGENT_PROPOSE_WINDOWS` in `agent-propose`); when a PR fixes its cause first, `agent-propose expire --by pr:<N> <id>`.
7. **Report:** the red rate and the one or two causes that drive it; the bucket table and the top of the "where" table, as printed; the top recurring or on-main signatures, each with its owner or the proposal just posted; what was ruled out and what the window cannot show (runs still going, PARTIAL, a workflow not read); for a trend, the same command for the previous window (`--until <start of this one>`).

## Cost: where CI time goes

The cost is run time: wall minutes per run and runner-minutes summed over jobs. Do not speculate about billing or infrastructure unless asked.

1. **Measure from data, never from memory.** Run `scripts/ci/ci-cost.py` first: runner-hours per workflow per day, the gate median split into EditMode and PlayMode, queue times, the slowest classes. Extend the script rather than hand-computing a number it should own. Its PlayMode figure is summed runner-minutes per gate, not one job's time; a gate's own time is its slowest Unity job's queue plus run, read from `~/.local/state/ci/jobs.jsonl`. For what the script does not give (Unity launch cost, per-class time, a gate's pick, EditMode per assembly) and how to read a window, follow `docs/operations/ci-cost.md`, Measuring. Raw `gh run list` / `gh run view --json jobs` calls follow `ci.md` "Analysis": cache every response and reuse it.
2. **Attribute.** Put every minute in one bucket: workflow and trigger (nightly, gate, branch dispatch, release), then fixed per-launch cost, per-test cost, over-picking (classes the change cannot affect), repeat gates (a re-gate after only a main merge, a second gate of a gated commit, a `run_attempt` above 1), solo reruns of a batch red, a cold Library import, or a slow test. Count the workstation's local Unity hours too (the run ledger `scripts/test/slots.sh` writes). Write the ruled-out suspects down so the next pass does not redo them.
3. **Rank levers** in the order of `ci.md` "Speed levers", deletion first, then by runner-hours saved per day (minutes saved per run times the runs per day it touches). Note the floor (a Unity launch costs about a minute) so targets stay honest.
4. **One lever per PR,** carrying what `ci.md` "Harness changes" and the repo's CI doc require.
5. **Re-measure the same way** after it lands, `scripts/ci/ci-cost.py --days N --before <end of the before window>`, and append the lever's before/after row to the `docs/operations/ci-cost.md` Log. A plan's estimate is replaced by the measured number.
6. **Report:** the answer in one or two sentences, including what got worse; one table from `--before` (metric, before, after, expected; keep the rows it prints); a decisions table, each with its PR and what it measured, dropped or deferred ones included; what makes the windows not comparable (slots, routing, gate count, load, runs still going, one night against one night); what is not measured yet and the next lever. Say a change caused a number only if that lever was measured alone. A report from a fresh measurement also lands by PR in `docs/operations/ci-benchmark.md` (a Readings row, plus any section whose numbers it changes).
7. **File the next lever** on the agent board (`notes ptask <project> --agent add "ci(cost): <lever> #size/s" '#tier/3'`), checking for an existing row first.

## Pass: a whole CI cleanup

1. **In flight first,** per the method, plus the plans of sessions on CI (grep `~/.claude/plans` for ci, quarantine, nightly).
2. **Baseline, from the scripts only.** Reds (3 days, all workflows) and Cost (`scripts/ci/ci-cost.py --days 1` online, then its re-gate table) plus the local run ledger pass rate (`~/.local/state/unity-test-runs/runs.tsv`, and `test-failures.tsv` for the tests red on many unrelated branches). Record every number in the plan with its window. A cached `--offline` read must cover the window you quote. Pass 2 onward, re-read both windows per the method with `--until` and `--offline`. Check that the last pass's fixes have had a nightly: if none has run on them, the pass reads that nightly before its report, and says so when it cannot. Count batch-only reds with `batch-only.py --run <Tests run id>` (in this skill's folder), never by hand.
3. **Bandaid inventory.** Each with file:line, the real cause, and an action. Grep list for the playground: the batch-then-solo rerun in `scripts/test/suite.sh`; `scripts/test/quarantine.txt` (expiries this week; remove a pure duplicate line in this pass yourself); raised ceilings in `PlayTestSession.cs` and their commits (`git log -S`); widened tolerances (`git log --grep 'allow\|tolerance\|lag'`); wall-clock deadlines the fixed-delay guard misses (`realtimeSinceStartup +`); host exclusions (`linux-only-classes.txt`); job and script timeouts (guards, keep). A test bandaid that must stay becomes a quarantine by `ci.md` "Red handling"; a guard that stays gets an owner, an expiry and a written why.
4. **Architecture: what one class leaves for the next.** Batch-only reds come from shared state. Check, with file:line: is the session reset between classes, or does `SwapTo` the current game no-op; does a class that stops the server leave later classes to time out; statics reset once per launch instead of per class; runtime writes to static catalogs and settings that TearDown does not restore exactly; one saves folder for the launch; fixed ports. Prove a leak with a two-class batch in leak order: red before, green after.
5. **Fix by cause, one area per branch, one gate each,** per `playground-headless-test` and the repo's ci.md. Fan independent areas out to background agents, each in its own `~/.worktrees/<repo>-<slug>`. Each brief carries the method's landing rule (fix PRs `--partial`, the report PR closes the item), says that a branch cut from `origin/main` tracks it, so push with `git push -u origin HEAD:<branch>`, and says to wait for the gate's own result before reporting, since a background agent can stop while its Unity run still works. A fix PR's gate red that is not the branch's (an unowned flake) becomes this pass's next fix on its own branch, per ci.md's stop-the-line rule: never a rerun. Read the failure text before calling anything load; compare hosts within the same run, not across runs, before blaming a host. Pool caps and slot counts go to home-config by PR with a before and after.
6. **Remove the bandaid** in the PR that fixes its cause, or the next one: lift the quarantine line, put the ceiling back, delete the rerun once `batch-only.py` reads zero batch-only reds on a nightly.
7. **Re-measure** with the same scripts and windows (`ci-cost.py --before <first landing>`, `ci-failures.py --days 1`, the ledger) and add the rows to `docs/operations/ci-cost.md`'s log. That log has word and date caps in `docs/budgets.txt`: keep one row per cleanup series and replace the last pass's row rather than adding one. Say what one day cannot show.
8. **Report** in `docs/operations/ci-cleanup.md` (current pass only) per the method, adding sections for CI cost, failure analysis, what ran, cleaned up (bandaid -> PR) and architecture findings; from pass 2 the table's columns are the original baseline, the last pass and this pass. Proposals per the method, evidence the Artifact page. On the last pass of a series, the report is also the series summary: cost and failure analysis per pass, every bandaid removed (with PR) and every one kept (owner, expiry, why), the architecture changes and whether shared components were the cause, whether the pass rate is acceptable against ci.md's rules, and what another pass would take on. The report's date cap is 0 (`check-docs.py`): name PRs and passes, never a date. Publish it as a new Artifact page per pass, titled `CI Cleanup Pass N`, and page per the method (`-t ci-cleanup`).
9. **Queue the next pass** per the method, unless this pass was the series' last: `--project <project>` (the project of this pass's item), slug `ci-cleanup-<project>-p<N+1>`, baseline `docs/operations/ci-cleanup.md`.

## Do NOT

- Do not rerun a job to diagnose it (`ci.md` "Red handling" step 1), or call a test flaky from one red or from `green@sha` alone.
- Do not quote a rate, count or timing you did not get from the scripts in this session or read from a dated doc; a number only one session can reproduce cannot be compared later.
- Do not break `ci.md` "Tiers" or "Red handling", or drop coverage, to get a green or hit a target.
- Do not restate a repo CI rule in a row, a PR or this file; link the doc.
- Do not fix in another session's area, or cancel another session's gate run; message it and measure around it.
