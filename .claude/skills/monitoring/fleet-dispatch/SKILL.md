# fleet-dispatch

The intake role of `fleet-lead` (Binks). `fleet-dispatch` keeps the queue fed: the board tops it up while fewer than `DISPATCH_LOW_WATER` (20) items are runnable. Board items start as fast as the gates allow, the human here or away, under the same gates as any queue item (`DISPATCH_PER_PASS` caps a pass when set above 0); presence only picks the pace target (below). A pass promotes up to the low water, or the room it can start if that is more. `DISPATCH_LOW_WATER=0` fills only an empty queue. The agentctl runner `fleet-dispatch` runs `fleet-dispatch run` on the `SCHEDULE` in its conf (off while the conf says `ENABLED=no`; `agentctl enable fleet-dispatch` arms it, `agentctl disable fleet-dispatch` turns it off again); this skill is for running it by hand and reading what it decided. It is the only thing that starts sessions from the board unasked: a `fleet-lead` pass does so only to heal a starved queue (below), and no order should tell one to.

Away comes from `fleet-presence`: no keypress in any tmux client and no desktop input for `AWAY_AFTER_MIN` minutes (fleet-presence's default), on this machine or on any machine that publishes to the store. The desktop counts because the human playing a test build holds no tmux client. Agents do not count: send-keys and paste-buffer leave `client_activity` alone (`tests/ui/fleet_presence.bats`). Dispatch can run on any machine and the human often sits at another, so every stowed machine runs `fleet-presence-publish.timer` every 2 minutes: `fleet-presence publish` writes its last input to `presence/<host>` in the agent store, which store-sync carries to every peer, and status reads each file as `<host>:<source>`. A file holds when the input was, not a verdict, so a machine that sleeps or dies ages into away on its own; a machine whose source reads unread writes nothing, so it cannot pin the fleet to here. It takes no time of day, because a night is a long away. When the human comes back, the next pass uses the present pace target and running sessions carry on. If it prints `unread`, usually because `hypridle` is not running, dispatch treats the human as here: the present target.

Pace targets: a pass starts a Claude item only while the fleet's live Claude sessions, hand starts included, are under the target: the live count plus the working Opus sessions the Claude accounts' spend has spare at their weekly pace (`claude-acct room --json` `.fleet.spare`, (keeps - burn) / rate, the `room for ~N more` of `claude-acct status`), at most `DISPATCH_TARGET_PRESENT` while the human is here and `DISPATCH_TARGET_AWAY` while away (both set in `fleet-dispatch.conf`), and never under the run floor (the floor wins over the cap), so neither a day nor a night spends the week ahead of its line (2026-11-18: 30 present while the accounts carried 19). Burn and the rate count each working session by its model (`pace.conf` `MODEL_WEIGHT_*`, Opus 1), so a Sonnet or Haiku session leaves more spare, and each start is counted as one more Opus session, so the guess never overspends (ar-3230: 37 live read as full against a carry of 19 while the accounts spent 0.7/h of 1.6/h). The target is Claude's budget alone: past it, an item routed to another source with room still starts (the other-source pass below); `DISPATCH_RUN_FLOOR` (set in the same conf) is the floor. The count is every non-parked session in the fleet state document `fleet-sessions` writes each minute, except one waiting its landing turn behind another PR (`open_job` `queue`): it holds a merge-line place, not a working slot, and a NEEDS session waiting on the human (its reason not `carrying on`, which is busy): it cannot move, so it holds no slot (`headroom --json` `needs` is how many; ar-3811); missing or older than `DISPATCH_STATE_FRESH_MIN` (10), it holds every start (BLOCKED). At the target a pass is NOOP. Hand starts count but are never refused. The runner's own sessions also hold at most the target in run units. `run --dry-run` and `headroom` print the target and the live count.

## Scope and triggers

Covers keeping the agent-queue topped up from the board, the pace target by presence, and starting a session by hand (`fleet-dispatch start`).

Use for "what would dispatch pick", "why did it skip that row", "start a session for this row", "pause dispatch". Moving live sessions through their plans: `shepherd`. Load and holds: `fleet-pace`.

Which projects dispatch is their stage: every project at `dev` or later with a repo, except the ones on `DISPATCH_OFF_PROJECTS` in the conf (finance, which holds bank data). `fleet-dispatch candidates` says "no worker covers <project>" for an off project, `suggest` lists its rows with that reason, and `fleet-dispatch covered` lists the projects that dispatch (inbox-triage's lane rule reads it). Who may take a row is `~/.config/fleet-dispatch/workers.json`, walked in file order, and no worker lists projects:

- `requested`: `#requested` rows tagged `#worker/requested`, up to tier 2.
- `fleet`: rows the human tagged `#worker/fleet`, up to tier 1, with a `#tier/N`.
- `board`: agent-board rows with no `#worker` tag, up to tier 2. No tags are needed, because the judge reads the tier. A tier 3 row (harness, CI, runners) goes through the tier-3 gate (below).

The human sheet stays opt-in: `board` never reads it. Tier 3 (CI, gates, runners, build, deploy, harness and tooling) has one gate in every project (policy.md, under Tier): a tier-3 row at S or M becomes a merging day item tagged `tier3` (a cleanup row of `DISPATCH_CLEANUP_PROJECTS` also `cleanup`, ranked first), which agent-land lands only with a `Review: ` line in the PR body and checks that ran green. No skip parks a row: each pass gives every agent-lane skip the exit its rule names (`skip_exits`, policy.md "Always skip"). A plan rule (`DISPATCH_PLAN_RULES`) tags it `#plan` for inbox-plan, under `DISPATCH_PLAN_BACKLOG` open ones. A row sized L or XL (`#size/l`, `#size/xl`) takes that exit as rule `too-big` with no verdict needed (a project the judge covers; not an epic, a parent, a gated row or one whose session failed; a skip naming a human rule keeps its own exit); one inbox-plan already planned through that exit that is still L goes to the human. A human rule (`DISPATCH_HUMAN_RULES`) moves a bare, `#urgent`, `#high` or `#requested` row to the human sheet and a `#low` one to `improvements.md`, dropping the agent row with a `--why` naming where it went (`notes ptask reopen` undoes it). `waits` gates it `#after/<row>` or `#pr/<owner>/<repo>/<N>` on what its reason names, when the row otherwise fits, else plan. Each exit is appended to verdicts.jsonl with `exit`; `fleet-dispatch exits --dry-run` lists what a pass would do. An untiered item on a cleanup project counts as tier 3 (`fleet-dispatch item-tier SLUG`). A row whose text starts `ci:` or `infra:` counts as tier 3 whatever its tag says. What each tier means is defined in `~/.config/fleet-dispatch/policy.md`, under Tier.

What kind of work a row is comes from its type prefix (`fix(area):`), and `~/.config/fleet-dispatch/kinds.json` routes each kind, keyed by notes-cli's `ROW_TYPES` (`tests/unit/fleet_dispatch.bats` "kinds" pins the keys): `rank` orders rows the feed ranks alike (within a project the board feed's `rank` decides: due, priority, #requested, then age; a `fix` row, `label` "bug", goes first among equals and `why` says so), `entry` is the skill its session starts on (`/one-shot` for code, and for a row with no type), `rung` (build, propose, human) and `exit` (pr, report, doc+ask, proof) say how far it goes (report is a check, which opens a PR only when it finds something to fix, so a clean run is unrated in the `outcome` agent-queue stamps at close, never a no-pr miss; a doc+ask brief has the session write a doc in the project's lab `docs/`, file one ask, record both with `agent-queue set <slug> report=<doc> ask=<id>`, close its row with `--proof doc:<path>` and move the item done, never open a PR; a proof brief, the `release` kind (off for board rows, so a session starts it only by hand: it fixes, improves or re-sends a release the system cut, and no row ever starts a cut), has it record the live proof its skill names in `note=`, close its row on that proof and move the item done, never agent-land), and `enabled` says whether it dispatches at all; the project's stage alone says where (`dispatchable`: dev or later). A row of a kind not enabled, an `epic(` row and a parent row (an open row names it in `#of/`) never reach the judge, and every other open row does (`#low` ranks last); `suggest` names the reason, and a hand `start` still takes one. Turning a kind on or off is a line in that file, never the script. A row's `#size/` tag is its size: the judge reads it as given, picks trust it over the judge, and the judge's size for an unsized row with an id is written onto it as `#size/x`.

- `fleet-dispatch kick` is the fast start-only path an event runs: the queued items that fit the gates and room, in seconds, with no reap, triage, judge or board fill, and no outcome published as `fleet-dispatch`. It stands down while a pass holds the lock; the timed `run` keeps the slow work. An event runs `kick`, the timer runs `run`: `agent-queue` (an add, a close), `agent-hold` (a release), `agent-ask` (an answer that releases held items) and `store-sync` (a pull of queue changes on the lease holder) rewrite `~/.agent/dispatch/.wake`, and `fleet-dispatch-kick.path` starts the kick unit (`journalctl --user -u agentctl@fleet-dispatch-kick.service`). Never call `fleet-dispatch run` to get work going (a 6 to 16 min CPU-bound pass, NOOP while one runs, nothing off the lease holder) or a hand `fleet-dispatch start` (it holds no run unit): `agent-queue add` or the outbox wakes a kick.
- `fleet-dispatch run --dry-run` runs the gates, says what would stop a real pass, and prints the picks without starting anything. It still judges new rows, up to `DISPATCH_JUDGE_MAX`. `fleet-dispatch run` starts them.
- `fleet-dispatch report` shows the latest verdict for every row it has judged: picked or skipped, size, judged tier, area, and the one-line reason. A verdict made under an older policy is marked stale.
- `fleet-dispatch candidates` lists the open rows it would judge next.
- `fleet-dispatch suggest [--json]` is the Candidates list, for display only: every open agent row (and every row a worker takes) of each project from dev up in `DISPATCH_PROFILES` (the profiles `run` reads), in rank order, each with its `why`, `auto` (a worker in `workers.json` takes it; widening a project is a line there), the cached verdict or `unjudged`, and whether an active item holds its area. It never judges or queues. `suggest --write` stores that list in `~/.local/state/agentctl/dispatch/candidates.jsonl`, which every real `run` pass does and `promote` trims, and both hub Candidates folds read only that file, stamped `as of` its time.
- `agent-hold set dispatch "<reason>"` pauses it; `agent-hold release dispatch` resumes it.
- Level: the conf's `DISPATCH_PER_PASS` and `DISPATCH_MAX_LOAD`, and `claude-acct room`'s slack and reserve, are the `mid` numbers (`DISPATCH_PER_PASS` 0 is no cap at every level). The `machine-mode` level (low, mid, high) multiplies them where they are read, by `.config/machine-mode/levels`; `headroom` prints the level in force. Raise a limit in the conf, change the level with `machine-mode`.
- Tier-3 rows: the day fill (`run` and `fleet-dispatch fill`) also judges the open agent-lane rows of every project at stage dev or later in `DISPATCH_PROFILES` and pulls the ones the judge read as tier 3 and dispatched (such a row goes to the judge as its tier-3 copy) under the same room, gates and per-pass limit as any other row, with no area hold, as queue items tagged `tier3` that merge behind the red-fix gate (policy.md, under Tier). A `#requested` row is eligible. It skips `decide:`, device, the human's machine, and the human-merge list (release cuts, secrets and auth, prod and data migrations, money: `DISPATCH_T3_SKIP`), every row of finance (`DISPATCH_T3_HUMAN_PROJECTS`), an untagged gated row, and wishes; it ranks `#requested` rows first, then observer rows (an improvement row tagged `#kpi/<k>`, or a `check(kpi):`, `fix(lesson):` and the like from retro and triage), then most urgent and oldest. Each row is `start`ed and closes when agent-land merges its PR. A headless harness still stops a tier-3 item at an open PR (`--pr-only`), since it cannot run the review. There is no night tag and no night window: night runs builds and nightlies only, and real work is pulled from the board under the queue cap. `fleet-dispatch fill --dry-run` lists these rows as `ready` with worker `tier3`.

## A pass, in order

1. Reap: an item whose session is gone is closed, or moves to `review/` (`on a PR`) while its PR is open. A parked PR with nobody on it gets an owner (`own_parked_pr`): red checks a `/fix-ci` session, green or in conflict with its base (which runs no checks) a lander, `DISPATCH_FIX_TRIES` tries of each per head, then one agent row tagged `#red #escalate` on the item's board (no human-sheet row and no page since ar-4765). An item with no PR whose session pushed work its trunk lacks (`branch:`) goes back to `queued/` with `salvage:` on that head, `DISPATCH_FIX_TRIES` times (`takeover_tries:`), instead of failing; a branch with nothing to land fails it as before. That is how a window the shepherd closed reaches a fresh agent (`tests/unit/fleet_dispatch_reap.bats`, "takeover"). Gone means its tmux session ended, or agent-panel lists no Claude in that tmux session (a shell outlived claude), or, for an item started in a hub window, none of the Claude sessions it lists (`sessions:`) is live. A parked pane, another agent than claude, an item started in the last `DISPATCH_REAP_GRACE` seconds (600) and an empty or unreadable panel are never read as gone. A Claude missing from the panel is never the verdict while a process recorded for one of the item's `sessions:` ids still runs (`~/.claude*/sessions/<pid>.json`), and otherwise one witness: the item settles only when a reap at least `DISPATCH_REAP_CONFIRM` seconds (120) after the first also misses it, and a reap that does not read it gone clears the first miss (`~/.agent/dispatch/reap-miss/<slug>`). A tmux session that ended needs no second witness. An item on a fleet worker (`host:`) that does not answer is left alone until that worker has gone unanswered on every reap for `DISPATCH_HOST_DEAD` seconds (1800; `~/.agent/dispatch/host-miss/<host>`) while this machine still syncs the store (`store-sync-age`): then its running and waiting items with unfinished work go back to `queued/` with `lost: <host> <sessions>` and, with no PR, `salvage:` from the `branch:` its session's Stop hook last pushed, and a pass places them on a node that answers. An item reap cannot settle and nothing will change on its own (a partial landing whose requeued run also ended without the final one, a PR its forge cannot read, a done item's row with no merge proof on its forge remote, `forgejo` for a Forgejo checkout) is logged once, when its reason changes, and gets one agent row tagged `#red` on the item's board (a refused row is said on stderr, nobody is paged): the partial at once, the others once they have stood `DISPATCH_ORPHAN_HOURS`. Its marker is `~/.agent/dispatch/stuck/<slug>`; deleting it files the row again on the next pass, and a marker no pass rewrote in a day is pruned (`tests/unit/fleet_dispatch_reap_restore.bats`, "logged once"). An item a false reap closed goes back with `agent-queue reopen <slug>`. A live one moves to `waiting/` while its Claude waits on the human (agent-panel `waiting`, an open plan or dialog) or has a pending ask, back to `running/` after. An agent-lane row started with no active item naming it goes by the PR of an item done ok that names it (merged closes it on merge proof, open keeps it started); failing that it is un-started, with a `failed` verdict, once reap has seen it that way for `DISPATCH_ORPHAN_HOURS` (72); first sightings are in `~/.agent/dispatch/orphans.tsv`. A `failed` verdict (that un-start, or a row's item ending failed or cancelled for a cause the model owns) expires the row's verdicts, so the next pass judges it again; `DISPATCH_FIX_TRIES` (2) of them since its last `cleared` hold it (one marked `hold`, a cause a retry cannot change, holds at once), and for an agent-lane row reap then files one approval ask carrying their reasons (unless a done item naming the row has a merged PR, which closes it on merge proof, or, for an item that ended ok, an open one, which it waits on; an ended item never un-starts or fails a row a newer item names), gates the row `#ask/<id>/retry` and writes the `cleared` that starts the count again, so retry starts it and drop drops it (`ask_failed_rows`; "ask_failed_rows" in `tests/unit/fleet_dispatch_start.bats`). Nobody appends `cleared` by hand. An open agent-lane row whose `#ask/` gate the human answered with another option is settled: an answer that says skip drops it with the answer as its why, any other answer swaps the gate for `#hold/row-<id>`, an agent-hold that `agent-hold release row-<id>` lifts to start it. A cancelled ask sets no hold: a done item on the row whose PR merged, read from its own record and not by a slug a later run reused, closes it on merge proof, else the ask is posed again once and the row gated on the new one (`settle_answered_gates`; "reap settle" in `tests/unit/fleet_dispatch_reap.bats` and `fleet_dispatch_reap_restore.bats`). Then the night fill (above). Room is the pace target (above) less the run units of live sessions the runner started (`origin: run`), no more than the target less every live session, capped at `DISPATCH_PER_PASS` when it is above 0.
2. Gates, each refusing when it cannot read its source (a red item has its own floor, below): no `dispatch` hold; `fleet-assess` not HOLD; load under `DISPATCH_MAX_LOAD` per core, on this machine the lower of the 1-minute load average and the cores busy over the last minute or so (a `/proc/stat` delta from a sample the minute record keeps, iowait counted busy), since load average lags a spike and counts threads blocked in the kernel (2026-11-17: 150+ items held an hour with the CPU 66% idle, ar-2851), and on a fleet worker its 1-minute load; GitHub budget not LOW. No idle-percent floor: from 2026-11-07 to 11-21 it never held a pass that load or `fleet-assess` did not hold too (activity.log; plan vast-soaring-prism P4, ar-34). `fleet-assess` and load read only this machine, so they hold only a start here: while a fleet worker takes a session the pass goes on and places each item it can there; nothing starts here, and no session here is preempted, while they hold. At launch, `claude-acct room` must name an account under its weekly pace, or the row waits. While fewer than `DISPATCH_RUN_FLOOR` run sessions are live (this pass's starts counted), the weekly pace does not hold a start: room is asked with the pace line lifted, and still refuses an account in its reserve, its 5h window or emptied before its reset; the start's line says `on the run floor`. Why: hand starts never wait on pace, so without a floor they fill the week and no run start, and so no dispatch-judge outcome, ever happens (2026-11-05). Every closed gate is named in the pass's line, joined by `; `, the account one in `claude-acct room`'s own words. The k3s cluster is not a gate either: while `fleet-shepherd infra` reads it red or unreadable (a k3s component other than `watches` above 0, a NotReady node; a watch alone, such as trivy criticals, does not count, ar-1608), `pick_item` holds only items of a project in `DISPATCH_CLUSTER_PROJECTS` (`home-config`), saying `cluster: ...`, and a start on a harness that spends the LiteLLM gateway waits while the gateway is down too (`load_gateway_down`, in route and `floor_gate`). Why: on 2026-11-23 a failing cluster-janitor watch turned the domain red and the machine-wide gate held every start, Unity included (ar-4889). A nightly red is deliberately not a gate: nightlies stay red while sessions merge normally, and the NIGHTLY row handles it.
   The red floor: while fewer than `DISPATCH_RED_FLOOR` (2) red items the runner started are live (this pass's red starts counted), plus one more for each queued or running `red watch` item, which start first, a red item at the head of the queue starts past load, a `fleet-assess` HOLD and the weekly pace, and no other red starts on it that pass (the class floor may start short items behind it). `agent-hold`, the reserve and the GitHub budget still hold it, and a red cluster still holds a red item of cluster work. Human decision 2026-11-06: a fix held behind a busy machine keeps the fleet red. Human decision 2026-11-10 (ar-1531): every tripped watch has a running owner the hour it trips. Tests: "red floor:" in `tests/unit/fleet_dispatch_run_floors.bats`.
   The human floor: a queued item that is urgent and `from: human`, or a fresh ask (an item from a `#requested` row, tag `requested`, whose `asked:` date, the row's created date that promote stamps, falls in the last `DISPATCH_ASK_FRESH_H` hours, 24, 0 is off; not `from: human`, which every add with no `--from` gets), starts on an account refused for its weekly pace alone, whatever the run floor holds (the standing rule that limits never cut off the human's own work; 2026-11-10 four dodginballs items sat 2h, ar-1412). Only the pace refusal lifts: the reserve, the 5h window, committed burn, load, a `fleet-assess` HOLD, `agent-hold` and the GitHub budget still hold it, and the rest of the queue stays held. A fresh ask still on the board is queued first, every run pass, by `ask_top_up` (fill_day's `ask` floor: `#requested` in the human's words, the board's own `since` inside the window), so a full pace target or the weekly pace no longer leaves it a row (ar-3471). A ready phase of a plan the human approved (a queue item with `plan:` set, `from: human`, no `after:` or tag hold) starts on the same floor, one phase a plan a pass; under a full pace target it waits in queue order like any item (the plan floor that started it past the target is gone, plan vast-soaring-prism P3). Past load such a phase still starts, on the plan load floor: while fewer than `DISPATCH_PLAN_LOAD_FLOOR` (2, 0 is off) approved plan phases the runner started are live (any start of such a phase this pass counted), the human floor starts only those phases past load and a `fleet-assess` HOLD on load, as the red floor does (a memory, stall or temperature HOLD still holds them), and the start line names what it went past "on the plan load floor" (`plan_load_floor_open`; human decision 2026-11-21, ask GwQIYE: at load 40 to 77 on 28 cores no approved chain started). Tests: "plan load floor:" in `tests/unit/fleet_dispatch_run_floors.bats`. The urgent items of an open sprint (tag `sprint`, which promote puts on an item whose board row is the open sprint's: its window holds it, or it is an unstarted agent row of the open version the window did not commit) start on the same floor too, up to `DISPATCH_SPRINT_FLOOR` (3, provisional, 0 is off) live, after the trainee floor (`sprint_floor_start`; 2026-11-19 urgent playground v0.5.4 sprint rows sat hours behind a full pace target, ar-3816); a non-urgent sprint row only ranks first and `agent-queue` lists a `sprint` item after red and urgent. Tests: "sprint floor:" in `tests/unit/fleet_dispatch_run_floors.bats`. `fleet-dispatch starved` names an urgent item no pass started even when a run start happened in the window, an approved plan's ready phase once the fleet is under its target, and one from the human under an `agent-hold` on dispatch or a load gate too (under load with how many of them are approved plan phases and how full the plan load floor is; a plan phase waiting on a full plan load floor is not starved), so queue-starved pages for whatever the floor cannot lift (2026-11-10: 2h of the 4h wait was a dispatch hold that read as nothing starved, ar-1432). It also names items held on an ask no answer can release (cancelled, gone, or answered with another option). Tests: "human floor:" in `tests/unit/fleet_dispatch_run_floors.bats`.
   The class floor: a pass tries the reds the red floor has slots for first (`red_floor_slots`), then the `short` items (a class under its `classes.json` `min_live`), then the rest in queue order (`pass_order`; 2026-11-23 unity sat at 1 of its 6 while reds and a cleanup row took the pass's starts, ar-4890). A short item starts on an account refused for its weekly pace alone, as on the run floor, after any red or human floor start that pass (`short_floor_start`); the reserve, the 5h window, committed burn, load, a `fleet-assess` HOLD, `agent-hold` and the GitHub budget still hold it, and it starts nothing past a full pace target. Tests: "pass order:" in `tests/unit/fleet_dispatch.bats`.
   No floor starts an idle project's item, a plan phase or a canary past a full pace target: the class mix (`classes.json`, applied in the `agent-queue` order) keeps each class from falling behind, and the red floor is the one interrupt (plan vast-soaring-prism P3 removed the project, source, plan and canary floors).
   The other-source pass: past a full Claude pace target (after the red floor), items start on another source with room, as many as its free slots (its cap, `max_live` or `rpm` over `run_rpm`, less live for each source `claude-acct room --json` calls ok, 1 for one with no cap). `route` refuses claude there ("the Claude pace target is full"), so an item starts only on a non-Claude candidate of its model-lane verdict or the harness it is pinned to, and every other route check holds. It tries pinned items, items whose cached verdict names another harness, and at most one unclassified item a slot, so a pass asks model-lane little; load, `fleet-assess` and `agent-hold` still hold it, and a pass that starts nothing is NOOP. 2026-11-18: 34 Claude sessions past a target of 30 held every item while codex, go and ocfree sat idle with room. Tests: "other sources:" in `tests/unit/fleet_dispatch_run_floors.bats`.
   The canary top-up: each pass keeps `DISPATCH_CANARY_KEEP` (set in `fleet-dispatch.conf`) canary items queued or running. It queues the missing ones (keep less queued less live) with `AGENT_QUEUE_PULL=dispatch fleet-bench canary queue --max N`, a few at a time across lanes, and that call cancels an earlier week's queued canaries (`fleet-bench canary retire`); the weekly retro queues none. It runs only while `floor_gate` is open (a red cluster shuts it only while the LiteLLM gateway is down too), never in a dry run. Queued canaries start in queue order, ranked by the class mix (`cleanup`, tag `canary`); past a full Claude pace target one pinned to another source with room starts on the other-source pass. `0` turns it off. Tests: "canary" in `tests/unit/fleet_dispatch_run_gates.bats` and "a canary pinned to another source" in `fleet_dispatch_run_floors.bats`.

   The project share: the conf's `DISPATCH_PROJECT_SHARE` is one table of `<project>:<percent>` words (`home-config:30 agent-runtime:10`; the human's picks, ask PaIYoy and epic ar-5367; listed only there, empty is off, a malformed word exits 78). When a project holds its percent or more of the queue items started in the last `DISPATCH_PROJECT_SHARE_H` hours (24, hand starts included; a hand start counts but is never refused), a pass starts none of that project's items but a red, the human's own (urgent `from: human`, `#requested` in the human's words, the ready phase of a plan the human queued (`plan:`, `from: human`; it still counts toward the share), the human floor) or a trainee floor start; any other urgent (a board row's `#urgent` included: the human's words carry `#requested`) and a canary on a Claude lane wait, and another project's item starts instead, its activity.log line ending `passed N items held by project share: ...`. Each project is held at its own cap, so one over its share never holds another under its own; the caps are independent and add up (home-config and agent-runtime together may take 40%), with no combined ceiling. A bare `#requested` is not the human's words: every `--want` stamps it, wind-down leftovers (`--want human` from a session) and the outbox and ask sweeps included. So promote reads the row's channel from notes' ingest record (`~/.local/state/notes/ingest.jsonl`, `asker_map`) into the item's `asker`; `asker=agent` counts under the cap and is no fresh ask for the human floor (ar-4912). Only focus, voice, request, meeting or a hand `--want human` read `human`; a row the record does not reach keeps its `#requested`. The fill passes their rows over too, the cleanup lane's included, so the board fills from other projects. With nothing else to start, the cap lets go: the queue pass goes on to the board, and when the board has nothing else either, the held item starts and its line says `the project share cap let it go`. The queue holds only work that can start: a board item the cap has held `DISPATCH_STARVED_MIN` (60) goes back to its row (`returned queue item ... to its board row`). A canary pinned to a harness with its own source (`harnesses.json` `source`) spends no Claude session, so it passes the cap, and while any project's share is full the canary top-up queues only those lanes (`canary queue --off-claude`; ask GDUmQQ, ar-4554). `fleet-dispatch headroom` prints one `project share:` line per project against its cap. A project off the table, or at `0`, has no cap. Before the cap, 82% of a day's starts were the fleet's work on itself. Tests: "project share:" in `tests/unit/fleet_dispatch_run_holds.bats`.
   Findings sampled in the last `DISPATCH_FINDING_FRESH_MIN` minutes hold only the items they are about, and the pass starts up to room queued items nothing holds, reading the gates again before each start after the first (`run --dry-run` names each held one): `starved pool:<pool>` holds items whose repo (origin's name) has jobs waiting in that pool, every item when the finding names no `repos`, when it binds on `capacity` or `admission` (a `labels` bind holds nothing: a held session would not free it); an urgent item held by starved pools alone goes past them, one start a pass (`pool_pass`, ar-3172), and `starved` names the finding that holds each item it lists. A `blind` finding holds nothing: it is a reader's gap, not a fault. Nor does `throughput-drop`: it names no binding stage, so a hold on it would starve the merges it waits on, and the stage it could mean (a pool starved on capacity or admission) holds on its own. Unreadable findings hold everything. A repo whose landing queue is over `DISPATCH_LANDING_QUEUE_MAX` PRs holds that repo's items the same way, except three kinds: urgent ones, which gate-line.py seats ahead of the queue; red ones, since a red main is often why the queue backs up; and the human's own asks. The depth is the deepest `landing_queue` on any session row in the fleet state document, so a queue no live session waits in reads as empty. A max that is empty or 0 turns the hold off. Items start again once the queue is at the max or under it (`landing_deep`, ask xxrlO7, ar-5306).
3. Board, only while fewer than `DISPATCH_LOW_WATER` queue items are runnable (or none, at 0). Above it the board is still read for its own rows only: `#requested` rows while fewer than the `requested` class `min_live` (`classes.json`, 4) runnable items carry the `requested` tag, cleanup rows while fewer than the `cleanup` one (2) carry `cleanup` (`class_gap`, from `agent-queue mix --json`; plan vast-soaring-prism P3 and ar-3944 removed `DISPATCH_REQUESTED_FLOOR` and `DISPATCH_CLEANUP_FLOOR`), any row of a project class's projects while that class's `min_live` is more than their live and runnable items, whatever class those rank in (`project_gaps`; `trader`, 2, so trader keeps sessions while a focus project fills the queue, and `unity` the same way, plan fleet-product-work-first P4; a project floor does not let the project share cap go, `share_let_go`), and every pass for committed rows (an agent row whose `#at/`, `#after/` or other gates all cleared), which go ahead of new picks up to the admission cap and start under the queue's own holds. An open sprint's rows go first of all: every pass, before the floors and the queue run, `sprint_top_up` queues the sprint's dispatchable rows (judged dispatch, or committed), as many as the pass's room or `DISPATCH_LOW_WATER`, whichever is larger, under the admission cap, and never in a dry run or a held pass, under the gate the sprint floor's start reads, so the queue order and the sprint floor take them ahead of queued off-sprint items (2026-11-21, ar-3816; "queues an open sprint's" in `tests/unit/fleet_dispatch_run.bats`, "still on the board" in `fleet_dispatch_run_floors.bats`). Candidates: every open `[ ]` row a worker may take, of each project at stage `dev` or later in `DISPATCH_PROFILES` (bnb and personal). A project is left out when `project-map.json` has no repo for it.
4. Judgment: one sonnet call for up to `DISPATCH_JUDGE_MAX` rows not judged before, each project's best-ranked row in turn so no board starves (an open sprint's row, its committed rows before the open version's uncommitted ones, then a cleanup row, first within a turn; the feed's `sprints` name the rows in `tasks` and `uncommitted`, so no row waits on a relock, and promote tags the item `sprint`, whichever path queues it), against `~/.config/fleet-dispatch/policy.md`. Every verdict, skip included, lands in `~/.agent/dispatch/verdicts.jsonl`, so a row is judged once until its text changes or the rule it names leaves the policy. A policy edit only dates the verdict (`policy` is the file's sig): it still picks and is not judged again, so an edit costs the judge's day budget nothing; to re-judge the rows a rule decided, give the changed rule a new id. `workers.json` is not in the key, since picks re-read it every pass. An `error` record never replaces an earlier verdict. Each verdict names the policy rule that decided it (`rule`, a `- (id)` bullet of the policy) and its call (`judge_call`, its `calls.jsonl` line); rows the reply left out are asked for once more in a second call of their own; a failed call, a reply that names no rule of the policy, or a row the retry leaves out too is an `error` verdict with its reason, and that row is judged again next pass (a retry stopped at its budget leaves no verdict and the pass names the stop). A dry run never judges. To change what gets picked, edit the policy, not the script.
5. Picks: verdict `dispatch` with size S or M, clear and agent-only, naming one `area`, judged no higher a tier than the row counts as, naming a rule the policy still defines (a stale verdict counts; picks re-check tier, size, area and the ceiling in code). Never two sessions on one area: an active queue item holds its area until reap closes it. One rank orders the picks: a cleanup row first (`kinds.json` `cleanup` on `DISPATCH_CLEANUP_PROJECTS`, unless it names shared infrastructure, `DISPATCH_CLEANUP_NOT`; it also promotes as high whatever its `#low`), then the project's `#prio/` (`notes projects --prio`, focus, high, normal, low), then, while a pool in `classes.json` `idle_pool.pools` runs under `busy_below` of its slots (`cc:pool_busy` over `cc:pool_slots`), a row whose repo runs workflows on that pool goes ahead of the others at the same due bucket, priority and `#requested` (the head of the feed rank), before age (`why` names `idle pool <pool>`; `run` logs each such pick, and `fleet-bench kpi` shows `pool_busy_share`), then the row's `#dueMMDD` (overdue, today, within 3 days), `#requested` (what the human asked for, as the night fill ranks it), worker order, row priority, kind (`kinds.json` `rank`, a bug first), stage, oldest `#cMMDD`. Each candidate carries a `why` naming them, and `fill --dry-run` prints it. Promoting tops the queue up to the mark; while the human is here the promoted items start at the trickle, the rest when they leave.
6. Launch: `fleet-dispatch start` (below) with the row and a brief that opens with its kind's `entry` (`/one-shot <row> ...` for code), on the world that declares `@agents`. The pass publishes WORKED only when a session started; BLOCKED when a gate, a finding, no account room or an `agent-hold dispatch` left a queue item waiting (amber on every dashboard, never a page; `queue-starved` pages); NOOP when nothing was runnable or the fleet is at its live cap; FAILED when it could not judge or could not start its pick. A WORKED pass that a limit stopped while runnable items waited and every gate was open says `under-used: ... <limit> is the limit` and logs it. `fleet-dispatch headroom` shows the window before raising `DISPATCH_PER_PASS` or a pace target: how many could start now, and the room under the target, load and run units (a heavy queue item holds 2 of the target's run units, a light one 1; `agent-queue add --weight` sets it). The load there counts each session started in the last `DISPATCH_START_LOAD_MIN` minutes as `DISPATCH_START_LOAD` more, because the 1-min load lags a start: a loop of hand starts that reads `headroom` between them is held once those starts fill the room. A hand start itself is never refused. Each real pass leaves that count in `~/.agent/dispatch/headroom.json`; `stats` publishes it as `could_start`, and the waybar Dispatch chip goes amber while it is over 0. Nothing raises a limit on its own; the human picks it.
7. Timing: a `run` pass ends with one stderr line, `pass steps: reap Ns, scan Ns, gates Ns, triage Ns, pass (K started) Ns, judge Ns, headroom and candidates Ns; Ts in all` (agentctl keeps it in `~/.local/state/agentctl/fleet-dispatch.stderr.log`), so a pass that runs long names its slow step. A board walk forks no process a row: one jq a board builds the rows, and the row patterns match in bash (ar-4911).

## Starting a session by hand: `fleet-dispatch start`

Every session an agent starts goes through `fleet-dispatch start`: the dispatch pass above, a session you start for a board row, and a reboot restore (`session-snapshot` restore). It opens the session (for a row, after re-reading the row, `ptask start`ing it, which stamps an id on a row with none, and checking it reads `[/]`), tags it `@dispatch` on its server (the session, or for a `--window` start the window it opened, since a session tag shows on every window) (the status line shows `dispatch: <project>: <row>`; the human reads it as "an agent started this"; a `--resume` whose item has no `origin` is the human's own conversation, a scratch send or the restore of a session they opened, and gets no tag) and records `session: <server>:<name>` on its queue item, the one record `reap` and `fleet-sessions` read (a bare name means `lab`). There is no separate session ledger. Never `wt new` + `claude` by hand, and never `tmux set-option @dispatch` on a session afterwards: on 2026-10-28 the human had to ask twice why sessions an agent started carried no label.

`run`, `reap`, `start`, `fill` and `promote` act only on the machine that holds the fleet lease (`fleet-lease fleet-dispatch`, the gate every singleton unit shares); elsewhere they say why and do nothing. `run` there exits 0, no fault, unless no remote of the store can say who holds the lease or this store is no peer clone (exit 1); the others exit 1. `fleet-dispatch hosts` prints who holds the lease on each remote (`fleet-lease status`), then an `unplaceable:` line for each project with queued items no worker can take, naming the missing clone (home-config `fleet_workers` `fleet_repos` or the host's `fleet_repos_extra`) or the harness no worker runs ready. Each real `run` also stores the `hosts --json` rows as one array in `hosts.json` beside `candidates.jsonl` (`hosts_write`), where the hub bar reads each worker's slots without ssh.

Park refuses a mid-turn session (log `preempt waits: <victim>: <why>`) and the pass tries the next. It parks one a pass and starts the urgent item in that pass when the freed units suffice and the gates pass, so a heavy item among light sessions takes two passes. A `run` pass, before it picks, unparks `why=preempt` ledgers, oldest first, while their units fit beside the ones the first urgent item or fresh ask it could start needs (one a finding, the gate or this machine's pace holds, or too heavy for the target's run units, keeps none; log `unpark keeps no run units for <slug>: <why>`; ar-3467), the findings read and no `dispatch` hold stands (log `unparked <key>`, or `unpark <key> failed: ...`). A pass never resumes a budget (`why=budget`), agent (`why=park`, `claude-acct unpark --all` resumes those) or human (`why=human`) park; `DISPATCH_PREEMPT=0` turns preempt off. `start` does not check the `dispatch` hold, which pauses only the runner. Before starting anything, read `agent-hold list` and `fleet-pace`'s pace check as for any other new work.

A dispatched session is an ordinary session from then on: the `shepherd` buckets, nudges and escalations apply to it unchanged, and its `/one-shot` records done on its row with proof. If it needs the human, it asks in its own conversation, files the same question with `agent-ask post`, and stops; the human answers in the session or from a board, and either way the answer lands in the session and closes the ask. Every pass that starts or reaps something appends a line to `~/.agent/dispatch/log.md`. `fleet-dispatch stats` counts it for the feed (HA sensor "Dispatch queue", Prometheus): runnable items and the oldest one's age, the queue's started, done and failed by the hour (from `agent-queue stats`), reap moves, and the items reaped `DISPATCH_FLAP_MOVES` or more times in an hour. Read those numbers, not the log, to answer "is dispatch moving".

## Steering the fleet onto projects: focus, rows and the share

No project ranks another's work. Three levers steer the fleet, each in one place:

- A row's own priority orders its work: board picks rank by the feed rank (RANK_JQ: due, priority, age) and the queue by `ORDER` (red, urgent, sprint, then priority). There is no project ladder: `notes projects --prio` takes only `focus` and `normal`, and refuses the retired `high` and `low` (ar-5207).
- `#prio/focus` turns a project's sprints on (`window::runs_sprints`) and ranks nothing. Set it with `notes projects --prio <p> --set focus` or `P` on the hub Projects tab (a toggle); `notes projects --prios` lists it. A focus always ends: `--set focus` writes a `Focus until:` head line (`--hours`, default 4, at most 24), and past it, or with none, the project reads as no focus. agent-web's Projects list shows it in its Focus strip, with Clear and a project and hours to set it.
- The project share cap holds each project of the conf's `DISPATCH_PROJECT_SHARE` to its own percent (above, step 2).
- The order in full: a `red` item, then an `urgent` one, then a `sprint` one, then item priority, then the class mix (`~/.config/fleet-dispatch/classes.json`, while `on`: inside each bucket the class furthest under its `share` of the items started in `window_days` goes next, history moving a class at most `lag_places` places, and a class with nothing queued gives its turns to the rest; agent-queue `MIX_JQ`). A class may name `projects` (matched after `tags` and `from`, before `kinds`, so a unity fix or chore without a `red`, `canary` or `from: human` leaves the bug and cleanup classes for `unity`) and a `min_live`: while fewer of its items than that are live (running or waiting), its first startable item goes ahead of the other classes in its bucket and `list --json` marks it `short`; the `unity` class (unity-core-playground, 6), `trader` (2), `requested` (4) and `cleanup` (2) set one; the last two also set how many `#requested` or `cleanup`-tagged runnable items the board top-up above the low water keeps (step 3), and being under `min_live` ranks the class first like any short one (`class_gap`). A short item that waits only on run units keeps the free ones from later non-urgent items, as an urgent one does but with no preempt (`pick_item`, "min_live:" in `tests/unit/fleet_dispatch_run_holds.bats`), so light fleet work cannot fill the run floor while heavy game work waits for its 2 units; load, idle and the holds still gate it. It ranks inside the pace target and starts nothing past it (ar-3943); a pass starts it ahead of reds past the red floor (the class floor, step 2). Then age. `agent-queue mix` shows each class against its share, its live items against `min_live` and the starved ones (runnable, none started in `starve_days`), mix on or off. A `#requested` row keeps its feed rank within its project and, under the `requested` class `min_live`, its top-up from the board (step 3).
- `headroom` names the focus projects and how many runnable items they hold (`focus`, `focus_runnable`); stats publishes `focus_projects` for the waybar hover's On focus count. A hand `start --item` and `cl` are never refused. Clear a focus with `--set normal`.

## A world server died: `fleet-dispatch restore`

`fleet-dispatch record` runs every minute from `fleet-state.service` and keeps `~/.agent/dispatch/panes/<server>.json` for each world in `.config/tmux-servers/`: every pane's session, window name, cwd and Claude session id. When the server it described is gone or restarted, it pages (`tmux <server> server died`) and renames the record to `<server>.lost.json`; when a `.lost.json` is still there (a restore that did not finish), the new record's conversations are added to it (one in both takes the newer window and cwd), so the second death never shrinks what a rerun brings back. A clean reboot pages the same way.

`fleet-dispatch restore` runs `tmx ensure`, then reopens each conversation through `start --resume --window`, as a window of the session it was in and in the permission mode its transcript last shows. A claude conversation whose queue item is running gets `RESTORE_PROMPT` as its first message and carries on by itself, in batches of the wake budget (fleet-pace skill, "Bulk wakes"): the rest stay closed on the record under the load hold `restore` until the minute record starts `fleet-restore.service` on room; one whose item waits, or the human's own with no item, comes back at an empty prompt. Each reopened pane is tagged `@fleet_restored` with the record's time, so its close timer runs on from the quiet it had when the server died (fleet-states.md, the close flow). It skips a conversation that is running (any account's `~/.claude*/sessions`), or that wound down on purpose (a `.request` or `.fired` in `~/.agent/spin-down/`), and lists plain shells and vanished folders without reopening them. A queue item needs no re-attaching: the same `<server>:<session>` comes back. All reopened renames the record to `<server>.restored.json`. A failure, or a record that grew during the walk, keeps it, so a rerun finishes the rest. `--dry-run` shows the list first. Until restore consumes a lost record, reap reads no item whose session or Claude it holds as gone, and an unreadable one holds every session of its server. On the fleet lease holder, both verbs then run on every other fleet worker at once as `<verb> --here` over `fleet_host_run`, since only a worker can read its own servers: each keeps its own record and reopens its own sessions. On any other machine they stay local. A worker that does not answer keeps its record for its next run and fails nothing; `--here` stays on this machine.

## Starved queue: a fleet-lead pass may start the head item

`fleet-dispatch starved` exits 1 when a dispatch hold has stood over `DISPATCH_STARVED_MIN` minutes (the runner's `held_since`, set by the first BLOCKED pass and kept across a run-floor start or one routed past the account hold; it leads with the Stopped line `fleet-dispatch stopped` prints, the one line hub Home and the briefing show), when an urgent or high queue item has been runnable over `DISPATCH_STARVED_MIN` minutes and no run pass started anything, or when runnable sits under `DISPATCH_LOW_WATER` with board rows a pass would pick and no run start in twice that time. It also exits 1 when board rows no verdict covers wait with no verdict written in `DISPATCH_STARVED_MIN` minutes, the human here or away, except at the pace target, where no pass reaches the judge. Its output also opens with "board rows gated on what can never clear" for each open or doing row whose gate `agent-queue gate` calls dead, such as an `#after/` naming no board row or a dropped one, or an `#ask/` the human cancelled or answered another way, which a reap settles first (`settle_answered_gates`: a cancelled ask closes a row whose done item's PR merged, else is posed again once; one that joined another moves the gate to it), so only a missing ask, a judge's or shepherd's answer, a re-posed ask cancelled again or a human-sheet row lasts here (`dead_holds`; `tests/unit/fleet_dispatch.bats`), and that alone exits 1 except while dispatch is held on purpose: nothing promotes such a row, so drop the tag or point it at the row that replaced it (the Sentinel watch `queue-starved` runs it, and its trip reaches the pass as a `watch:` due line). On 2026-11-04 four gates in turn held every pass for 7.5h while the shepherd watched and could not act. A `fleet-lead` pass that sees it:

1. `fleet-dispatch run --dry-run` and `agent-hold list` in one call, to read what stops a real pass.
2. If the block is load (the pace check says HOLD), account room (`claude-acct room`), or an `agent-hold` anyone set, leave it: those are the gates working. Answer the line with `fleet-shepherd skip` naming the gate; the watch has already paged the human.
3. Otherwise start the oldest item `starved` named, one per pass: `fleet-dispatch start --item <slug>`. Log it (`fleet-shepherd log "healed starved: <slug>, gate was <what dry-run said>"`) and file the gate that held it as an agent-board row, because a start by hand fixes the item, not the pass.

`starved` reads a fleet at its pace target as working. `fleet-dispatch idle-cap` is the other half: it exits 1 when the live sessions the target counts are at the target and under `DISPATCH_IDLE_CAP_PCT` (50) of them are busy (WORKING, or NEEDS carrying on), naming each idle one, and 2 with an `unreadable:` line on a missing or stale state document. The watch `fleet-cap-mostly-idle` runs it; its trip is a `red watch` item (triage-routes) whose owner moves the idle rows: the shepherd's nudge and takeover (`fleet-shepherd due`), or the cause that keeps them from closing.

`fleet-dispatch sprint-stalled` exits 1 naming each agent row of an open sprint that has gone `DISPATCH_STARVED_MIN` (60) minutes with no active queue item, no session and no open gate or child, with the row's last verdict; 2 with an `unreadable:` line on a failed queue, gate, board or worker read; 0 under a dispatch `agent-hold`. First sightings live in `~/.agent/dispatch/sprint-stalled.tsv`. The watch `sprint-stalled` runs it. Its owner reads `fleet-dispatch suggest` for each named row and fixes what holds it: a stale verdict, a tier no worker takes (`no worker takes it:`), or a `#plan` row inbox-plan has not taken. Queuing the row clears it.

## Do NOT

The fleet-wide list is in `fleet-lead`; this is this role's own.

- Set or clear a project's focus, or change `DISPATCH_PROJECT_SHARE`, without the human asking: they are the human's levers for where the fleet works.
- Widen dispatch beyond the profiles in `DISPATCH_PROFILES`, shrink the human-merge list (`DISPATCH_T3_SKIP`), relax the policy, raise a worker's `max_tier`, add a worker, or put `#worker/*` on a row, without the human asking. An agent filing a row may add its own `#tier/N` reading; assignment is the human's.
