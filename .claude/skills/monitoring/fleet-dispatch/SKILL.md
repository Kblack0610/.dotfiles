# fleet-dispatch

The intake role of `fleet-lead` (Binks). `fleet-dispatch` keeps the queue fed: the board tops it up while fewer than `DISPATCH_LOW_WATER` (3) items are runnable. Board items start as fast as the gates allow, the human here or away, under the same gates as any queue item (`DISPATCH_PER_PASS` caps a pass when set above 0); presence only picks the pace target (below). A pass promotes up to the low water, or the room it can start if that is more. `DISPATCH_LOW_WATER=0` fills only an empty queue. The agentctl runner `fleet-dispatch` runs `fleet-dispatch run` on the `SCHEDULE` in its conf (off while the conf says `ENABLED=no`; `agentctl enable fleet-dispatch` arms it, `agentctl disable fleet-dispatch` turns it off again); this skill is for running it by hand and reading what it decided. It is the only thing that starts sessions from the board unasked: a `fleet-lead` pass does so only to heal a starved queue (below), and no order should tell one to.

Away comes from `fleet-presence`: no keypress in any tmux client and no desktop input for `AWAY_AFTER_MIN` minutes (set in the conf), on this machine or on any machine that publishes to the store. The desktop counts because the human playing a test build holds no tmux client. Agents do not count: send-keys and paste-buffer leave `client_activity` alone (`tests/ui/fleet_presence.bats`). Dispatch can run on any machine and the human often sits at another, so every stowed machine runs `fleet-presence-publish.timer` every 2 minutes: `fleet-presence publish` writes its last input to `presence/<host>` in the agent store, which store-sync carries to every peer, and status reads each file as `<host>:<source>`. A file holds when the input was, not a verdict, so a machine that sleeps or dies ages into away on its own; a machine whose source reads unread writes nothing, so it cannot pin the fleet to here. It takes no time of day, because a night is a long away. When the human comes back, the next pass uses the present pace target and running sessions carry on. If it prints `unread`, usually because `hypridle` is not running, dispatch treats the human as here: the present target.

Pace targets: a pass starts a Claude item only while the fleet's live Claude sessions, hand starts included, are under the target: the live count plus the working Opus sessions the Claude accounts' spend has spare at their weekly pace (`claude-acct room --json` `.fleet.spare`, (keeps - burn) / rate, the `room for ~N more` of `claude-acct status`), at most `DISPATCH_TARGET_PRESENT` (set in `fleet-dispatch.conf`) while the human is here and `DISPATCH_TARGET_AWAY` (25) while away, and never under the run floor (the floor wins over the cap), so neither a day nor a night spends the week ahead of its line (2026-11-18: 30 present while the accounts carried 19). Burn and the rate count each working session by its model (`pace.conf` `MODEL_WEIGHT_*`, Opus 1), so a Sonnet or Haiku session leaves more spare, and each start is counted as one more Opus session, so the guess never overspends (ar-3230: 37 live read as full against a carry of 19 while the accounts spent 0.7/h of 1.6/h). The target is Claude's budget alone: past it, an item routed to another source with room still starts (the other-source pass below); `DISPATCH_RUN_FLOOR` (15) is the floor. The count is every non-parked session in the fleet state document `fleet-sessions` writes each minute, except one waiting its landing turn behind another PR (`open_job` `queue`): it holds a merge-line place, not a working slot; missing or older than `DISPATCH_STATE_FRESH_MIN` (10), it holds every start (BLOCKED). At the target a pass is NOOP. Hand starts count but are never refused. The runner's own sessions also hold at most the target in run units. `run --dry-run` and `headroom` print the target and the live count.

## Scope and triggers

Covers keeping the agent-queue topped up from the board, the pace target by presence, and starting a session by hand (`fleet-dispatch start`).

Use for "what would dispatch pick", "why did it skip that row", "start a session for this row", "pause dispatch". Moving live sessions through their plans: `shepherd`. Load and holds: `fleet-pace`.

Who may take a row is `~/.config/fleet-dispatch/workers.json`, walked in file order:

- `requested`: `#requested` rows tagged `#worker/requested`, on `unity-core-playground`, up to tier 2.
- `fleet`: rows the human tagged `#worker/fleet`, up to tier 1, with a `#tier/N`.
- `board`: agent-board rows of the game and its games (unity-core-playground, dodginballs, apociseum, shape-city) with no `#worker` tag, up to tier 2. No tags are needed, because the judge reads the tier. A row tagged `#tier/3` stays out.
- `personal`: agent-board rows of trader, black-dev, kenneth-black-portfolio and notes-cockpit with no `#worker` tag, up to tier 2. Finance is in no worker: its rows touch bank data and stay human-gated.
- `infra`: agent-board rows of agent-runtime and home-config with no `#worker` tag, up to tier 2. Their tier 3 rows (harness, CI, runners) still run only as tier3 items to a PR.

The human sheet stays opt-in: `board` never reads it. Tier 3 (CI, gates, runners, build, deploy, harness and tooling) has two lanes (policy.md, under Tier): a cleanup row (a `kinds.json` kind with `cleanup`: fix, chore, a deletion refactor) of `DISPATCH_CLEANUP_PROJECTS` at S or M becomes a merging day item tagged `cleanup tier3`, which agent-land lands only with a `Review: ` line in the PR body and checks that ran green; any other tier-3 row runs unattended only to an open PR, as a `tier3` queue item (below). A cleanup row judged unclear or size L goes to inbox-plan instead. An untiered item on a cleanup project counts as tier 3 (`fleet-dispatch item-tier SLUG`). A row whose text starts `ci:` or `infra:` counts as tier 3 whatever its tag says. What each tier means is defined in `~/.config/fleet-dispatch/policy.md`, under Tier.

What kind of work a row is comes from its type prefix (`fix(area):`), and `~/.config/fleet-dispatch/kinds.json` routes each kind, keyed by notes-cli's `ROW_TYPES` (`tests/unit/fleet_dispatch.bats` "kinds" pins the keys): `rank` orders rows the feed ranks alike (within a project the board feed's `rank` decides: due, priority, #requested, then age; a `fix` row, `label` "bug", goes first among equals and `why` says so), `entry` is the skill its session starts on (`/one-shot` for code, and for a row with no type), `rung` (build, propose, human) and `exit` (pr, doc+ask, proof) say how far it goes (a doc+ask brief has the session write a doc in the project's lab `docs/`, file one ask, record both with `agent-queue set <slug> report=<doc> ask=<id>`, close its row with `--proof doc:<path>` and move the item done, never open a PR; a proof brief, the `release` kind (off for board rows, so it starts only when the human starts it or `/release` queues it), has it record the live proof its skill names in `note=`, close its row on that proof and move the item done, never agent-land), and `stages`, `enabled` and an optional `off` list of projects say where it dispatches at all. A row of a kind that is off there, an `epic(` row, a parent row (an open row names it in `#of/`) and a backlog-tier row (`tier:backlog`, past its project's days budget (`agent_board_days`), which the notes sweep sets and lifts) never reach the judge; `suggest` names the reason, and a hand `start` still takes one. Turning a kind on or off is a line in that file, never the script. A row's `#size/` tag is its size: the judge reads it as given, picks trust it over the judge, and the judge's size for an unsized row with an id is written onto it as `#size/x`.

- `fleet-dispatch run --dry-run` runs the gates, says what would stop a real pass, and prints the picks without starting anything. It still judges new rows, up to `DISPATCH_JUDGE_MAX`. `fleet-dispatch run` starts them.
- `fleet-dispatch report` shows the latest verdict for every row it has judged: picked or skipped, size, judged tier, area, and the one-line reason. A verdict made under an older policy is marked stale.
- `fleet-dispatch candidates` lists the open rows it would judge next.
- `fleet-dispatch suggest [--json]` is the Candidates list, for display only: every open agent row (and every row a worker takes) of each project from dev up in every profile, in rank order, each with its `why`, `auto` (a worker in `workers.json` takes it; widening a project is a line there), the cached verdict or `unjudged`, and whether an active item holds its area. It never judges or queues. `suggest --write` stores that list in `~/.local/state/agentctl/dispatch/candidates.jsonl`, which every real `run` pass does and `promote` trims, and both hub Candidates folds read only that file, stamped `as of` its time.
- `agent-hold set dispatch "<reason>"` pauses it; `agent-hold release dispatch` resumes it.
- Level: the conf's `DISPATCH_PER_PASS` and `DISPATCH_MAX_LOAD`, and `claude-acct room`'s slack and reserve, are the `mid` numbers (`DISPATCH_PER_PASS` 0 is no cap at every level). The `machine-mode` level (low, mid, high) multiplies them where they are read, by `.config/machine-mode/levels`; `headroom` prints the level in force. Raise a limit in the conf, change the level with `machine-mode`.
- Tier-3 PR rows: the day fill (`run` and `fleet-dispatch fill`) also judges the open agent-lane rows of `DISPATCH_T3_PROJECTS` (agent-runtime, notes-cockpit, home-config, trader, audio, each at stage dev or later) of `DISPATCH_T3_PROFILE` and pulls the ones whose verdict says tier 3 is the only reason to skip (`tier3_only`) under the same room, gates and per-pass limit as any other row, one an area, as queue items tagged `tier3`; each brief stops at an open PR (`--pr-only`). A `#requested` row is eligible, since the human asked for it and the brief stops at a PR. It skips `decide:`, device, the human's machine, secrets, prod and wishes; it ranks `#requested` rows first, then observer rows (an improvement row tagged `#kpi/<k>`, or a `check(kpi):`, `fix(lesson):` and the like from retro and triage), then most urgent and oldest. Each row is `start`ed; `done` waits for the human's merge. There is no night tag and no night window: night runs builds and nightlies only, and real work is pulled from the board under the queue cap. `fleet-dispatch fill --dry-run` lists these rows as `ready` with worker `tier3-pr`.

## A pass, in order

1. Reap: an item whose session is gone is closed, or moves to `review/` (`on a PR`) while its PR is open. Gone means its tmux session ended, or agent-panel lists no Claude in that tmux session (a shell outlived claude), or, for an item started in a hub window, none of the Claude sessions it lists (`sessions:`) is live. A parked pane, another agent than claude, an item started in the last `DISPATCH_REAP_GRACE` seconds (600) and an empty or unreadable panel are never read as gone. A Claude missing from the panel is never the verdict while a process recorded for one of the item's `sessions:` ids still runs (`~/.claude*/sessions/<pid>.json`), and otherwise one witness: the item settles only when a reap at least `DISPATCH_REAP_CONFIRM` seconds (120) after the first also misses it, and a reap that does not read it gone clears the first miss (`~/.agent/dispatch/reap-miss/<slug>`). A tmux session that ended needs no second witness. An item on a fleet worker (`host:`) that does not answer is left alone until that worker has gone unanswered on every reap for `DISPATCH_HOST_DEAD` seconds (1800; `~/.agent/dispatch/host-miss/<host>`) while this machine still syncs the store (`store-sync-age`): then its running and waiting items with unfinished work go back to `queued/` with `lost: <host> <sessions>` and, with no PR, `salvage:` from the `branch:` its session's Stop hook last pushed, and a pass places them on a node that answers. An item reap cannot settle and nothing will change on its own (a partial landing whose requeued run also ended without the final one, a PR its forge cannot read, a done item's row with no merge proof on its forge remote, `forgejo` for a Forgejo checkout) is logged once, when its reason changes, and gets one human-sheet row (one page if the sheet refuses it): the partial at once, the others once they have stood `DISPATCH_ORPHAN_HOURS`. Its marker is `~/.agent/dispatch/stuck/<slug>`; deleting it files the row again on the next pass, and a marker no pass rewrote in a day is pruned (`tests/unit/fleet_dispatch_reap.bats`, "logged once"). An item a false reap closed goes back with `agent-queue reopen <slug>`. A live one moves to `waiting/` while its Claude waits on the human (agent-panel `waiting`, an open plan or dialog) or has a pending ask, back to `running/` after. An agent-lane row started with no active item naming it goes by the PR of an item done ok that names it (merged closes it on merge proof, open keeps it started); failing that it is un-started, with a `failed` verdict, once reap has seen it that way for `DISPATCH_ORPHAN_HOURS` (72); first sightings are in `~/.agent/dispatch/orphans.tsv`. An open agent-lane row whose `#ask/` gate the human answered with another option is settled: an answer that says skip drops it with the answer as its why, any other answer swaps the gate for `#hold/row-<id>`, an agent-hold that `agent-hold release row-<id>` lifts to start it (`settle_answered_gates`; "reap settle" in `tests/unit/fleet_dispatch_reap.bats`). Then the night fill (above). Room is the pace target (above) less the run units of live sessions the runner started (`origin: run`), no more than the target less every live session, capped at `DISPATCH_PER_PASS` when it is above 0.
2. Gates, each refusing when it cannot read its source (a red item has its own floor, below): no `dispatch` hold; `fleet-assess` not HOLD; cluster not red; 1-minute load under `DISPATCH_MAX_LOAD` per core; GitHub budget not LOW; real idle above `DISPATCH_MIN_IDLE` percent, idle plus nice time over a `DISPATCH_IDLE_WINDOW` (60) second `/proc/stat` delta, one sample reused by every gate for that window (nice-19 work yields by design; one 2 s `top` frame swung 17-41%, ar-34, ar-5). `fleet-assess`, load and real idle read only this machine, so they hold only a start here: while a fleet worker takes a session the pass goes on and places each item it can there; nothing starts here, and no session here is preempted, while they hold. At launch, `claude-acct room` must name an account under its weekly pace, or the row waits. While fewer than `DISPATCH_RUN_FLOOR` run sessions are live (this pass's starts counted), the weekly pace and real idle do not hold a start: room is asked with the pace line lifted, and still refuses an account in its reserve, its 5h window or emptied before its reset; the start's line says `on the run floor`. Why: hand starts never wait on pace, so without a floor they fill the week and no run start, and so no dispatch-judge outcome, ever happens (2026-11-05). Every closed gate is named in the pass's line, joined by `; `, the account one in `claude-acct room`'s own words. A nightly red is deliberately not a gate: nightlies stay red while sessions merge normally, and the NIGHTLY row handles it.

3. Board, only while fewer than `DISPATCH_LOW_WATER` queue items are runnable (or none, at 0). Above it a floor still reads the board for its own rows only: `DISPATCH_REQUESTED_FLOOR` (4) for `#requested` rows, `DISPATCH_CLEANUP_FLOOR` (2) for cleanup rows. Candidates: every open `[ ]` row a worker may take, of each project at stage `dev` or later in `DISPATCH_PROFILES` (bnb and personal). A project is left out when `project-map.json` has no repo for it.
4. Judgment: one sonnet call for up to `DISPATCH_JUDGE_MAX` rows not judged before, each project's best-ranked row in turn so no board starves (a cleanup row first within a turn), against `~/.config/fleet-dispatch/policy.md`. Every verdict, skip included, lands in `~/.agent/dispatch/verdicts.jsonl`, so a row is judged once until its text changes or the rule it names leaves the policy. A policy edit only dates the verdict (`policy` is the file's sig): it still picks and is not judged again, so an edit costs the judge's day budget nothing; to re-judge the rows a rule decided, give the changed rule a new id. `workers.json` is not in the key, since picks re-read it every pass. An `error` record never replaces an earlier verdict. Each verdict names the policy rule that decided it (`rule`, a `- (id)` bullet of the policy) and its call (`judge_call`, its `calls.jsonl` line); rows the reply left out are asked for once more in a second call of their own; a failed call, a reply that names no rule of the policy, or a row the retry leaves out too is an `error` verdict with its reason, and that row is judged again next pass (a retry stopped at its budget leaves no verdict and the pass names the stop). A dry run never judges. To change what gets picked, edit the policy, not the script.
5. Picks: verdict `dispatch` with size S or M, clear and agent-only, naming one `area`, judged no higher a tier than the row counts as, naming a rule the policy still defines (a stale verdict counts; picks re-check tier, size, area and the ceiling in code). Never two sessions on one area: an active queue item holds its area until reap closes it. One rank orders the picks: a cleanup row first (`kinds.json` `cleanup` on `DISPATCH_CLEANUP_PROJECTS`, unless it names shared infrastructure, `DISPATCH_CLEANUP_NOT`; it also promotes as high whatever its `#low`), then the project's `#prio/` (`notes projects --prio`, focus, high, normal, low), then the row's `#dueMMDD` (overdue, today, within 3 days), `#requested` (what the human asked for, as the night fill ranks it), worker order, row priority, kind (`kinds.json` `rank`, a bug first), stage, oldest `#cMMDD`. Each candidate carries a `why` naming them, and `fill --dry-run` prints it. Promoting tops the queue up to the mark; while the human is here the promoted items start at the trickle, the rest when they leave.
6. Launch: `fleet-dispatch start` (below) with the row and a brief that opens with its kind's `entry` (`/one-shot <row> ...` for code), on the world that declares `@agents`. The pass publishes WORKED only when a session started; BLOCKED when a gate, a finding, no account room or an `agent-hold dispatch` left a queue item waiting (amber on every dashboard, never a page; `queue-starved` pages); NOOP when nothing was runnable or the fleet is at its live cap; FAILED when it could not judge or could not start its pick. A WORKED pass that a limit stopped while runnable items waited and every gate was open says `under-used: ... <limit> is the limit` and logs it. `fleet-dispatch headroom` shows the window before raising `DISPATCH_PER_PASS` or a pace target: how many could start now, and the room under the target, load, idle and run units (a heavy queue item holds 2 of the target's run units, a light one 1; `agent-queue add --weight` sets it). The load there counts each session started in the last `DISPATCH_START_LOAD_MIN` minutes as `DISPATCH_START_LOAD` more, because the 1-min load lags a start: a loop of hand starts that reads `headroom` between them is held once those starts fill the room. A hand start itself is never refused. Each real pass leaves that count in `~/.agent/dispatch/headroom.json`; `stats` publishes it as `could_start`, and the waybar Dispatch chip goes amber while it is over 0. Nothing raises a limit on its own; the human picks it.

## Starting a session by hand: `fleet-dispatch start`

Every session an agent starts goes through `fleet-dispatch start`: the dispatch pass above, a session you start for a board row, and a reboot restore (`session-snapshot` restore). It opens the session (for a row, after re-reading the row, `ptask start`ing it, which stamps an id on a row with none, and checking it reads `[/]`), tags it `@dispatch` on its server (the status line shows `dispatch: <project>: <row>`; the human reads it as "an agent started this"; a `--resume` whose item has no `origin` is the human's own conversation, a scratch send or the restore of a session they opened, and gets no tag) and records `session: <server>:<name>` on its queue item, the one record `reap` and `fleet-sessions` read (a bare name means `lab`). There is no separate session ledger. Never `wt new` + `claude` by hand, and never `tmux set-option @dispatch` on a session afterwards: on 2026-10-28 the human had to ask twice why sessions an agent started carried no label.

`run`, `reap`, `start`, `fill` and `promote` act only on the machine that holds the fleet lease (`fleet-lease fleet-dispatch`, the gate every singleton unit shares); elsewhere they say why and do nothing. `run` there exits 0, no fault, unless no remote of the store can say who holds the lease or this store is no peer clone (exit 1); the others exit 1. `fleet-dispatch hosts` prints who holds the lease on each remote (`fleet-lease status`).

- For a queue item: `fleet-dispatch start --item <slug> [--model <m>]`. It cuts a fresh worktree with `wt new --detach` and moves the item to `running/`.

- On another harness: add `--harness claude-lazer|lazer-reserve|opencode|codex` and a `--model` from `~/.config/agentctl/harnesses.json`, or set `agent:` and `model:` on the item. claude-lazer and opencode go through the gateway on the eval key, lazer-reserve on the claude-reserve key, codex on the ChatGPT plan login. Each harness names the source it spends (`source` in `harnesses.json`) and a start asks `claude-acct room --source <name>`. A pinned start (by hand, a batch, or a pass for an item pinned by `agent:`) logs under model-lane lane `eval`. QUEUE.md "Harnesses" has the rest.
- Routing: a run pass starts each queue item on the first of its model-lane candidates (`candidates` in `lanes.yaml`, in fit order, each fit ordered by its source's rank in `claude-acct room --json`, lowest first) that has room and may take it: a fleet worker and `DISPATCH_SANDBOX_PROFILE` run claude only, a headless harness (`headless` in the map) takes no plan item and, pinned or not, no excluded kind of work (an `excluded` entry with a `match` in fleet-bench's `matrix.json`: deploy, prod, secrets, release, store, Unity editor and play, live host ops such as a runner drain, deregister or systemctl stop; none at all while that file is unreadable), and a routed item past the unattended tier ceiling stays on claude unless it is a red, which may go to a harness that is not headless. An item pinned by `agent:` is its own one candidate; `routed: <harness>` marks a routed one, so a requeued item routes again. When no account has room the gate stays open while another source has room; an item no candidate can take is skipped for the pass (its verdict is cached for the day) and named in the BLOCKED reason. The source's own `reserve` and `max_live` in `~/.config/claude-acct/sources` bound it (`reserve` 2 live, the `lazer` pool's 20% reserve). `claude-acct` refuses to park or move a Lazer pane, so the shepherd's budget park logs "could not park" and the key's own budget bounds it.
- Trainees: a queued row of at most lanes.yaml `trainee: points` (its board row's points now, else the `#pts/N` its task was queued with; `start` reads them with `agent-queue show --json --points`) at a tier in `trainee: tiers`, or a tier-3 row `cleanup_row` accepts whose slug's cksum is a multiple of `tier3_share` (`tier3_pick`), whose kind opens a PR, not a plan, canary, verify or review item, with no model of its own and no trainee run before, is offered first to the `trainee:` candidates on a lane sandbox (one model per harness, picked by the slug), each under its `projects` allowlist, `max_open` open ladder rows (trainee or direct) and `max_live` running items per harness (none named, no cap past max_open), whenever its source has room, the Claude hold or not. A trainee's provider is a free key that sees the row and its repo, and its gateway sandbox builds no cargo or npm, so `trainee_public_why` refuses a row whose repo is not in `DISPATCH_TRAINEE_REPOS` (`~/.dotfiles`), whose words match that repo's `.githooks/sensitive-tokens.txt`, or that names a file it does not track or one that is no shell, bats or markdown file outside a cargo or npm tree. Those tiers stand in for the harness's `max_tier` and the unattended ceiling, because the review lands the diff; a tier-3 row's review brief asks for the `Review:` line agent-land's review_gate wants. The run is stamped `trainee: <harness>:<model>` and logs under lane `trainee`; it cannot commit, so its tail, `fleet-dispatch trainee-review <slug>` outside the sandbox, saves the worktree diff to `~/.local/state/agentctl/dispatch/trainee/<slug>.patch` beside its base (`<slug>.base`), puts the worktree back and moves the row to review, where it waits for a batch review. The trainee floor runs each pass after the canary floor, past the pace target: it files and starts one `trainee-batch-<stamp>` item (`--from trainee`, tags `trainee-review trainee-batch`, claude on the `reviewer` lane's model, a brief of every waiting diff) once `review_batch` diffs wait or one waits while a trainee holds its max_open rows, never two at once; then each trainee harness with a free slot starts the first queued row it takes, else promotes the top-ranked judged board row it takes that names at least one file, and starts it in the same step, so no promoted row sits queued. Each pass says why it is shut ("trainee floor: ..."); `candidates: []` turns it off. The review lands each row with `agent-land <N> --item <slug>` or runs `fleet-dispatch trainee-reject <slug> --why "<why>"`, which sends the row back to the queue on claude (a redo on the trainee's run, its why on that run for `model-lane score`); no diff is a reject too. Tests: `tests/unit/fleet_dispatch_run.bats` and `fleet_dispatch_start.bats` "trainee" and "trainee floor:". <!-- skill-drift: ignore (the trainee dir is created by the first trainee run) -->
- Direct runs: once `model-lane score` promotes a trainee pair for a class (the next rung), the verdict lists it in `direct` (apart from a lane's `promoted`, which never lands unreviewed) for that class and the trainee offer leaves it out. route takes it at its own fit for any tier-1 row of the class that opens a PR, any `#pts`, never one a ladder run took before (`trainee:` or `direct:`), still in its sandbox, under `max_tier` and inside the harness's `max_open` ladder rows (`direct_why`). No diff, a failed hook, push or PR, or a failed landing closes the PR and sends the row back to the queue on claude (a redo, which model-lane counts toward the send-back to trainee); a PR agent-land merged before it failed stays, the row running. Tests: `fleet_dispatch_run.bats` and `fleet_dispatch_start.bats` "direct".
- Every start of a Claude item with no `--model` (a run pass, a hand start, a plan phase, an `after:` chain) picks the model with `model-lane classify --floor $DISPATCH_LANE_FLOOR --size <its #size/ tag>` on the item's headline, never its body or weight (sonnet: a dispatched session lands its own PR), logs the run and stamps `lane_run=<id>` on the item; the item's close reports its outcome (`agent-queue move`). A model-lane failure starts the item on opus, unlogged. An explicit `--model` wins and logs nothing.
- For a row: `fleet-dispatch start --project <p> [--agent] --row <id> --brief <file> [--model <m>]`. Write the brief to a file first: `/one-shot <task>`, then where the row is and how to record it done. `start` claims the row, promotes it to a queue item (slug and `from: board:<project>:<id>` from the row's id, priority from the row, high on a bare row; a row with no id is refused when its project has no `code`) and starts that item. Do not `start` the row yourself first: `start` refuses a row that is not open.
- To queue a row without starting it: `fleet-dispatch promote --project <p> [--profile <x>] [--agent] --raw "<line>"`, what the Board tab's Start runs. It takes the row's exact line, refuses one that changed or is already started, and the item starts like any board item, under the pass's gates.
- One conversation: `fleet-dispatch start --project <p> --server <server> --session <name> --cwd <dir> --resume <claude session id> [--item <slug>]`. With `--item` (a running or waiting item) the item records the new session, `origin: resume`; without one the session is only tagged. The sheet is left alone, `--row` is refused, and a session name that already exists on that server is refused unless `--window <name>` says to open it as a window of that session. It reopens in the permission mode its transcript last shows.
- A lost server or a reboot: `fleet-dispatch restore [--server <s>] [--dry-run]`, below.
- A queue item's claude start or resume drops the tools in `CLAUDE_AUTO_DROP_TOOLS` (`claude-telemetry.sh`: `Workflow,ScheduleWakeup,Artifact`) with `--disallowedTools`, as runners and shepherd passes do, because an unattended session almost never calls them and their schemas are paid on every turn. A task that names one of them, ultracode or `/loop` keeps every tool, and so does an empty value. A resume of a conversation no queue item lists drops nothing.
- `DISPATCH_SANDBOX_PROFILE` (empty, off) runs every claude start and resume under that lane sandbox profile (`~/.config/agentctl/sandbox/<name>.json`, `lane_sandbox` over `agent-run/lib/sandbox.sh`; `DISPATCH_SANDBOX_GH_TOKEN_FILE` is the session's own GitHub token). A missing or malformed profile, or a start on a non-claude harness, refuses the start and the item stays queued. Contract: agent-run `docs/contract.md` "Lane sandbox".

Only the sessions the dispatch pass started count against the run units (the pace target, heavy 2, light 1) and its area rule; hand launches and restores carry the label and their item but hold none of its slots. A parked session (a `claude-acct park` ledger) holds none either. Preempt: when the first urgent item or fresh ask waits only on this machine's units, the pass parks one runner session for it with `claude-acct park --why preempt --for <slug>`, never a hand session, one running an urgent item or fresh ask, or one preempted in the last `DISPATCH_PREEMPT_REST` minutes (60, log `preempt spares <victim>`); one whose weight covers the shortfall goes first, then lowest priority, then newest start. Park refuses a mid-turn session (log `preempt waits: <victim>: <why>`) and the pass tries the next. It parks one a pass and starts the urgent item in that pass when the freed units suffice and the gates pass, so a heavy item among light sessions takes two passes. A `run` pass, before it picks, unparks `why=preempt` ledgers, oldest first, while their units fit, no urgent item it could start waits (one a finding holds or too heavy for the target's run units does not count), the findings read and no `dispatch` hold stands (log `unparked <key>`, or `unpark <key> failed: ...`). Budget (`why=budget`), agent (`why=park`) and the human's (`why=human`) parks are never touched; `DISPATCH_PREEMPT=0` turns preempt off. `start` does not check the `dispatch` hold, which pauses only the runner. Before starting anything, read `agent-hold list` and `fleet-pace`'s pace check as for any other new work.

A dispatched session is an ordinary session from then on: the `shepherd` buckets, nudges and escalations apply to it unchanged, and its `/one-shot` records done on its row with proof. If it needs the human, it asks in its own conversation, files the same question with `agent-ask post`, and stops; the human answers in the session or from a board, and either way the answer lands in the session and closes the ask. Every pass that starts or reaps something appends a line to `~/.agent/dispatch/log.md`. `fleet-dispatch stats` counts it for the feed (HA sensor "Dispatch queue", Prometheus): runnable items and the oldest one's age, the queue's started, done and failed by the hour (from `agent-queue stats`), reap moves, and the items reaped `DISPATCH_FLAP_MOVES` or more times in an hour. Read those numbers, not the log, to answer "is dispatch moving".

## Steering the fleet onto projects: `#prio`

One store sets project precedence: the `#prio/<word>` head tag on a project's lab front page, set by `notes projects --prio <p> --set <word>` or `P` on the hub Projects tab, which steps normal, focus, high, low (`notes projects --prios` lists them).

- One ladder, rank only: `focus`, then `high`, normal, `low`. Board picks (RANK_JQ `pprio`) and queue order (agent-queue `ORDER` `$rank`) put a focus project's work first, so a pass starts focus items first and starts a lower tier only when no focus item can (held by an `after:`, a tag window or a resource, or no place for it). Nothing is held or skipped for a focus, so a focus never blocks the fleet and an empty one costs nothing. There is no hold list.
- Above the tier: a `red` item, then an `urgent` one (so a queued item's `#urgent` jumps every tier). Below it: item priority, then the class mix (`~/.config/fleet-dispatch/classes.json`, while `on`: inside each bucket the class furthest under its `share` of the items started in `window_days` goes next, history moving a class at most `lag_places` places, and a class with nothing queued gives its turns to the rest; agent-queue `MIX_JQ`), then age. `agent-queue mix` shows each class against its share and the starved ones (runnable, none started in `starve_days`), mix on or off. A `#requested` row keeps its feed rank within its project and its floor (`DISPATCH_REQUESTED_FLOOR`).
- `headroom` names the focus projects and how many runnable items they hold (`focus`, `focus_runnable`); stats publishes `focus_projects` for the waybar hover. A hand `start --item` and `cl` are never refused. Clear a focus with `--set normal`.

## A world server died: `fleet-dispatch restore`

`fleet-dispatch record` runs every minute from `fleet-state.service` and keeps `~/.agent/dispatch/panes/<server>.json` for each world in `.config/tmux-servers/`: every pane's session, window name, cwd and Claude session id. When the server it described is gone or restarted, it pages (`tmux <server> server died`) and renames the record to `<server>.lost.json`; when a `.lost.json` is still there (a restore that did not finish), the new record's conversations are added to it (one in both takes the newer window and cwd), so the second death never shrinks what a rerun brings back. A clean reboot pages the same way.

`fleet-dispatch restore` runs `tmx ensure`, then reopens each conversation through `start --resume --window`, as a window of the session it was in and in the permission mode its transcript last shows. A claude conversation whose queue item is running gets `RESTORE_PROMPT` as its first message and carries on by itself, in batches of the wake budget (fleet-pace skill, "Bulk wakes"): the rest stay closed on the record under the load hold `restore` until the minute record starts `fleet-restore.service` on room; one whose item waits, or the human's own with no item, comes back at an empty prompt. It skips a conversation that is running (any account's `~/.claude*/sessions`), or that wound down on purpose (a `.request` or `.fired` in `~/.agent/spin-down/`), and lists plain shells and vanished folders without reopening them. A queue item needs no re-attaching: the same `<server>:<session>` comes back. All reopened renames the record to `<server>.restored.json`. A failure, or a record that grew during the walk, keeps it, so a rerun finishes the rest. `--dry-run` shows the list first. Until restore consumes a lost record, reap reads no item whose session or Claude it holds as gone, and an unreadable one holds every session of its server. On the fleet lease holder, both verbs then run on every other fleet worker at once as `<verb> --here` over `fleet_host_run`, since only a worker can read its own servers: each keeps its own record and reopens its own sessions. On any other machine they stay local. A worker that does not answer keeps its record for its next run and fails nothing; `--here` stays on this machine.

## Starved queue: a fleet-lead pass may start the head item

`fleet-dispatch starved` exits 1 when a dispatch hold has stood over `DISPATCH_STARVED_MIN` minutes (the runner's `held_since`, set by the first BLOCKED pass and kept across a run-floor start or one routed past the account hold; it leads with the Stopped line `fleet-dispatch stopped` prints, the one line hub Home and the briefing show), when an urgent or high queue item has been runnable over `DISPATCH_STARVED_MIN` minutes and no run pass started anything, or when runnable sits under `DISPATCH_LOW_WATER` with board rows a pass would pick and no run start in twice that time (the Sentinel watch `queue-starved` runs it, and its trip reaches the pass as a `watch:` due line). On 2026-11-04 four gates in turn held every pass for 7.5h while the shepherd watched and could not act. A `fleet-lead` pass that sees it:

1. `fleet-dispatch run --dry-run` and `agent-hold list` in one call, to read what stops a real pass.
2. If the block is load (the pace check says HOLD), account room (`claude-acct room`), or an `agent-hold` anyone set, leave it: those are the gates working. Answer the line with `fleet-shepherd skip` naming the gate; the watch has already paged the human.
3. Otherwise start the oldest item `starved` named, one per pass: `fleet-dispatch start --item <slug>`. Log it (`fleet-shepherd log "healed starved: <slug>, gate was <what dry-run said>"`) and file the gate that held it as an agent-board row, because a start by hand fixes the item, not the pass.

## Do NOT

The fleet-wide list is in `fleet-lead`; this is this role's own.

- Set or clear a project's `#prio` without the human asking: it is their lever for where the fleet works.
- Widen dispatch beyond the profiles in `DISPATCH_PROFILES`, add a tier-3 PR project (`DISPATCH_T3_PROJECTS`), relax the policy, raise a worker's `max_tier`, add a worker, or put `#worker/*` on a row, without the human asking. An agent filing a row may add its own `#tier/N` reading; assignment is the human's.
