# fleet-dispatch

The intake role of `fleet-lead` (Binks). `fleet-dispatch` keeps the queue fed: the board tops it up while fewer than `DISPATCH_LOW_WATER` (3) items are runnable, and board items start up to `DISPATCH_PER_PASS` a pass while the human is away, or `DISPATCH_PRESENT_PER_HOUR` (1) an hour while they are here. Setting both to 0 brings back the empty-queue, away-only fill. The agentctl runner `fleet-dispatch` runs `fleet-dispatch run` on the `SCHEDULE` in its conf (off while the conf says `ENABLED=no`; `agentctl enable fleet-dispatch` arms it, `agentctl disable fleet-dispatch` turns it off again); this skill is for running it by hand and reading what it decided. It is the only thing that starts sessions from the board unasked: a `fleet-lead` pass does so only to heal a starved queue (below), and no order should tell one to.

Away comes from `fleet-presence`: no keypress in any tmux client and no desktop input for `AWAY_AFTER_MIN` minutes (set in the conf). It takes no time of day, because a night is a long away. When the human comes back, board starts drop to the present trickle at the next pass and running sessions carry on; night items wait for away. If it prints `unread`, usually because `hypridle` is not running, dispatch treats the human as here: the trickle.

Who may take a row is `~/.config/fleet-dispatch/workers.json`, walked in file order:

- `requested`: `#requested` rows tagged `#worker/requested`, on `unity-core-playground`, up to tier 2.
- `fleet`: rows the human tagged `#worker/fleet`, up to tier 1, with a `#tier/N`.
- `board`: agent-board rows of the game and its games (unity-core-playground, dodginballs, apociseum, shape-city) with no `#worker` tag, up to tier 2. No tags are needed, because the judge reads the tier. A row tagged `#tier/3` stays out.
- `personal`: agent-board rows of trader, black-dev, kenneth-black-portfolio and notes-cockpit with no `#worker` tag, up to tier 2. Finance is in no worker: its rows touch bank data and stay human-gated.

The human sheet stays opt-in: `board` never reads it. Tier 3 (CI, gates, runners, build, deploy, harness and tooling) has two lanes (policy.md, under Tier): a cleanup row (a `kinds.json` kind with `cleanup`: fix, chore, a deletion refactor) of `DISPATCH_CLEANUP_PROJECTS` at S or M becomes a merging day item tagged `cleanup tier3`, which agent-land lands only with a `Review: ` line in the PR body and checks that ran green; any other tier-3 row runs unattended only to an open PR, as a `night` queue item (below). A cleanup row judged unclear or size L goes to inbox-plan instead. An untiered item on a cleanup project counts as tier 3 (`fleet-dispatch item-tier SLUG`). A row whose text starts `ci:` or `infra:` counts as tier 3 whatever its tag says. What each tier means is defined in `~/.config/fleet-dispatch/policy.md`, under Tier.

What kind of work a row is comes from its type prefix (`fix(area):`), and `~/.config/fleet-dispatch/kinds.json` routes each kind, keyed by notes-cli's `ROW_TYPES` (`tests/unit/fleet_dispatch.bats` "kinds" pins the keys): `rank` orders rows within a priority (a `fix` row, `label` "bug", goes first and `why` says so), `entry` is the skill its session starts on (`/one-shot` for code, and for a row with no type), `rung` (build, propose, human) and `exit` (pr, doc+ask) say how far it goes (a doc+ask brief has the session write a doc in the project's lab `docs/`, file one ask, record both with `agent-queue set <slug> report=<doc> ask=<id>`, close its row with `--proof doc:<path>` and move the item done, never open a PR), and `stages`, `enabled` and an optional `off` list of projects say where it dispatches at all. A row of a kind that is off there, an `epic(` row, and a parent row (an open row names it in `#of/`) never reach the judge; `suggest` names the reason. Turning a kind on or off is a line in that file, never the script. A row's `#size/` tag is its size: the judge reads it as given, picks trust it over the judge, and the judge's size for an unsized row with an id is written onto it as `#size/x`.

- `fleet-dispatch run --dry-run` runs the gates, says what would stop a real pass, and prints the picks without starting anything. It still judges new rows, up to `DISPATCH_JUDGE_MAX`. `fleet-dispatch run` starts them.
- `fleet-dispatch report` shows the latest verdict for every row it has judged: picked or skipped, size, judged tier, area, and the one-line reason. A verdict made under an older policy is marked stale.
- `fleet-dispatch candidates` lists the open rows it would judge next.
- `fleet-dispatch suggest [--json]` is the Candidates list, for display only: every open agent row (and every row a worker takes) of each project from dev up in every profile, in rank order, each with its `why`, `auto` (a worker in `workers.json` takes it; widening a project is a line there), the cached verdict or `unjudged`, and whether an active item holds its area. It never judges or queues.
- `agent-hold set dispatch "<reason>"` pauses it; `agent-hold release dispatch` resumes it.
- Level: the conf's `DISPATCH_PER_PASS`, `DISPATCH_NIGHT_MAX` and `DISPATCH_MAX_LOAD`, and `claude-acct room`'s slack and reserve, are the `mid` numbers. The `machine-mode` level (low, mid, high) multiplies them where they are read, by `.config/machine-mode/levels`; `headroom` prints the level in force. Raise a limit in the conf, change the level with `machine-mode`.
- Night items: every run pass, and `fleet-dispatch fill`, judges the open agent-lane rows of `DISPATCH_NIGHT_PROJECTS` (agent-runtime, notes-cockpit, home-config, trader, audio, each at stage dev or later) of `DISPATCH_NIGHT_PROFILE` and promotes up to `DISPATCH_NIGHT_MAX` (6 active, one an area) whose verdict says tier 3 is the only reason to skip (`tier3_only`) as queue items tagged `night`, which agent-queue holds to its night window; each brief stops at an open PR. A `#requested` row is eligible, since the human asked for it and the brief stops at a PR. It skips `decide:`, device, the human's machine, secrets, prod and wishes; it ranks `#requested` rows first, then observer rows (an improvement row tagged `#kpi/<k>`, or a `check(kpi):`, `fix(lesson):` and the like from retro and triage), then most urgent and oldest. Each row is `start`ed; `done` waits for the human's merge. A run pass does this right after reap, ahead of run units, the queue's depth and the gates, since promoting is not starting; only a `dispatch` hold stops it, and the pass's line starts `queued N for the night`. A judge that fails there does not stop the queue: the pass goes on and ends FAILED. `fleet-dispatch fill --dry-run` lists them as `night`.

## A pass, in order

1. Reap: an item whose session is gone is closed. Gone means its tmux session ended, or agent-panel lists no Claude in that tmux session (a shell outlived claude), or, for an item started in a hub window, none of the Claude sessions it lists (`sessions:`) is live. A parked pane, another agent than claude, an item started in the last `DISPATCH_REAP_GRACE` seconds (600) and an empty or unreadable panel are never read as gone. A live one moves to `waiting/` while its Claude waits on the human (agent-panel `waiting`, an open plan or dialog) or has a pending ask, back to `running/` after. An agent-lane row started with no active item naming it is un-started, with a `failed` verdict, once reap has seen it that way for `DISPATCH_ORPHAN_HOURS` (72); first sightings are in `~/.agent/dispatch/orphans.tsv`. Then the night fill (above). Room is `DISPATCH_MAX_LIVE` minus live sessions the runner started (`origin: run`), capped at `DISPATCH_PER_PASS`.
2. Gates, each refusing when it cannot read its source (a red item has its own floor, below): no `dispatch` hold; `fleet-assess` not HOLD; cluster not red; 1-minute load under `DISPATCH_MAX_LOAD` per core; GitHub budget not LOW; real idle above `DISPATCH_MIN_IDLE` percent on a two-frame `top` sample. At launch, `claude-acct room` must name an account under its weekly pace, or the row waits. While fewer than `DISPATCH_RUN_FLOOR` run sessions are live (this pass's starts counted), the weekly pace and real idle do not hold a start: room is asked with the pace line lifted, and still refuses an account in its reserve, its 5h window or emptied before its reset; the start's line says `on the run floor`. Why: hand starts never wait on pace, so without a floor they fill the week and no run start, and so no dispatch-judge outcome, ever happens (2026-11-05). Every closed gate is named in the pass's line, joined by `; `, the account one in `claude-acct room`'s own words. A nightly red is deliberately not a gate: nightlies stay red while sessions merge normally, and the NIGHTLY row handles it.
   The red floor: while fewer than `DISPATCH_RED_FLOOR` (2) red items the runner started are live (this pass's red starts counted), a red item at the head of the queue starts past real idle, load, a `fleet-assess` HOLD and the weekly pace, and only red items start on it that pass. `agent-hold`, the reserve, a red cluster and the GitHub budget still hold it. Human decision 2026-11-06: a fix held behind a busy machine keeps the fleet red. Tests: "red floor:" in `tests/unit/fleet_dispatch.bats`.
   Findings sampled in the last `DISPATCH_FINDING_FRESH_MIN` minutes hold only the items they are about, and the pass starts up to room queued items nothing holds, reading the gates again before each start after the first (`run --dry-run` names each held one): `starved pool:<pool>` holds items whose repo (origin's name) has jobs waiting in that pool, every item when the finding names no `repos`; `throughput-drop <project>` holds items on that project's repo; `starved <host>` holds every item. A `blind` finding holds nothing: it is a reader's gap, not a fault. Unreadable findings hold everything.
3. Board, only while fewer than `DISPATCH_LOW_WATER` queue items are runnable (or none, at 0). Candidates: every open `[ ]` row a worker may take, of each project at stage `dev` or later in `DISPATCH_PROFILES` (bnb and personal). A project is left out when `project-map.json` has no repo for it.
4. Judgment: one sonnet call for up to `DISPATCH_JUDGE_MAX` rows not judged before, each project's best-ranked row in turn so no board starves, against `~/.config/fleet-dispatch/policy.md`. Every verdict, skip included, lands in `~/.agent/dispatch/verdicts.jsonl`, so a row is judged once until its text or the policy changes; `workers.json` is not in the key, since picks re-read it every pass. Each verdict names the policy rule that decided it (`rule`, a `- (id)` bullet of the policy) and its call (`judge_call`, its `calls.jsonl` line); a failed call, a reply that names no rule of the policy, or a row the reply left out is an `error` verdict with its reason, and that row is judged again next pass. A dry run never judges. To change what gets picked, edit the policy, not the script.
5. Picks: verdict `dispatch` with size S or M, clear and agent-only, naming one `area`, judged no higher a tier than the row counts as, made under the current policy. Never two sessions on one area: an active queue item holds its area until reap closes it. One rank orders the picks and the judge's cap: a red row first, then a cleanup row (`kinds.json` `cleanup` on `DISPATCH_CLEANUP_PROJECTS`, which also promotes as high whatever its `#low`), then the project's `#prio/` (`notes projects --prio`, focus, high, normal, low), then the row's `#dueMMDD` (overdue, today, within 3 days), `#requested` (what the human asked for, as the night fill ranks it), worker order, row priority, kind (`kinds.json` `rank`, a bug first), stage, oldest `#cMMDD`. Each candidate carries a `why` naming them, and `fill --dry-run` prints it. Promoting tops the queue up to the mark; while the human is here the promoted items start at the trickle, the rest when they leave.
6. Launch: `fleet-dispatch start` (below) with the row and a brief that opens with its kind's `entry` (`/one-shot <row> ...` for code), on the world that declares `@agents`. The pass publishes WORKED only when a session started; BLOCKED when a gate, a finding or no account room left a queue item waiting (amber on every dashboard, never a page; `queue-starved` pages); NOOP when nothing was runnable, the fleet is at its live cap, or the human held dispatch; FAILED when it could not judge or could not start its pick. A WORKED pass that a limit stopped while runnable items waited and every gate was open says `under-used: ... <limit> is the limit` and logs it. `fleet-dispatch headroom` shows the window before raising `DISPATCH_PER_PASS` or `DISPATCH_MAX_LIVE`: how many could start now, and the room under load, idle and run units (a heavy queue item holds 2 of `DISPATCH_MAX_LIVE`, a light one 1; `agent-queue add --weight` sets it). Each real pass leaves that count in `~/.agent/dispatch/headroom.json`; `stats` publishes it as `could_start`, and the waybar Dispatch chip goes amber while it is over 0. Nothing raises a limit on its own; the human picks it.

## Starting a session by hand: `fleet-dispatch start`

Every session an agent starts goes through `fleet-dispatch start`: the dispatch pass above, a session you start for a board row, and a reboot restore (`session-snapshot` restore). It opens the session (for a row, after re-reading the row, `ptask start`ing it, which stamps an id on a row with none, and checking it reads `[/]`), tags it `@dispatch` on its server (the status line shows `dispatch: <project>: <row>`; the human reads it as "an agent started this") and records `session: <server>:<name>` on its queue item, the one record `reap` and `fleet-sessions` read (a bare name means `lab`). There is no separate session ledger. Never `wt new` + `claude` by hand, and never `tmux set-option @dispatch` on a session afterwards: on 2026-10-28 the human had to ask twice why sessions an agent started carried no label.

- For a queue item: `fleet-dispatch start --item <slug> [--model <m>]`. It cuts a fresh worktree with `wt new --detach` and moves the item to `running/`.

- On another harness: add `--harness claude-lazer|opencode` and a `--model` from `~/.config/agentctl/harnesses.json` (or set `agent:` and `model:` on the item). These go through the gateway on the eval key, log under model-lane lane `eval`, and only a hand or a batch starts them; a pass skips them. QUEUE.md "Harnesses" has the rest.
- Spill to Lazer: when no account has room, a run pass starts a claude item on `lazer-reserve` (claude-lazer on the claude-reserve key, Sonnet) instead of leaving it waiting, if its tier is within the unattended ceiling, `model-lane classify` puts it on Sonnet or Haiku (a refusal is cached for the day), fewer than `DISPATCH_SPILL_MAX_LIVE` (2) spill sessions are live, the pool is under `DISPATCH_SPILL_POOL_PCT` (80) of its budget by `lazer-spend`, and the key has budget left. A shut spill is named in the BLOCKED reason; `DISPATCH_SPILL_MAX_LIVE=0` turns it off. `claude-acct` refuses to park or move a Lazer pane, so the shepherd's budget park logs "could not park" and the key's own budget bounds it.
- Every start of a Claude item with no `--model` (a run pass, a hand start, a plan phase, an `after:` chain) picks the model with `model-lane classify --floor $DISPATCH_LANE_FLOOR` (sonnet: a dispatched session lands its own PR), logs the run and stamps `lane_run=<id>` on the item; the item's close reports its outcome (`agent-queue move`). A model-lane failure starts the item on opus, unlogged. An explicit `--model` wins and logs nothing.
- For a row: `fleet-dispatch start --project <p> [--agent] --row <id> --brief <file> [--model <m>]`. Write the brief to a file first: `/one-shot <task>`, then where the row is and how to record it done. `start` claims the row, promotes it to a queue item (slug and `from: board:<project>:<id>` from the row's id, priority from the row, high on a bare row; a row with no id is refused when its project has no `code`) and starts that item. Do not `start` the row yourself first: `start` refuses a row that is not open.
- To queue a row without starting it: `fleet-dispatch promote --project <p> [--profile <x>] [--agent] --raw "<line>"`, what the Board tab's Start runs. It takes the row's exact line, refuses one that changed or is already started, and the item starts like any board item: away, or within the present trickle.
- One conversation: `fleet-dispatch start --project <p> --server <server> --session <name> --cwd <dir> --resume <claude session id> [--item <slug>]`. With `--item` (a running or waiting item) the item records the new session, `origin: resume`; without one the session is only tagged. The sheet is left alone, `--row` is refused, and a session name that already exists on that server is refused unless `--window <name>` says to open it as a window of that session. It reopens in the permission mode its transcript last shows.
- A lost server or a reboot: `fleet-dispatch restore [--server <s>] [--dry-run]`, below.
- A new claude start drops the tools in `DISPATCH_DROP_TOOLS` (`Workflow,ScheduleWakeup`) with `--disallowedTools`, because a queue session almost never calls them and their schemas are paid on every turn. A task that names one of them, ultracode or `/loop` keeps them; an empty value keeps every tool. A resume keeps what it ran with.

Only the sessions the dispatch pass started count against `DISPATCH_MAX_LIVE` and its area rule; hand launches and restores carry the label and their item but hold none of its slots. `start` does not check the `dispatch` hold, which pauses only the runner. Before starting anything, read `agent-hold list` and `fleet-pace`'s pace check as for any other new work.

A dispatched session is an ordinary session from then on: the `shepherd` buckets, nudges and escalations apply to it unchanged, and its `/one-shot` records done on its row with proof. If it needs the human, it asks in its own conversation, files the same question with `agent-ask post`, and stops; the human answers in the session or from a board, and either way the answer lands in the session and closes the ask. Every pass that starts or reaps something appends a line to `~/.agent/dispatch/log.md`. `fleet-dispatch stats` counts it for the feed (HA sensor "Dispatch queue", Prometheus): runnable items and the oldest one's age, the queue's started, done and failed by the hour (from `agent-queue stats`), reap moves, and the items reaped `DISPATCH_FLAP_MOVES` or more times in an hour. Read those numbers, not the log, to answer "is dispatch moving".

## A world server died: `fleet-dispatch restore`

`fleet-dispatch record` runs every minute from `fleet-state.service` and keeps `~/.agent/dispatch/panes/<server>.json` for each world in `.config/tmux-servers/`: every pane's session, window name, cwd and Claude session id. When the server it described is gone or restarted, it pages (`tmux <server> server died`) and renames the record to `<server>.lost.json`. A clean reboot pages the same way.

`fleet-dispatch restore` runs `tmx ensure`, then reopens each conversation through `start --resume --window`, as a window of the session it was in and in the permission mode its transcript last shows. It skips a conversation that is running, or that wound down on purpose (a `.request` or `.fired` in `~/.agent/spin-down/`), and lists plain shells and vanished folders without reopening them. A queue item needs no re-attaching: the same `<server>:<session>` comes back. All reopened renames the record to `<server>.restored.json`; a failure keeps it, so a rerun finishes the rest. `--dry-run` shows the list first.

## Starved queue: a fleet-lead pass may start the head item

`fleet-dispatch starved` exits 1 when a dispatch hold has stood over `DISPATCH_STARVED_MIN` minutes (the runner's `held_since`, set by the first BLOCKED pass and kept across a run-floor or spill start; it leads with the Stopped line `fleet-dispatch stopped` prints, the one line hub Home and the briefing show), when an urgent or high queue item has been runnable over `DISPATCH_STARVED_MIN` minutes and no run pass started anything, or when runnable sits under `DISPATCH_LOW_WATER` with board rows a pass would pick and no run start in twice that time (the Sentinel watch `queue-starved` runs it, and its trip reaches the pass as a `watch:` due line). On 2026-11-04 four gates in turn held every pass for 7.5h while the shepherd watched and could not act. A `fleet-lead` pass that sees it:

1. `fleet-dispatch run --dry-run` and `agent-hold list` in one call, to read what stops a real pass.
2. If the block is load (the pace check says HOLD), account room (`claude-acct room`), or an `agent-hold` anyone set, leave it: those are the gates working. Answer the line with `fleet-shepherd skip` naming the gate; the watch has already paged the human.
3. Otherwise start the oldest item `starved` named, one per pass: `fleet-dispatch start --item <slug>`. Log it (`fleet-shepherd log "healed starved: <slug>, gate was <what dry-run said>"`) and file the gate that held it as an agent-board row, because a start by hand fixes the item, not the pass.

## Do NOT

The fleet-wide list is in `fleet-lead`; this is this role's own.

- Widen dispatch beyond the profiles in `DISPATCH_PROFILES`, add a night project, relax the policy, raise a worker's `max_tier`, add a worker, or put `#worker/*` on a row, without the human asking. An agent filing a row may add its own `#tier/N` reading; assignment is the human's.
