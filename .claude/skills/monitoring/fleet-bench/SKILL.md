# fleet-bench

On 2026-10-27 the shepherd told the human when each session would finish ("about 9:00 PM", "tomorrow around midday") by assuming one phase per hour. Nothing kept those numbers and nothing checked them. The first one scored, an hour later, took up to 2.6x as long as predicted. This skill is the record and the check. It is a component of its own, like `fleet-dispatch`: the shepherd only reads it.

Every number here is counted from samples. None is a model's grade, because model-graded evals on this fleet read 10/10 almost every time and rank nothing.

## Scope and triggers

Benchmark the agent fleet from counted facts: where every live session is in its plan, when it should finish, and afterwards how far off that prediction was. Verbs: findings | respond | loop | throughput | flow | forecast | vs | queue | requests | sources | report | effect | eta | headline | scorecard | sessions | stats | sample | review | asks | ledger | kpi | improve | retro | room | triage | health. Use when the user asks "how accurate are the ETAs", "when will agent-N be done", "when will the fleet be done", "what order will the work land in", "how did today go against the forecast", "is work coming in faster than it gets done", "benchmark the sessions", "how fast is the fleet moving", "show me the scorecard", "how often does CI go red before merge", "how long do queue items wait", "how many queue items reached a PR this week", "review a sample of merged PRs", "which asks are blocking", "what is waiting on me", "did anything act on that alert", "which KPI should we work on next", "did that fix move the number", or when the shepherd writes a "where are we" summary and needs an ETA per session. Model-free: `review` reads no diff with a model since 2026-11-02. Not for load or holds (fleet-pace) and not for what one session did after it ended (session-outcomes).

## Where to look

- `~/.notes/lab/projects/current/agent-runtime/docs/bench/latest.md`: the daily scorecard, one row per session over the last 24h (phase now, phases ticked, hours working, hours waiting on you, hours stalled, nudges, peak context, then PRs merged, CI reds, reverts and cost). One dated file per day sits beside it. It syncs with notes, so it reads on the phone.
- The morning briefing (`agentctl-briefing`, 06:45) writes the scorecard, puts the headline and its path in `agents.md` (the agent briefing; `briefing.md` is the human overview), and carries the pending-asks line in its one page.
- `~/.notes/lab/projects/current/agent-runtime/docs/bench/asks.md`: every pending ask in hub Home's order, the ones blocking a live session first, rewritten by the 06:45 briefing. New asks page from `hub needs --page` (title `Needs you`), not from here.
- `fleet-bench report`: every live session (phase done/total, bucket, ETA, what the ETA is based on), then how accurate past ETAs were, then the last agentctl outcome of `fleet-bench`, `fleet-review` and `briefing`.
- `fleet-bench eta`: one line per live session, or `--json` for scripts. The shepherd's "where are we" summary takes its ETAs from here.
- `fleet-bench requests [--json] [--since T]`: the human's urgent requests from the queue, a plan chain as one row, then what finished since T (default: the last rundown). The one home of that grouping: a view reads `--json`, never its own copy. Fields and order: `REQUESTS_JQ` in the script.
- `fleet-bench forecast`: when the whole fleet should be done, the drain, and the next phases in order. The scorecard's "Forecast" section carries it, plus `vs` against the newest baseline at least an hour old (at 06:45 that is yesterday's `daily-<date>`). The briefing freezes `daily-<date>` before it writes the scorecard.
- `fleet-bench epics`: each project's features from idea to verified, per epic its step, done/total and ETA, on track or behind its frozen ETA, and once landed its score. The scorecard's "Epic ETAs" section carries the scores per project and the open epics behind.
- The scorecard's "Release windows" section: per project the open window (committed, delivered, open, dropped, interrupted against its `sprints/<v>.md` `## Committed` snapshot) and the last cut's line (`stages.md`, "Release windows"), read from `notes projects --stats --json`.
- Prefix + Ctrl-g (`fleet.sh`) has a `bench` section under the asks: the headline, then one ETA row per live session. Its runners section lists `fleet-bench` and `briefing` with every other agentctl unit, red when the last outcome is STALLED or the run failed.
- `agentctl status fleet-bench` and `agentctl logs fleet-bench -f` for one run's detail.

## Verbs

- `sample`: one pass. It reads `fleet-sessions --json`, appends one line per live session to `progress.jsonl`, writes an estimate for any session whose phase count has no estimate yet, and scores every estimate whose session has since finished. Each pass also writes `fleet_projects.prom` from `hub projects --json` (`BENCH_HUB_PROJECTS_CMD`): `agent_project_state` and the open window's `agent_project_window_rows` and `agent_project_window_days_left` (stages.md, Release windows). The agentctl runner `fleet-bench` runs it every 10 minutes: `fleet-sessions` has no event to wait on, so this is a steady poll, and one run costs about 14 s, mostly `gh`.
- `eta [--json]`: the newest estimate per live session from the newest sample, calibrated when its basis has enough scores (see "How the numbers are made"). A finished session has none. Once the newest sample is past the ETA, the row reads `late 2.4h` instead of a time, and the estimate itself stays as it was. `--json` gives `eta`/`eta_epoch` (the ETA shown, calibrated when it was), `raw_eta_epoch`, `factor`, `late_min` (minutes past it, null when not late) and `basis`.
- `report`: as above. Read-only.
- `accuracy --json`: one object per basis kind from `scores.jsonl`: `basis`, `n` (scored), `n_ratio` (scored with a ratio), `median_ratio`, `median_error_min`, `median_abs_error_min`, and `factor`, the calibration a new estimate of that kind gets now (null below the minimum). The same function makes the factor and the report's per-basis lines, so all three always agree. The watch board's ETA trust line reads it.
- `headline`: the last `BENCH_WINDOW_H` (24) hours in one line: sessions, phases ticked, hours waiting on you, hours stalled, ETAs scored and their median raw ratio, and the calibrated ones' median ratio when any were scored.
- `scorecard`: writes `<date>.md` and `latest.md` in `BENCH_SCORECARD_DIR` and prints the path. Sections: Vitals; KPIs; Bottlenecks (hours lost per queue, on runs not passed, waiting on you and stalled, biggest first, then the branches behind the failed runs); Where the time went (per project and plan, with 24h spend and merges); Agent depth (test runs, CI polls, tool errors and tokens past the last edit, from session-outcomes' `activity`); Session time (hours per project over `BENCH_TIME_DAYS` by what was running: work, gate, test, other jobs, you, parked, from session-outcomes' `time_use`); Queue (the `queue` line, what is active now, done per day, and outcomes by project and by source); Models (the `models` table); Trainee (per trainee pair: runs, approved, rejected, landed from lane `trainee` in model-lane's log, with landed split by the item's `review_fix` (none or small, set by the batch review before it lands the diff), then `fleet-dispatch trainee-pool`: the pool size, its commonest refusal, and the floor open or shut with the gate's reason; seam `BENCH_TRAINEE_CMD`); Sources (the `sources` table); Canary lanes (`canary list --by harness,model`); Task matrix (`canary matrix`, Codex); Sizes and kinds (the `sizes` tables); ETA accuracy; Consolidation ledger. A source that cannot be read shows `?` or says so; it is never left out.
- `sections [--days N] [--json]`: what each section of a repo costs to land, over the last `BENCH_SECTIONS_DAYS` (7) days, the most gate hours first: PRs, first-try share, gate reds and minutes per PR, gate hours, greens lost (a green head a later commit replaced, for any reason), and the claiming session's cost, tokens and work minutes per PR, a session's total split evenly over its merged PRs. The session comes from outcomes at read time, so a PR claimed after it was counted still joins. It covers every merged PR, where the KPIs and the scorecard's CI lines cover only those a session claims. A PR counts in every section it touches, so sections sum past the All PRs row. The scorecard prints the top `BENCH_SECTIONS_TOP` (15).
- `stats --json [--since E]`: one object per session sampled, or merging a PR in `pr-ci.jsonl`, since epoch E (default: all of it), over its whole life rather than the 24h window: `minutes` per bucket (the same gap rule as the scorecard hours), `nudges`, `escalations` (each time the flag turns on), `ticked`, `peak_context`, `first_epoch` and `last_epoch`, and `merged` {prs, lines_added, lines_deleted, ci_runs, ci_reds}, null when it merged nothing. `sampled: false` marks a session only `pr-ci.jsonl` knows. `agentctl-session-outcomes` stores each row as its row's `delivery`, so `card` and `worst` read it there.
- `review [--days N]`: the window is the last 24h (`BENCH_WINDOW_H`), or back to the cursor `review.last` when that is older, never more than `BENCH_REVIEW_MAX_DAYS` (7), so a failed or missed night is counted by the next pass. A pass sets the cursor to its start time, held back to the oldest PR it left for later or could not count; a `--days` window moves it only when it reached the usual start. For every PR that session-outcomes lists as merged in the window and `pr-ci.jsonl` has not counted, one `gh pr view` (a Forgejo PR, repo `host/owner/repo`: one read of that host's API, `so_forgejo_pr`) gives its size and the run ledger (`schedules-sync runs --branch --until <merge>`) its CI runs from its first commit to merge; a PR in a repo the ledger does not sync (`schedules-sync repos`) is left out with a count, a Forgejo PR whose `pulls/N` is a 404 while its repo's pull list reads (the forge lost it) is named and left out without holding the cursor (a review with nothing else is NOOP), and one merged after the ledger's last sync waits for the next review. A repo with a `sections` block on its tracker in `project-map.json` (`repo`, `gate`: the file path of the gate workflow, `.github/workflows/test.yml`, since a run is titled by its run-name; `roots`) also counts every PR the PR store (`schedules-sync prs`) has merged there in the window, claimed or not, and adds each PR's `sections` (a path inside no root is `other`), `gate_runs`, `gate_red`, `gate_min` and `green_lost` (a green gate on an earlier head that had to run again). `--days N` sets the window to N days and recounts rows from before those fields. No model reads the diff: the model review was dropped on 2026-11-02 after 310 of 312 runs failed on the gateway key's budget. The agentctl runner `fleet-review` runs it at 02:45, after session-outcomes (02:30) and before the 06:45 scorecard.

- `asks [--write]`: every pending ask, read from `hub needs --json` (`BENCH_NEEDS_CMD`), in the order hub Home ranks them, with what each holds. It prints the digest; `--write` also writes `asks.md` in `BENCH_SCORECARD_DIR` and prints the one-line summary (counts and the top one) with no page and no verdict, for the morning briefing to carry.

- `ledger [--json|--check|--unlisted]`: the consolidation ledger. It counts runner confs (`runners`, `runners_on` without `ENABLED=no`), timers (a switched-on oneshot conf with a `SCHEDULE`, where `agentctl reload` writes one), files with a direct headless `claude -p|--print` outside agentctl-run (`launches_direct`, gitignored build output skipped), distinct `last-outcome` verdicts, pending asks and those older than `ASK_STALE_DAYS` (14), and open agent-board rows. `--check` prints `runners` or `timers` when over `~/.config/agentctl/ledger-baseline`, each launch file with no row in the `~/.config/agentctl/PIPELINES.md` "Model calls outside agentctl-run" table and each row whose file no longer launches (`--unlisted` prints just those), and exits 1 (2 with no baseline or no table); it reads only the confs, the table and the source tree, so the private repo's CI runs it through the public `.github/workflows/ledger.yml`. To add a runner or timer, retire one or add a dated delta line to the baseline in the same PR (its header has the format; the file is merge=union, so two PRs never conflict on it); a launch needs its table row instead. The scorecard carries the counts and the check under "Consolidation ledger". `--launches DIR...` prints the scan's matches; `runner_contract.bats` uses it.

- `kpi --vitals [--json]`: the front page, the `BENCH_VITALS` rows in order, each with the question it answers (you, outcome, quality, cost). Same values as `kpi`; the scorecard opens with this table and `agent_bench_vital{question,kpi}` publishes the list, its value the row order, so a view reads the list and takes each value from `agent_bench_kpi`. A key `kpi` does not carry stays as a row of dashes.
- `kpi [--json] [--at T | --trend DAYS | --check [ERE]]`: the KPI table over the last 7 and 28 days (`| KPI | 7d | 28d | threshold | status |`), or one JSON object keyed by KPI; the scorecard carries it under "KPIs", right after the headline. `--at T` evaluates both windows as of a past time (the comms and counted-now KPIs read null, since nothing records them as of then). `--trend N` prints one row a day of the 7d windowed KPIs, oldest first. `--check ERE` prints each KPI whose name matches ERE that is past its threshold and exits 1 when any is (2 when ERE matches none): the runner-score watch's probe. The outcome rows are the history, so neither keeps a store of its own.
- `chain [--json|--check] [--kpi <key>]`: the work-chain rows of the KPI table (the `KPI_CHAIN` keys below), counted now; `--check` prints `<kpi> <value> (<bound> <threshold>)` for each one past its threshold and exits 1. `--kpi <key>` narrows it to one `KPI_CHAIN` key (any other exits 2) and reuses a count up to `CHAIN_SNAPSHOT_MAX_S` old from `chain.<FIX_SINCE>.counts` in the bench dir, since one count takes about 3 min. `chain --check --kpi <key>` is the probe of that key's own `chain-<key>` Sentinel watch, one per bounded key, so a new trip shows while other chain KPIs stay red (ar-3966). A source that cannot be read leaves its KPI `-`, never past: with none past, `--check` names each bounded KPI whose count read `<key>=?` or printed no line for it (a share over an empty window counts `-`, read) on an `unreadable:` line, or says the count failed, and exits 2 (a failed count without `--check` is an error, exit 1), which Sentinel reads as UNKNOWN (ar-5413).
- `prio-defaults [--json]`: the open rows that rank by default (no priority tag or no `#why/<reason>`) by the filer that wrote each, most first, with `PRIO_SAMPLE` (3) sample ids: the rows behind `prio_default`. A fix for an origin lands at that filer.
- `inflow [--project P] [--days N] [--json]`: where a project's board comes from (default agent-runtime): every open agent-lane row attributed to its source, then per source the arrivals per day over N days (`INFLOW_DAYS`, 14), how they ended (closed by PR, done with no PR, dropped, dup, other) and the age of its open rows. A source is the ingest `origin` of the row's first added or filed event, else the `#from/` its triage carried in (`from: dream`, `from: ladder-scout`, `from: item or session`), else `self-check` (a hand session), else the writer; a row the record never saw is `pre-log`, below the first id the record minted. The record starts 2026-11-19, so a longer window reads from there (the header says so). A settled event ends a row as closed by PR only when it carries a PR. `other` is a row the record shows no close for (moved, rehomed or closed by hand). It reads every profile's rows of the project name. `--json` adds each source's per-day counts.
- `churn [--days N] [--json|--check]`: agent-runtime's churn per local day (N complete days, default 7, plus today so far): dotfiles merges, rows filed, closed, dropped, reopened, and follow-ups a session filed itself; these are the counts behind the `churn_*` KPI rows. `--check` prints nothing while it holds; when filed exceeded closed on each of the last `CHURN_RUN_DAYS` (3) complete days it prints those days and exits 1, and 2 when the ingest record cannot be read, so an unreadable source never trips it; it is the probe of the `runtime-churn` Sentinel watch. Only the last `CHURN_RUN_DAYS` complete days are checked, so `--days` below that is raised to it under `--check` alone. It reads only the ingest record (`BENCH_INGEST`) and the merge log (`BENCH_CHURN_MERGES_CMD`, `git log origin/main` of `~/.dotfiles`: the remote-tracking ref, so merges the checkout has not fetched are missing).
- `bottleneck [--json | --check [stalled|pools]]`: the scorecard's Bottlenecks table on its own, or its rows as JSON. `--check` with no name runs both checks (one line each, the worse exit code). `--check pools` (the `pool-wait` watch, `alert` route: capacity is the human's call): exit 1 when any pool's job-hours with jobs waiting (`cc:pool_waiting` over the window) pass `pool_wait_hours_max`, naming each pool; 2 when the bound is unset or Prometheus gave no pool series. `--check stalled` (the `fleet-bottleneck` watch, `agent` route): exit 1 when the Sessions stalled hours over the window pass `stalled_session_hours_max`, naming the top three sessions; 2 when the sampler's newest sample is over two cadences old or the bound is unset. A session the human holds open is HELD and never counted. The table and the check read one function, `bottleneck_data`; every stalled minute, the Prometheus gauges included, comes from `window_stats`.
- `pipeline [--json]`: where every item sits, inbox -> backlog (the open and started rows `board_open` counts that no live item holds) -> queued -> running -> waiting -> done (finished in 24h). WIP and age (p50, p90, oldest) come from the state files; in and out over 1h and 24h and the dwell of what left come from `notes log --steps --json` (`BENCH_STEPS_CMD`), which owns the record's schema. The bottleneck is the step whose age p90 is furthest past its `step_age_p90_<step>_max`, none while all are inside; steps taking in more than they let out over 24h are listed as growing. Each step also carries `measure` over `measure_bound` as `score`, a `verdict` (`ok`, `near` at 0.8, `over` at 1, `-` with no bound, never `ok`) and a `why` tally of up to three reasons: the measure is the age p90 for most steps; for `admission` (between backlog and queued) the items the queue cap held in 24h (`agent-queue admission --json`, its `day`) against `admission_held_24h_max`; for `dispatch` (between queued and running) the minutes the runner's hold has stood against `DISPATCH_STARVED_MIN` (`headroom.json`, read only under 45 minutes old), with its `held` reason whole, `clears` and `floor_starts`, and "stopped" only when no floor started under the hold. `doors 24h` counts the rows each writer filed over 24h in the ingest record (`BENCH_INGEST`), by human, a runner by its conf name, or session, with inbox lines after a +; `out 24h` counts what left: merged, done, dup, moved (a drop that kept the row at another home: improvements.md, a sheet, another board) and dropped. Inbox ages count from each line's first intake event in `ingest.jsonl`. The `headline` names the worst step, stopped first, then the furthest over: `<step>, <measure> (<pct>% of <bound>): <reason>. <clears>.` The same numbers are the `agent_chain_*` gauges in `fleet_bench.prom` (Grafana's Pipeline row). `pipeline --check chain-lag` trips when an urgent or high chain's handoff p90 over 24h (`agent-queue stats` `chain.h24`: an `after:` item from its predecessor's finish to its start; an item with an ask, pr, nightly, rbw or hold gate is left out, because its ready time is not recorded) passes `chain_handoff_p90_max` (60); a successor still waiting counts only once it starts, `chain-after-stuck` owns the stuck one.
- `effect <T | owner/repo#N> [--days N] [--json]`: each windowed KPI over the N days (default 14) up to a change against the N days after it, where a PR is read as its merge time. The verdict per KPI is improved or regressed when it moved more than `BENCH_EFFECT_FLAT` (10%) in the direction that is better for it, flat inside that, and pending until the after window has ended. Many changes land in any window, so a verdict is a lead to look at, never proof that one change did it.

- `retro`: reads each live improvement claim (below) and keeps the lesson guard rows. A claim whose row closed with a PR (`done` with `pr:` in its why), or whose queue item moved to done with one, `BENCH_EFFECT_DAYS` (14) or more ago gets a verdict: the KPI's 7d value now against the claim's baseline, by the `effect` rule and the direction the claim's bound gives (`max` lower is better, `min` higher). The bar in `kpi-thresholds` plays no part, so an edit to it cannot turn a flat result into a pass. A row dropped, a dup, cancelled or closed with no PR is `unproven`; one still open, or merged under 14 days ago, stays live. `regressed` adds one `fix(kpi): revert <pr>, <k> went from <a> to <b> #kpi/<k> #high #size/s` row and claims it from the new value; `flat` and `unproven` end the claim, so `improve` names the KPI again with `last` naming that row. It adds no row for a KPI past its threshold: `improve` names those one at a time. It keeps one `guard <hash>:` row for each lesson whose `<!-- sig:YYYY-MM-DD <regex> -->` matched Bash commands in `BENCH_GUARD_RECUR` (default 2) or more sessions after its date (session-outcomes `lesson_hits`), or whose `<!-- seen:N DATE -->` marker (dream writes it on each corroboration) reached `BENCH_GUARD_SEEN` (default 3, keyed by the lesson's title, `so_lesson_seen`), `#high` at twice that, added or refreshed in place with `ptask edit`; the row asks for a hook, test or lint and for the lesson to be deleted once it lands. WORKED when it wrote a verdict or a row, NOOP otherwise, FAILED when the ledger, `notes log` or the KPIs are unreadable. The briefing runs it on Mondays. It queues no canary: fleet-dispatch tops its canary keep up (`canary queue --max N`, `DISPATCH_CANARY_KEEP`).
- `canary list [--by harness,model[,pts]] [--json] | verify [id...] | queue [--harness h [--model m [--effort e]] [--task id[,id]] [--pts n[,n]] | --max N [--off-claude p[,p]]] | start <id> | score <id> | matrix [--harness h] [--days N] [--json]`: a fixed eval set of past PRs, re-run weekly so a config change shows up in the KPI series. One task per file in `BENCH_CANARY_DIR` (`~/.config/fleet-bench/canary/*.json`): `id`, `project`, `pr`, `base` (the merge's first parent), `merge`, `task` (the PR title), `pts` (the whole job's size on the board's `#pts/` scale, scored by the rubric in `~/.config/inbox-size/prompt.md`), `accept` (the test names it added) and `oracle` (`paths`, the PR's test files, and `cmd`, the argv that runs them), and optionally `stack` (else its project's in `matrix.json`). A task with no merged PR (a known-answer fix at a pinned `base`, the 1-point tier: four plain-ASCII doc fixes) has no `merge` and `paths: []`; its `oracle.script` is a bare file name in `BENCH_CANARY_ORACLES` (`~/.config/fleet-bench/canary-oracles`, beside the tasks) that `canary_oracle` pipes into `cmd`'s stdin (`bash -s -- <args>`), so the session cannot see or edit it, and its `oracle.answer` (`script`, `cmd`) writes the known answer for `verify`. `ascii-fix.sh` is the answer key of the doc fixes: only the named file changed since `base` (a character device srt masks in the jail is no file), no non-ASCII byte, `git diff --numstat` is `N N`, and each changed line keeps its `[A-Za-z0-9_]+` words (the key names Ctrl, Cmd, Opt, Shift, Alt are dropped from both sides, so a key glyph spelled `Ctrl+Cmd+M` passes). The other two 1-point tasks are one-line shell fixes from merged PRs whose bats the oracle runs. `verify` proves each oracle in a throwaway worktree under `~/.cache/fleet-bench/`: it must fail at `base` and pass at `merge` (a task with no `merge`: with its answer written in); exit 1 names a BAD task. `queue` adds one item per task, and `queue --max N` tops up at most N across the weekly claude lane and each lane in `BENCH_CANARY_LANES` (`~/.config/fleet-bench/canary-lanes`, `harness model [effort]` a line) whose source, the harness's harnesses.json `source`, `claude-acct room --source` says has room (a lane with no room or no source is said and skipped), one task a lane a round, after it cancels the queued items of an earlier week; `--off-claude <project,...>` (fleet-dispatch's, the projects whose share is full) leaves a claude lane, the weekly one included, out of those projects' tasks only; fleet-dispatch calls it as `AGENT_QUEUE_PULL=dispatch fleet-bench canary queue --max N` (agent-queue admits only dispatch's pull or a hand add). A bare `queue` queues the lane's whole week; `--task` names the tasks and `--pts` the sizes a lane queues (both need `--harness`; an unknown id exits 2), so a batch of one size or a few tasks is one call. Slug `canary-<id>-<YYYYwWW>`, `--from canary --tags canary` (no story row, and fleet-dispatch gives it its task as the whole brief, so no PR); an item already there is skipped. Every lane queues at `low`, since a canary is a check (ar-4349); another harness's lane starts as overflow on its own source. In the session, `start` detaches the repo at `base` (clean tree only), and `score` lays the PR's own tests over the tree from `merge` (`git checkout <merge> -- <paths>`, so the session cannot edit its scorer), runs `cmd` under `BENCH_CANARY_TIMEOUT` (900s), logs to `<state>/canary/<run>.log`, keeps the harness's own log of the run beside it as `<run>.harness.log` when `BENCH_CANARY_RUN_LOG` prints one (a sandboxed lane's tail sets it to `fleet-dispatch run-log`, the run's lines of the opencode log that rotates), and appends `{epoch, run, id, project, pr, session_id, harness, model, effort, pass, rc, config}` to `<state>/canary.jsonl`, where `config` is each `BENCH_CANARY_CONFIG_REPOS` repo's HEAD. The claude lane's run on opus of a 1-point known-answer task also carries `control: true`: it is the positive control, and the claude lane queues those tasks first. A week (the slug's ISO week) whose control failed reads `instrument`, and so does any run with rc 127 (a runner not found): such a row reads pass null in list, lanes, matrix and the `canary_` KPIs, which count it apart, so a broken oracle or sandbox never reads as a weak model. A run scores once (exit 3 after). A lane is a harness and model on the same tasks: `queue --harness codex --model sol` adds `canary-<id>-<week>-codex-sol` items with that `agent` and `model` (`--effort high` adds `-hi` and an `effort` the launcher passes on, codex as `-c model_reasoning_effort`), `score` reads all three off the item (the session id is the harness's own, else the newest one claimed on the item), `list --by harness,model` compares lanes (an effort is a lane of its own, `codex/sol@high`) on runs, pass rate and the outcome rows' minutes, turns, cost and tokens, and sets each non-claude lane beside the claude lane on the tasks both ran (`same_tasks`, `pass_rate_same`, `claude_pass_rate_same`); ### Findings

- **Demand is sessions, not runs.** Local runs fall by design once gates move to the pool, so runs/h would read that as demand gone.
- **Episode.** The time a rule first fired for a scope. It outlives a gap up to `finding_clear_min` (60), so one outage is one episode, and a recurrence after that is a new one. `fact` is `<rule> <scope> @<episode>`, the key a ledger pages once on. There are no close rows: a finding is open while its newest row is inside the clear window.
- **Thresholds** are starting points set from the 10-29 replay. Defaults are in the code; a `finding_*=` line in `KPI_THRESHOLDS` overrides one.
- **Replay.** `tests/fixtures/bench-replay-1029/` is that day, read through `BENCH_NOW`, `BENCH_PROM_TSV`, `BENCH_MERGES_TSV` and `BENCH_RUNS_TSV`. The rules fire at 09:30 (pool), 13:00 (local slots) and 14:20 (merges); the human found it at 19:59.

## How the numbers are made

State is in `~/.agent/bench/` (override with `FLEET_BENCH_DIR`).

| File | One line per | Fields that matter |
|---|---|---|
| `progress.jsonl` | session per sample | `epoch`, `session_id`, `target`, `project`, `bucket`, `phases_done`, `phases_total`, `finished`, `idle_min`, `context_tokens`, `nudged` |
| `estimates.jsonl` | session per phase count | `made_epoch`, `eta_epoch` (raw), `per_phase_min`, `basis`; when calibrated also `factor`, `factor_n`, `cal_eta_epoch` |
| `scores.jsonl` | estimate whose session finished | `error_min`, `ratio` (both against the raw ETA), `horizon_min`, `done_bound`; when calibrated also `factor`, `cal_error_min`, `cal_ratio` |
| `pr-ci.jsonl` | merged PR | `repo`, `number`, `session_id`, `merged_epoch`, `additions`, `deletions`, `ci_runs`, `ci_red` |
| `review.last` | review pass | one epoch: every merge before it is counted or left out for good |
| `forecasts.jsonl` | frozen forecast | `label`, `made_epoch`, `last_p50`/`last_slow` (and median, p90), `drain`, `queue`, `schedule[]` (per session: `phases[]` with `name`, `p50`, `slow`) |
| `forecast-scores.jsonl` | baseline once it resolved | `resolved_by`, `actual_last`, `bound`, `ratio_p50`, `ratio_slow`, `error_min`, `within_slow`, `in`, `in_per_h` against `in_per_h_frozen` |
| `epic-baselines.jsonl` | open epic first seen, and each scope change | `project`, `epic`, `made_epoch`, `reason` (first seen, scope), `total`, `total_weight`, `p50`, `slow`, `cal_p50`, `basis` |
| `<outcomes>/<project>/epics/scores.jsonl` | epic baseline once its rows landed | `made_epoch`, `landed_epoch`, `pred_p50`, `pred_slow`, `ratio`, `error_min`, `within_slow`, `verdict` (ahead, behind), `baselines`, `prs` |
| `findings.jsonl` | firing finding per sample | `epoch`, `rule`, `scope`, `episode`, `decision_class`, `evidence`, `conclusion`, `cost`, `fact` |
| `responses.jsonl` | act on a finding (`respond`) | `epoch`, `fact`, `actor`, `action` (paged, asked, filed-row, cancelled, fixed), `ref` |

- **Phase time.** Each plan file is its own timeline, so a session that starts a new plan does not count the switch as a phase. A phase is measured only when the samples saw both its start and its end, so a session's first phase on the record is never measured (it may have started hours earlier). When one sample sees two phases tick at once, the gap is split evenly between them. The time includes waiting on the human.
- **ETA** = now + phases left x per-phase minutes. Per-phase is the median measured phase time of that session (`basis: session-median(n)`), else of every session in its project (`project-median(n)`), else `BENCH_DEFAULT_PHASE_MIN`, 60 (`default`). A session or project needs `BENCH_BASIS_MIN_N` (3) measured phases before its median is used: on 2026-11-02 one measured phase predicted 3.5 days for a session that took 20 minutes. A new estimate is written only when the phase count changes, so one estimate stands for each step of a plan and is scored as it was made.
- **Calibration.** The raw ETA runs long or short by a measured amount per basis (on 2026-10-28 project-median ETAs took 0.3x as long as predicted), so each new estimate also gets a factor: the median raw `ratio` over every score of the same basis kind (`session-median`, `project-median`, `default`, `shepherd-guess`), counting only scores that have a ratio. It applies only once that kind has `BENCH_CAL_MIN_N` (5) of them, clamped to `BENCH_CAL_MIN` (0.25) and `BENCH_CAL_MAX` (4), and rounded to 0.01. Then `cal_eta_epoch` = made + (raw ETA - made) x factor, and every view (`eta`, `eta --json`, `report`, the bench section of Prefix + Ctrl-g, the shepherd's summary) shows it, with the basis reading for example `project-median(13) x0.3 (n=23)`. Below the minimum the raw ETA is shown and the basis has no factor. The factor is fixed when the estimate is made, so a published ETA does not move as later scores land; an estimate made before calibration existed shows raw until its session's next phase tick. The raw ETA stays in `eta_epoch` and is what `ratio` is scored against, so the factor is always made from raw ratios: scoring the calibrated ETA instead would pull the ratio to 1 and the factor would undo itself.
- **Finish** is the first sample that reads `finished` (fleet-sessions' DONE work conditions). If that was the session's first sample at all, the real finish was earlier, and the score says `done_bound: upper`.
- **Score.** `error_min` = finish - ETA (positive means it ran long). `ratio` = actual duration / predicted duration (2 means it took twice as long). `horizon_min` = how far ahead the ETA looked. A calibrated estimate is also scored against its calibrated ETA (`cal_error_min`, `cal_ratio`), so the report shows whether calibration helps. The report gives medians by basis, by basis calibrated, and by horizon (under 2h, 2-8h, over 8h).
- **Scorecard hours.** Each sample owns the time until the next sample of that session, in that sample's bucket: WORKING is working, NEEDS is waiting on you, STALLED is stalled, except a row the human holds open (label `manual` or `stay`, `.local/lib/kept.jq`), whose STALLED time is HELD and in no hours column. A gap longer than `BENCH_GAP_CAP_MIN` (20, two cadences) counts as 20 minutes, because a longer gap means the sampler itself was down. Nudges count each time the shepherd's `nudged` flag turns on. PRs merged, reverts and cost are the newest session-outcomes line for that `session_id`, `-` when it has not been observed yet.
- **CI reds.** Runs on the PR's branch from its first commit (or its opening, if earlier) to its merge. Red is `failure`, `timed_out` or `startup_failure`; `cancelled` is a superseded run and does not count. Earlier runs on the same branch name belong to an older PR and are left out. The scorecard sums them per session; the headline sums them over the window.
- **Ask rank.** Asks keep hub Home's order (`hub_core::home::needs`): the ones only the human can answer first, each by (1 + a live session + plan phases left + queued items after it) x minutes waited, then the ones the judge said a machine could answer. fleet-bench never re-ranks them. Asks with no live session behind them (headless asks, asks whose session ended) are listed in their own section.
- **Forecast.** Each open phase of a session takes per-phase minutes x the factor of its newest estimate (the p50 end), and the same minutes x the median raw ratio of ETAs scored in the last window (the slow end, 1 when none were). The first open phase ends at the estimate's made time plus one phase, or now if that is already past, and each later phase follows one phase after it. Names come from the plan's `## Phases` checklist, through the same parser `fleet-sessions` uses, and `phase N` stands in when there is no checklist. The band is wide on purpose: on 2026-11-03 the factor was 1.16 while the last 24h ran 1.93x, and the band shows that gap instead of averaging it away. The drain is open phases / (out per hour - net in per hour) over the last window. When inflow is at or above burn, no time is given.
- **Queue items.** Each item is one phase (an item from `agent-queue add --plan` counts its `phases:`, another item naming a `plan:` that plan's open phases, a plan item with no plan the median phases per plan) at its project's median measured phase time (the project through `project-map.json` `trackers.<p>.repo`, so `dodginballs` reads `unity-core-playground`), else the fleet median, else `BENCH_DEFAULT_PHASE_MIN`, calibrated by that basis kind's factor; the slow end uses the last window's ratio. Items run on the dispatcher's slots: `BENCH_QUEUE_SLOTS`, else the pace target the last dispatch pass published (`room_max_live` of `BENCH_DISPATCH_STATS_CMD`, `fleet-dispatch stats`: what the Claude accounts carry, at most the conf's `DISPATCH_TARGET_PRESENT` or `_AWAY`, or `DISPATCH_RUN_FLOOR` when that is higher), else 1 slot, said out loud: also when the target is 0 or the last pass is over 45 min old. A running item holds a slot until it ends; one whose session is already on the schedule ends at that session's finish and is not counted again. Each time a slot frees it goes to the first queued item in queue order whose `after:` parent has ended, else to the one ready soonest. Waiting, night- or time-held items, items after one that did not finish ok, and items behind those are listed as not scheduled with the reason, never given a time. Load gates and away-only board items are not modelled, so the item line is the best case. The item line has its own finish and does not move the all-done-by that baselines are scored on.
- **Forecast score.** A baseline resolves when every session in it has finished (it said so, or it ticked as many phases as it had open) or is gone (absent from a sample, ended at the first sample without it). Past `BENCH_FORECAST_HORIZON_H` (48) a baseline also resolves, as a lower bound with `open` counted. `ratio_p50` = (actual last finish - made) / (predicted last p50 - made). `sample` scores each baseline once. `report` prints them under "Fleet forecast accuracy". Back-test, 2026-11-03: the 2026-11-02 06:45 baseline held 5 sessions with 14 phases and was due by 13:02. After 24h, 4 of them were still open (ratio 3.8x or more), and 67 more sessions had started. Inflow was 12.75/h against 3.58/h when it was frozen.
- **Epic ETA.** An open epic's ETA is when its last open leaf row should land. A leaf whose queue item (`row: <project>:<id>`) is on the forecast ends where that item ends (live or placed on the dispatch slots, `forecast` items `ends`). The rest is the tail: the open leaves with no scheduled item or the open plan phases no active item carries, whichever is more (a backfilled plan's phases are its epic's stories, so the two are the same work, never summed). The tail starts when the agent queue drains and runs one unit after another at the repo's calibrated phase pace (`project-median`, else `fleet-median`, else `default`). Basis is `queue`, `pace(...)` or `queue+pace(...)`; the slow end is never before p50. An epic with nothing filed and no plan has no ETA ("no rows or plan phases filed"). `cal_p50` applies the median ratio of scored epic ETAs of the same basis kind, once there are `BENCH_CAL_MIN_N`. Each `sample` freezes a baseline for an open epic with an ETA the first time it sees it (an epic is filed only on a human yes, so first seen is approval) and again when its total count or weight changes (scope). An epic is behind when now is past its frozen p50 or its ETA now is past the frozen slow end. When every leaf has landed (open 0, done above 0) or the epic closed, `sample` scores the newest baseline once: `ratio` = (landed - made) / (frozen p50 - made), raw, landing as exact as the sample cadence. Scores go one level under outcomes so no session-outcomes reader picks them up.
- `project` is the tmux target with the server, the window and any `-agent-N` removed, so every `unity-core-playground-agent-*` session shares one project median.

A hand-made estimate can be added as a line in `estimates.jsonl` with `basis: "shepherd-guess"` and the same fields. It is scored like any other. The first five, from the 2026-10-27 evening summary, are there.

## Outcomes

Each runner publishes under its own name (`$AGENTCTL_NAME`) through `agent-proof.sh`'s `proof_report`.

- `sample`: WORKED when it wrote lines, NOOP when no session is live, STALLED with exit 1 when `fleet-sessions` failed. On STALLED nothing is written: the history gets a gap, and every number around it stays correct. Its epics step (freeze and score) runs after the session rows, with or without a live session; when it fails it says so on stderr and the outcome stands.
- `review`: WORKED when it counted a PR, NOOP when nothing new merged, FAILED with exit 1 when `gh` failed while counting.

## Cost

The sampler, the scorecard, the CI count and the ask digest call no model. They use no Claude subscription usage and no gateway allowance.

## Do NOT

- Read a score as a grade of the session. A long ratio usually means the plan's phases were uneven or the session waited on the human, which the samples' `bucket` field shows.
- Edit `progress.jsonl` to fix a number. Fix the sampler. The history is the source every number is rebuilt from.
- Add a model call to `sample`. Judgment belongs in a separate runner that reads these files.
