# fleet-queue

The agent-queue is the one intake for agent work: one file per item under `~/.agent/queue/<state>/`, and the item is the only record of that work. `agent-queue` is its only writer. `~/.config/agentctl/QUEUE.md` owns the design, the item fields and where each record lives; read it for the fields. `~/.local/src/docs/agent-queue.md` lists every verb. This skill is the operator path: file an item, see why it is not running, close it.

## Scope and triggers

- You are starting tracked work, or a session needs its queue item (`$AGENT_QUEUE_ITEM`, else `agent-queue mine`).
- An item sits queued and you need to know why.
- A PR is ready to land and its item must close.

Not for how dispatch picks and starts sessions (`fleet-dispatch`), or an account having no room (`fleet-runners`, "Account room").

## File an item

1. Your own task, unless `$AGENT_QUEUE_ITEM` is set: `agent-queue add --running --project <p> [--row <id>] "<task>"`. `--row` names the open agent board row you are working, starts it and refuses an id that is not open or that a live item already names.
2. Work for later (an add wakes a `fleet-dispatch kick` that starts it when the gates and room allow; never call `fleet-dispatch run` or a hand `fleet-dispatch start` to push it): `agent-queue add --project <p> [--priority urgent|high|normal|low] [--tags "t1 t2"] [--weight heavy|light] [--after <slug>] "<task>"`. Only the board fills the queue (`~/.config/agentctl/QUEUE.md`, "Admission"): this writes an item only for the human (no `--from` but `human`, in a terminal or a session they opened), a hand start or dispatch's pull. From a machine filer on `agent_direct_filers` it files a board row with the task as its brief, carrying any gate as a gated add does, prints `held <slug> -> <board>:<id>` on stdout (the line a caller reads the row from, never stderr) and exits 5: the normal result, not a failure. From a session (`$AGENT_QUEUE_ITEM` or `$CLAUDE_CODE_SESSION_ID` set) or any other script the follow-up is no row: it goes to the outbox, which prints `inboxed <slug> -> inbox` and still exits 5, and inbox-triage files it or joins its twin, so a session never reads a row id from it. A bare add by hand is high; a session (`$CLAUDE_CODE_SESSION_ID` or `$AGENT_QUEUE_ITEM` set) names `--priority` or is refused: normal for real work, low for upkeep, high only when it blocks a release or a red on main. An urgent add by the human at hand (by hand or from a session they sit in; `--from` defaults to human, and a dispatched session's `$AGENT_QUEUE_ITEM` makes it not) starts its session at once unless the dispatch hold keeps it; any other waits for a dispatch pass. The queue holds only work that can start: a gated add (a gate tag `at:`, `pr:`, `ask:`, `hold:`, `rbw:` or `nightly:`, or `--after` an item not done ok) queues nothing, puts each gate on the item's board row as a hashtag (`#after/<row>`, `#ask/<id>/<option>`), prints the same held line with its gates appended, `(#gate)`, and exits 5; dispatch pulls the row once `agent-queue gate` reads its gates clear, and `set` of a gate on a queued item returns it to its row the same way. An item with no `--row` that is not from the board files its own story row, with the task as the row's brief, less a first line that is the row's own words: the row is the task, the item is the run, so a returned item's next promote takes its brief back from the row, and `agent-queue retask` rewrites both. An item whose plan changed keeps its title until `agent-queue set <slug> title="<new>"` (any state, a done one too); the row's own words are `notes ptask edit`.
3. A plan (whether an epic runs as one: `~/.local/src/docs/lifecycle.md`, "Taking an epic on"): `agent-queue add --plan <plan.md> --dry-run` first, then without `--dry-run`, which from a session names `--priority` as step 2 says. It queues one oneshot item per unchecked `## Phases` line whose wait is met, and files each other one as its board row gated `#after/<the row it waits on>`, which an ok close of that row's item pulls at once (`fleet-dispatch pull-after`). Each line waits on the one before unless the line says `(independent)` (after `--after` alone) or `(after N; needs <result>)` (after phase N's item, `(after N, M; needs ...)` after several; `needs` names the output the phase consumes, and the add refuses a missing one, a shared-file reason such as "edits ship.sh", and a marker that does not parse); `(with N)` joins phase N's item; `(at YYYY-MM-DD HH:MM)` holds that phase alone until then (its `at:` tag, so its board row is gated `#at/<date>/<HHMM>`) at high when the plan is urgent, since an urgent row holds a sprint's cut; a marker may carry a note, `(independent; why)`, with no parenthesis inside it. `agent-queue add --plan <plan> --check` reads and validates the markers alone. A line that opens `P<N>` is phase N (so `P9` above `P8` is still 9 and 8), else its place in the list is its number. At urgent or high, filed by the human at hand, each phase whose wait is met starts at once, and each next one when its predecessor closes ok; at normal or low the first ones wait for a dispatch pass. From a machine filer or a dispatched session `--plan` writes no items: it files one board row titled by the plan's heading and slug (`plan_row_title`), and exits 5 (step 2); dispatch's promote of that row queues the chain (`add --plan --from board:<project>:<id>`), puts the row on the plan's `rows:` line and leaves it started until the last phase lands. A row's gate is released by taking the hashtag off the row (`notes ptask <p> --agent tag --remove <tag> <id>`); when the human says start a gated phase now, `fleet-dispatch start --agent --row <id> --brief <f> --now` starts it past its `#after/`, logged, and never a hand edit of the board file. Mark `(after N)` only when phase N's output is this phase's input, never for shared files (`lifecycle.md`, "Taking an epic on"). `AGENT_QUEUE_START=0` only queues.
4. `agent-queue list [--state queued|running|review|waiting|done|active|all]` prints TSV: state, priority, slug, project, mode, then session, hold or status, tags, from. `show <slug>` prints one item; `next` prints the head.

## States and moves

- queued -> running when a session starts on it; running -> waiting while its session waits on the human or owns a pending ask (`fleet-dispatch reap` does this); -> review (`on a PR`) while it sits on an open PR with its session ended; -> done when closed.
- `agent-queue move <slug> <state>`; `done` needs `--status ok|failed|cancelled`, `cancelled` (and `agent-queue cancel <slug>`) takes `--why "<reason>"`, required from a session or script and kept on the item as `cancelled_by` and `cancel_why`; work the human asked for (`from: human`, or a `#requested` row) cancels from a session or script only with `--ask <id>=<option>`, an ask with options naming the item that the human or the judge answered with that option, and `done --status ok` on an item with `pr:` refuses until it has `merged:` (agent-land, or reap on merge, writes it); `done --status ok` with no `pr:` also closes the item's board row, `--proof item:<slug>`, and warns on stderr when that close fails. `--if <state>` makes the move conditional and exits 3 when the item is elsewhere. `cancel <slug>`, `bump <slug> <priority>`, `set <slug> key=value` (for example `pr=<N>`). `retask <slug> "<task>"` (or stdin) rewrites a queued item's task when it holds a wrong fact; the header stays. `reopen <slug> [--to running|waiting] [--why text]` puts back an item a false close finished (a reap that read a live session as gone) and starts its board row again; it reopens a `failed` close as it is, and an `ok` close only with `--unland <owner>/<repo>#<N>`, the PR it closed on that was not its work: that PR comes off `pr:` and `merged:`, and its row reopens through `notes ptask reopen` before it starts. It exits 1 when the row will not reopen or start.
- Sending items back to their board is `agent-queue return <slug> --why "<reason>"`, never `cancel`: it closes the item `cancelled` with `end_reason: returned`, un-starts its row, and takes every queued item `after:` it along (`cancel_cause: returned with <slug>`). A return of the human's work needs no ask unless it is `--drop` or the item has no board row; those take `--ask <id>` as cancel does. A plain `cancel` leaves those items dead, and a cancel of an item behind a dead `after:` records `cancel_cause:` with the root cause. A row gated `#after/` on a row that was dropped, or `#ask/` on an ask that can never release it, reads dead in `agent-queue gate` and in `fleet-dispatch starved`: take the tag off the row or re-gate it. Why: 2026-11-12 a bulk return by cancel lost about 40 chains (ar-2299).
- `agent-land` normally does the closing. Use `move ... done` by hand only for work with no PR.

## Why an item is not starting

1. A gated row: `agent-queue gate --all` names each gate tag on the open rows clear, pending (why) or dead, plus a clear line for each `#hold/` row a grant lets through (`row` in `--json`). An item queued before the board held gates (`agent-queue list --state queued`, the sixth column) holds the same way. Holds are `after <slug>` (that slug must be done ok; a failed predecessor never releases it), `at:HH:MM` (not before that time TODAY; once the time of day has passed it holds nothing, so use `at:YYYY-MM-DDTHH:MM` for a later day), `pr:<owner>/<repo>#N` (until the PR is MERGED; a failing `gh` also holds), `nightly:<repo>` (until that repo's scheduled runs for today have finished), and `ask:<id>[=<option>[+<option>]]` (until the human answers that agent-ask, with one of those options as the answer's first word; an ask that offers options must name them; pending, cancelled, judge-answered or missing holds), and `hold:<resource>` (while `agent-hold` holds that resource, by anyone; a session that finds one it needs held runs `agent-queue requeue <slug> --hold <resource>` and winds down), and `rbw:<folder>/<name>` (until `rbw list` shows that entry; locked rbw holds; file it with any ask that has the human add a key, so the deploy starts on its own). The full rules: agentctl `QUEUE.md`, "Order and tags".
2. No hold: it is a dispatch gate. `fleet-dispatch stopped` names it in one line, and `fleet-dispatch run --dry-run` shows what a pass would pick. Common ones: no account has room (`fleet-runners`, "Account room"), load or `fleet-assess` HOLD (`fleet-pace`), run units full (heavy holds 2 units, light 1; `fleet-dispatch headroom`). `DISPATCH_PER_PASS` caps the starts a pass makes when above 0 (default 0, no cap; the conf leaves it unset).
3. Tags: `red` is read by `fleet-dispatch`, not by `agent-queue`: it sorts the item first, briefs it on the `fix-red` skill, which reviews and merges its own PR, and exempts it from the board waiting while the human is present. `cause:<sig>` marks a red item `fleet-bench triage` filed for a recurring failure (routes in `~/.config/agentctl/triage-routes`); a fix in hand (queued, running, waiting or in review) keeps its cause from being filed again, and `add` refuses a second live item with that `cause:`, naming the owner; one that closed with the red still here is retried, tagged `retry:<earlier slugs>`, up to `TRIAGE_FIX_TRIES` (2) items in `TRIAGE_FIX_DAYS`, then one escalation on Opus, then one ask (no human-sheet row); `TRIAGE_FIX_CAP` limits new ones a day.
4. A running item whose session is dead is the shepherd's to nudge or reap (`shepherd`).

## Land and close

1. `agent-land <pr>` runs fetch, item-line, checks, merge, proof, item, board, plan. Add `--item <slug>` when the session records more than one item, `--plan <file> --phase "<text>"` to tick a plan phase, `--dry-run` to see the steps. Run it from a checkout of the PR's repo: the number is read in `--repo <owner>/<repo>`, else the repo of the item's own `pr:`, else this checkout's, and a PR outside this checkout's origin, or a merged one that is not the item's, is refused.
2. The item is `--item`, then `$AGENT_QUEUE_ITEM`, then `agent-queue mine`. With none it refuses before any gh call; add one with `agent-queue add --running`. An item taken from the session, not named by `--item`, takes only a PR in its project's repo: a side PR in another repo is refused before anything is touched, so name its item (`--partial` while the item's own PR is still to land). In that repo it takes only a PR the item records (`pr:`, `open_pr:`) or whose body names it on an `Item: <slug>` line; any other PR is refused, since it may be a side fix (unity-core-playground#2985 closed its session's release watch, ar-3970) or a sibling subagent's work (they share one session id, so `agent-queue mine` can return a sibling's item). Pass `--item <slug>` for such a PR.
3. Exit 0 landed, 1 a step failed (fix it and re-run; an already merged PR skips checks and merge, so the re-run finishes the record step), 2 usage (more than one item without `--item`, or the removed `--project` and `--title`), 3 behind origin base or a catch-up conflict (merge the base, re-run), 4 stacked on an item that has not closed done ok (re-run once it has), 5 critical work (`judge_work_level`) waiting on its validate item: a second agent's session reviews the PR and lands it on a pass, so the author winds down.
4. A `tier3` PR item (not `cleanup`) stops at the open PR: `agent-queue set <slug> pr=<owner>/<repo>#<N>`, then `agent-queue move <slug> review`. `fleet-dispatch reap` records `merged:` and closes it once the PR merges.

## Do NOT

- Do not write into `~/.agent/queue/` by hand or `mv` an item; every transition goes through `agent-queue`, so two writers cannot both move one.
- Do not file an item for a want nobody has set up: that is a follow-up sent with `notes ptask --agent add --why <slug>` (the outbox, then a board row; the slug names the row's priority, `notes-system`), and `agent-queue` is not a notes list. Work the human asked for in a session they opened is not a follow-up: `agent-queue add` for one task, `--plan` for several; an add from their interactive session starts now unless low, and every start at add that does not start leaves a line in `~/.agent/dispatch/log.md`.
- Do not `cancel`, `move` or `bump` another session's item. Do not dispatch around a gate by adding an item with a fake hold or tag.
- Do not merge a PR with `gh pr merge` and skip `agent-land`; the item, board row and plan then never close.
