# shepherd

The delivery role of `fleet-lead` (Binks). Binks aims at measured improvement of the fleet, one KPI at a time with a check (`fleet-lead`, step 3); this role is the means. It answers one question: is every session either working, waiting on the human, or finished and wound down? A session that is none of these gets one nudge per fact, and a fact that survives its nudge goes to the human. It never does a session's work for it.

## Scope and triggers

Covers moving every agent session through its plan: the buckets (WORKING, STALLED, LANDED, DONE), one nudge per fact, escalation and overdue phases.

Use for "which sessions are stuck", "nudge the stalled ones", "wind down the finished ones", "/shepherd status". Load: `fleet-pace`. One pass over everything: `fleet-lead`.

## Verb: `status`

Run `fleet-sessions` and show its table. It sorts every live Claude session into one bucket from facts (session status, plan mode, the ask queue, `fleet-assess` rows, git, and the PR store), with no judgment:

The buckets (PARKED, NEEDS, STALLED, WORKING, LANDED, DONE, CHAT and NIGHTLY) are defined once, each with its entry facts, exit, actor, action and pinning test, in the bucket table of `~/.local/src/docs/fleet-states.md`. Read it there; `tests/unit/fleet_states_doc.bats` keeps it equal to what `fleet-sessions` emits.

**The rule.** Every row's `blockers` lists each reason it is not DONE; quote them when you report a row. A session is DONE when its plan's `## Phases` checklist has no `- [ ]` left (`[x] <name> (#PR)` landed, `[-] <name>: <why>, <board row>` deferred by the human), no ask, prompt or plan approval of its own is open, and nothing it made is unlanded. A plan with no checklist, or no plan file, is one phase: its merged PR with a clean tree is DONE. A non-code kind (`kinds.json` `exit` doc+ask: research, design, legal) never makes a PR: its session is DONE once its item records the doc it wrote (`report=`) and the ask it filed (`ask=`), and that ask is the human's to answer, not the session's blocker. Then, and only then, it winds down. A phase is a queue item: `agent-queue add --plan` turns a plan's unchecked phases into items chained with `after:`, each started in its own session, so a session whose remaining phases are items is DONE once its own phase lands. Until its phases are queued a merged phase is LANDED (the LANDED row of the bucket table says who files the rest).

Dirt counts by owner: in a session's own worktree (under `~/.worktrees/`) every dirty file is its own, but in a repo's main checkout only the files it edited count (`edited_files` from agent-panel), so the human's half-done config does not stall every session in that checkout. The reason names the first 3 dirty paths (`FLEET_DIRTY_NAMES`), so the nudge says what to land or restore. Ahead counts files whose content is not on the default branch, not commits, so a squash merge or a local merge of landed work reads 0.

**The watch board.** The hub board's Sessions tab (key 4 in window `hub:board`, `hub tab sessions`; the web's Sessions tab) is the same facts as a stage board the human leaves open: one row per session with a column per stage (sync: commits behind the default branch; conflicts: whether merging it in would conflict; tree; PR; CI; plan phases; eta: the expected finish from `fleet-bench eta`, HH:MM or with a weekday when not today, plus its basis short (`s3` is the session's own median over 3 phases, `p16` the project's, `default` nothing measured yet); stage = the bucket; labels; idle; why, which on a WORKING row is the session's last action; task; prs: merged over total this session, all repos; work and wait: how much of its age was work, and the largest other share, jobs, you or parked), the open asks, and below them the last changes from `~/.agent/shepherd/watch.log` ("agent-11  ci pending -> fail, stage WORKING -> STALLED (PR #979 CI red)"). `fleet-state.timer` runs `fleet-sessions tick` every minute: one fetch and collect that writes the state document (with each session's `eta`), appends the changes to `watch.log` and keeps `watch.state`, so the log builds whether or not the tab is open. Read `watch.log` since your last pass to see what moved. `fleet-sessions explain <who>` prints one session in full: plan, each PR with its state, the time split, its last action and message. Parked hours say a session sat still until something woke it, not why, so check before calling one forgotten.

**Labels** carry only what the facts cannot: `fleet-sessions label <session|self> +name|-name` (no ops prints them), shown in the `labels` field. `manual` is the human's: the shepherd leaves that session alone until it has been quiet `FLEET_CHAT_CLOSE_H` (24h), when its close verdict reads now and `close_sample` closes it. A session sets it on itself only when the human told it to stay open, as its answer to a close (wind-down, step 0, check 3), so one reply stops every later nudge and escalation. `quality:<step>` is a session's own, set while a cleanup pass runs and shown in the board's quality column. Stages are never labels; they are derived every pass.

`FLEET_IDLE_MIN` (20), `FLEET_SHELL_STALE_MIN` (120: a background shell waiting on a gate, a test, a build (a Unity authoring run), a subagent or a process (`tail --pid` on another pid, an event wait), by agent-panel's `open_job` class, is WORKING until this, then bucketed on its facts with "background shell idle over 120m", except a live `FLEET_QUEUE_GATES` process (`gate-and-land.sh`, `ci-gate.sh`, `gate-line.py --recheck`, `agent-land`: a gate waiting for its landing turn, which ends itself), which stays WORKING, as does a background `pgrep` loop on a live one (`pgrep -f 'gate-and-land.sh 123'`, its pattern naming that gate); any other shell, a sleep loop or a watch, is bucketed on its facts after `FLEET_IDLE_MIN` with "background shell is not a gate or test"; a finished plan reads DONE after `FLEET_IDLE_MIN` with "background shell still running") and `FLEET_GATE_LOGS` (`Logs/gate.txt Logs/gate-and-land.out`: a write to one of these under the worktree, or to the output file of a background task the transcript has not seen finish, counts as activity for a gate or test shell, so a running local gate is not idle) and `FLEET_SUSPECTS_MAX` (3) are the tuning knobs. A nightly suite after a busy day has dozens of PRs in its range, so nobody is told it was theirs and the human gets the row. Say the NIGHTLY rows first, then the counts per bucket, then the NEEDS rows in full and the CHAT rows one line each. Read-only.

## Verb: `triage`

The close analysis, for "where is each session, can it close": `fleet-sessions close` (`--json` for a reader). One line per session, close-now first: verdict, session, bucket, phases done of total with percent, quiet minutes, `fleet-bench` eta, and why. The verdict (`now`, `after <step>`, `keep`) is the `close` field of the state document; its steps are the close flow in `~/.local/src/docs/fleet-states.md`. Report it as counts per verdict, then the `now` rows by name, then the `after` rows with their step. It changes nothing and closes nothing.

## Verb: `nudge`

What a `fleet-lead pass` runs for `nudge`, `escalate`, `overdue`, `landing`, `nightly red` and `shared red` due lines. The code (`fleet-shepherd due`) applies the same rules to the state document, so a due line is the row this verb would act on.

1. `fleet-dispatch reap`, which moves each queue item by its session: to `waiting/` when the session waits on the human (a pending ask counts only once the session is neither busy nor in a shell), to `done/` when the session is gone (`review/` while its PR is still open), un-starting a board item's row when it ended without a PR. Then `fleet-sessions --json`. Each row has `bucket`, `pane`, `fact`, `nudged`, `escalated`, `plan_file`, `phases_done`, `phases_total`, `next_phase`, `finished` (DONE's work conditions alone, ignoring status and idle, the close flow's `finished` step reads it), `owners`, `dispatch` (the row it was started for, or null), `main_red` (its repo's default branch is red: a NIGHTLY row exists for it; the field name is kept for its JSON readers),, `labels`, `open_job`, `wait_min` (minutes its oldest queue gate has waited its landing turn, local sessions only, else null) and `landing_queue` (PRs labelled for its repo's landing queue, or null). NIGHTLY rows come first and lead the report: a nightly red is the most important thing on the board.
2. `ListAgents`, and match each row to a session name by its pane id (`%216` in both).
3. Skip every row whose `labels` holds `manual`: the human has it, so it is never messaged or escalated (past quiet `FLEET_CHAT_CLOSE_H` its close verdict is now, and `close_sample` closes it); list it in the report as manual. Skip every PARKED row the same way (its claude is gone, so a message wakes nothing); list it as parked. One with nothing left to land is closed by `close_sample` (its window, nothing typed), and an item left open with every phase done or queued is moved done by `close_items_sample` once quiet; neither is a nudge. A nightly red never stops work: `main_red` changes no nudge, because the PR gate keeps the default branch green and a nightly is fixed by its owner or the human, not by stalling everyone else. 2026-11-03: the old skip left three sessions idle 3-5 hours on unlanded work behind a Shots-only red, and the human said the nightly should never stop work. For each `nudge` due line (STALLED rows with `nudged: false` whose close verdict is not `now`, and DONE or LANDED rows the close flow keeps with a `close.left`; any other LANDED row gets none, for the reason in the rule above), claim it with `fleet-sessions mark <session_id> "<fact>"` first and send one `fleet-comms` message only when the mark succeeds: exit 1 means another pass already nudged this fact, so send nothing (a `then: fleet-sessions mark` on a due line that exits 1 was already marked: the same rule). A send that fails after the mark is not retried: the row reaches the human as nudged and unmoved. A row holding an open ask it filed (`own_asks` above 0) is not nudged: its window is where the question waits. A close is never a message. Every row whose close verdict is `now` belongs to the 15-minute `fleet-shepherd check` (`close_sample`), with no model: it claims the close once for good (`fleet-sessions mark --close <session_id>`) and types `/wind-down auto` (`/wind-down` for CHAT) into an idle, empty prompt; a pane that cannot take typing (a draft in the box, copy mode, busy) waits for the next check, and a row that stays after its close reads `nudged` and is escalated once. Why: 2026-11-18 a pass's message to a session in another permission mode was held for approval and expired unseen, its mark stopped the typed close, and hub/dotfiles:4 and :8 stayed open overnight.
   - STALLED where the session says its phase is blocked on the human (a key, a secret, an approval): read its pane first, and send this instead of its bucket nudge: "Which step needs the human? Only that step is blocked, not the phase: build the rest with that step switched off, open the PR, post one `agent-ask` with the exact commands, then carry on with your plan." A phase that as a whole must wait for the human's decision is queued by the session behind an `ask:` tag (`fleet-queue`, step 3).
   - STALLED `PR #N closed without merging`: "PR #N closed without merging and no PR of yours merged. If another PR replaced it, say which; if the work is still wanted, open a new PR; if it is not, say so and run /wind-down auto."
   - STALLED `its item <slug> is running here`: "Your queue item `<slug>` is still running here, and nothing unlanded on your branch is its work (a PR that merged may be another item's). Carry on with it to a PR; if it is done or blocked, `agent-queue move <slug> done` (or `waiting` with an `agent-ask`) and run /wind-down auto."
   - STALLED `its item <slug> is still open with every phase done or queued`: "Every phase of your plan is ticked or held by another queue item, so closing `<slug>` is all that is left: `agent-land <your last PR> --item <slug>` without `--partial`, or `agent-queue move <slug> done`, then /wind-down auto."
   - STALLED `its plan file is missing`: "Your plan file (`<plan_file>`) does not exist, so no one can tell which phases are left. Restore it (or write the `## Phases` checklist again in a new one), then carry on. If the work is finished and the plan is gone on purpose, say so, close your item (`agent-queue move <slug> done`) and run /wind-down (not `auto`: it reads this row as unfinished)."
   - STALLED `nightly red after PR #N`: "The default branch's `<workflows>` went red in the range that includes your PR #N. Reproduce it, fix it on a new branch off origin/main, land it, then carry on with your plan."
   - `nudge SHARED:` due line (a test red on several branches, owned by the queue item it names): send each session id it lists: "`<test>` is red on several branches at once and queue item `<slug>` owns it. Do not gate again on it; carry on with other work and merge main once `<slug>` lands." Then run the line's `fleet-sessions mark` call.
   - STALLED `PR #N conflicts with the default branch`: "PR #N conflicts with the default branch. Merge origin/<base> into your branch and resolve it; never rebase a pushed branch. A green gate stays green: gate again only when the merge changed files your pick depends on (the repo's CI doc, for unity-core-playground docs/operations/ci.md rule 6). Then carry on with your plan."
   - STALLED with `background shell is not a gate or test`: "Your background shell is not a gate, a test or a subagent. If it waits for a time or a day of data, queue that step as an `at:` item whose task names your plan (agentctl `QUEUE.md`, `at:`), close this item, and wind down; otherwise stop the shell. Then carry on with your plan."
   - STALLED `turn ended on API Error <code>`: "Your last turn stopped on an API error (<code>), usually a transient edge fault. Retry what you were doing and carry on with your plan."
   - STALLED `resume killed its background <kind> (<text>) before it finished`: "Your session was resumed (a reboot or a lost tmux server) and that killed your background <kind> (`<text>`) before it finished; nothing reran it. Run it again now, the same command in the background, then carry on with your plan."
   - STALLED: name the fact and the next step from `one-shot`: dirty or ahead with no PR, open the PR; red CI, fix it; green and unmerged, merge it; work after a merge, land it as a new PR. End with "then carry on with your plan".
   - `nudge DONE:` or `nudge LANDED:` due line: the close flow keeps the row for work left here, and its `close.left` names the blocker. Send the STALLED message above that matches `close.left`, not the bucket reason, which names the plan: `its item <slug> is running here` and `its item <slug> is still open with every phase done or queued` take their own messages, `nightly red after PR #N` takes the nightly one, and unlanded work (dirty files, off the default branch, `PR #N open`, commits after a merged PR) takes the generic STALLED one.
   - `overdue:` due line (a WORKING session, or a NEEDS one carrying on, not mid-turn, whose state.json `overdue` verdict is set: fleet-sessions `overdue_of` calls a phase overdue once it has run twice its `fleet-bench eta` estimate and at least an hour, never while its queue item still waits on a gate or the session waits its landing turn, and puts it on the session running the phase, once for every session sharing the plan; fleet-states.md "Schema"): read its pane first. If it is plainly moving (a gate running, output in the last minutes), `fleet-shepherd skip "<line>" "<what it is doing>"`. Otherwise: "Phase `<n>/<m>` `<name>` has been open `<age>`, about twice the `<expected>` a phase takes here. What is blocking it? If it is the human, ask in this conversation and file it with `agent-ask post`, then build the rest of the phase without that step; if it is too big, land what works and split the rest into the next phase; otherwise carry on and land it." Then run the ledger call the line prints. An `escalate overdue:` line goes to the human as step 4 says, with the ledger call it prints.
   - `landing:` due line (a project whose oldest queue gate (`gate-and-land.sh`, `agent-land`, `gate-line.py --recheck`) has run `FLEET_SHEPHERD_LANDING_WAIT_MIN` (120) or more, counting every session whose gate waits, manual ones left out; a session with a measured wait is never `overdue:`, and a skip holds for the project while its queue stays slow): find what holds the slot (`gh pr list -R <repo> --label landing-slot`) and the session landing it. If that one is moving, `fleet-shepherd skip "<line>" "<what holds the slot>"`; if it is stuck, escalate the line as step 4 says.
   - `critical:` due line (a session whose open PR waits on the landing slot while #high or #urgent board rows are gated `#after/` on its item's row, waited `FLEET_SHEPHERD_CRITICAL_MIN` (60) or more; state.json `critical`): the rows it names wait on this PR alone, so never skip it as "WORKING". Queued behind others, run its `then:` bump, which the slot honors from its next poll, and read the place again on the next pass; holding the slot or riding a train, read that gate, and if it is not moving take the landing over from its worktree (the lesson of 2026-11-19).
4. **Escalate.** Rows for the human: NEEDS rows and NIGHTLY rows with empty `owners`. A DONE, LANDED or CHAT row that survives its nudge is closed by the close flow (a close that fails pages once, `close_page`), and a STALLED row that survives it is taken over (below), so neither gets an `escalate` line. Never message them. For each one with `escalated: false`, run `fleet-sessions escalate <session_id> "<fact>"` with the row's fact exactly (an `escalate` due line carries that call as its `then:`; a reworded fact never clears the line) and add it to this pass's page (`fleet-lead`, Reporting). A `shared red:` line is a shared test red no queue item could be filed for: escalate it the same way. A NIGHTLY row with owners is theirs to fix; it reaches the human only when the owner's nudge did not move it. A `pace:` line naming parked sessions is `fleet-pace`'s, not this verb's. A row typed its close (`close_sent`) whose verdict is still `now` and whose pane is an idle prompt is closed by `fleet-shepherd check` an hour after the close was typed (fleet-states.md, Close verdict); escalate the rest as above. **Takeover.** A STALLED row not `manual`, not in plan mode, on this machine and with no ask of its own, whose nudge is `FLEET_SHEPHERD_TAKEOVER_MIN` (60) old and which has been quiet that long, has its window closed by `fleet-shepherd check` (`takeover_sample`, through `wind-down.sh close`, at an empty idle prompt only) once its work is safe: a clean tree, its commits on a remote, a branch off the trunk and a queue item of its own. `fleet-dispatch reap` hands its item, PR or branch to a fresh agent; the shepherd starts nothing, and you do not message or close such a row by hand. A row it cannot hand over, a close that fails, or a branch already taken over `FLEET_SHEPHERD_TAKEOVER_TRIES` (2) times that stalled again pages the human once per fact (`takeover-failed:` in log.md); no other STALLED row pages.

## A task from the human

When the human gives the shepherd a task, plan it with them in the chat until the task text is complete, then file it: `agent-queue add --from shepherd --want human --project <p> [--row <id>] --priority <p> [--after <slug>] "<task>"`, with `--priority urgent` when the human calls it important or asks for a report back, so it leads every summary (fleet-lead, "Your requests"), and otherwise the priority and `after:` that fit what is already queued (`agent-queue list`). Only the board fills the queue (`~/.config/agentctl/QUEUE.md`, "Admission"), so the add files a `#requested` board row after the self-check `notes ptask add` runs in a session the human opened (a shortlist of similar open rows means no row yet: join the one that is this work, or file it with `--checked <their ids>`), which ranks first, carrying any `--after` as its `#after/` gate, and exits 5. A task with a report says in its text to publish the report and run `agent-queue set <slug> report=<url>`. The dispatcher promotes and starts it; the shepherd never starts a session itself (fleet-lead, "Do NOT"). Store and verbs: `~/.config/agentctl/QUEUE.md`.

## The ledger

`~/.agent/shepherd/<session_id>` holds the last nudged fact and the last escalated fact. `~/.agent/shepherd/.takeover` keeps each window closed for takeover (by branch) and each failed takeover paged; `.close-paged` lists each session whose failed window close was paged. A new fact for the same session (its PR went from red to green, or the next phase merged) is nudged again; the same fact never is, whichever pass sends it (`mark` refuses a fact already marked). Every DONE fact is one fact (its tail shrinks as queued phases start), so a DONE session is nudged once and then escalated if it stays. An open PR's fact ends with its head commit (`@branch@<sha12>`), so a push that is still red is a new fact and gets one more nudge. A conflict's fact ends with the merge base instead (`@branch base <sha12>`): the same unresolved conflict at a new head is the same fact, and only a branch that merged the default branch in and then conflicts again is nudged again.

## Do NOT

The fleet-wide list is in `fleet-lead`; these are this role's own.

- Close, kill, or `/wind-down` a session yourself (`claude-acct move` is not a close: the same conversation carries on in the same pane). The shepherd asks: `close_sample` types `/wind-down auto`, which the session runs and refuses unless its close verdict is now (`fleet-sessions close --self`) or when its last message is an open question to the human.
- Message a NEEDS, WORKING or CHAT session, send a close by message (`close_sample` types every close), or repeat a fact the ledger already holds. The exceptions are an `overdue:` line and `fleet-pace`'s line to a session whose search was killed.

## Related

- `fleet-lead`: the pass that routes these due lines here, and the report and page.
- `fleet-comms`: message wording.
- `fleet-bench`: the phase estimates fleet-sessions measures the `overdue` verdict against, and the board's eta column.
- `one-shot`: the delivery tail (gate, PR, merge, board done, pull, wind-down) a nudge points a session along.
- `wind-down`: what a DONE or CLOSE session runs as `/wind-down auto`; it checks `fleet-sessions close --self` reads `now`, that no question to the human is open, and that the human did not order the window kept open (then it labels itself `manual`) before closing. A human-asked wind-down skips all three checks.
