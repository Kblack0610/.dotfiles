# agent-web

A web view of the Claude agents running in tmux on this machine. From a phone or another computer you can read any session's transcript or live screen, type into it, press the keys a permission prompt needs, and answer the headless `agent-ask` queue. The board tabs show the tabs of the tmux hub board (`hub:board`, `Prefix+i`) with charts: the same tabs in the same order (`hub_core::layout`), from the same hub-core readers.

It reuses agent-panel's library (the pane x `~/.claude/sessions` join, the tmux wrappers), so the web list and the `Prefix+g` chooser always agree on what an agent is.

A new tab or section follows `../docs/dashboards.md` (the dashboard standards, and the layout both hub surfaces are moving to).

## How it works

| Piece | Source |
|---|---|
| Daily's outbox (`#daily/outbox`) | `/api/outbox` (`src/outbox.rs`). GET is hub-core's `outbox::read`, the reader the hub TUI's Daily outbox view (`o`) shares: `notes outbox show --json` (the `## Outbox` items as text, their hash, how many wait) and today's intake steps from `notes log --day <today> --json` (filed, dup, planned, left, refused; newest first, counted). PUT `{base, text}` pipes the text through `src/cli.rs` (the one place agent-web spawns `notes` with stdin) to `notes outbox put --base <hash>`, the one writer: it replaces the items under the outbox lock if the hash still matches, else exits 3 and the handler answers 409 with the current doc (a CLI error is a 502; a control character or over 64 KB is a 400). The view (`static/outbox.js`, drawn in the note's place on Daily, reached from Daily's nav; the retired `#outbox` lands here) is one textarea that saves 1.5s after you stop typing; the line the cursor is on is held back while it is new, until Enter, Send (Ctrl+Enter) or leaving the box, so the sweep never files half a sentence. The sweep (`agentctl-inbox-triage --watch`, 30s after the last write) takes the lines it files out of the file; a write of `outbox.md` or `ingest.jsonl` is an SSE `outbox` event, the page re-reads, and `mergeLines` drops from the box only the lines the sweep took, keeping what you typed since. Reads and writes run one at a time, and a 409 merges and saves again. Handled today lists each step with its time, row id and project link, a left or refused line with its why |
| Home tab | `/api/home` (`main.rs` `home_board`) is hub-core's `home::build`, the join the hub TUI's Home draws, over `state.json` (its asks read live from `agent-ask list`, `hub_core::boards::state`, so Home matches the questions panel), agent-queue and the Infra tab's cached Prometheus answer: NUMBERS and HEALTH first (only the domains that are not green; all green is one chip), then NEEDS YOU (asks, sessions waiting on you, waiting queue items, red nightlies, `cc:red_now`; one row per tmux session, newest first) and RUNNING (the queue's running items with plan phases). Each list shows its first `shown` rows (`hub_core::home::SHOWN`, sent in the answer) and folds the rest under `+N more`. Each Needs you card leads with its kind (`NEED_KINDS` in `static/waiting.js`: Plan to approve, Question, Permission, Your turn, Blocked, Failing) and a stripe in that kind's colour (categorical hues for the dialog kinds; amber and red only for blocked and failing, dashboards rule 5); the list is grouped in that order under one chip per kind with its count. An ask or an open dialog on Needs you is drawn with its answer card (`static/waiting.js`), so it is answered in place. It re-reads on the fleet state, queue and asks events and every 60s while open (Prometheus has no push). `#waiting` and `#asks`, the retired Waiting tab, land here |
| Queue tab | agent-queue, the one intake for agent work (`~/.config/agentctl/QUEUE.md`), and the only writer of `~/.agent/queue`, so every route shells out to it with plain arguments (`src/queue.rs`): `GET /api/queue` is `agent-queue list --json --state all` (active items plus today's finished ones), `POST /api/queue` is `add --from human` with the task on stdin (a plan item starts its session at once, inside agent-queue), `/api/queue/cancel` and `/api/queue/bump` are `cancel` and `bump`, and `/api/queue/projects` is the names in `project-map.json`. agent-queue's stderr comes back as the 400 the page shows. `/api/queue/stats` is `agent-queue stats --json` worded by hub-core (`Stats::week` and `sitting_line`, the hub Queue tab's two lines), shown above the sections. `/api/queue/candidates` is `hub_core::queue::candidates` (`fleet-dispatch suggest --json`): hub-core's total, auto count and first 30 ranked rows, each with hub-core's title and start label, read on showing the tab and after a promote, never on a queue event, since it reads every board; Promote posts the board's Start to `POST /api/board` (`fleet-dispatch promote`). Sections: Waiting for you, Running, Up next (with why an item waits), Done today, then Candidates folded; each `/api/agents` row carries `items`, the queue items in that pane (hub-core `with_items`, fleet-sessions' `item_of` rule: an item whose `sessions` holds the pane's Claude session id, as an item added by hand records, or whose `session` names its tmux session, narrowed to the `window` it recorded), and that is how a card finds its panes. Open session shows when that is one pane; an item from before `window` existed can share `hub:dotfiles` and find several. A card carries what its session needs: the dialogs open in its panes and the pending asks they filed, answered as on the Waiting tab. An item with several panes shows every dialog and ask from them, each labelled with its pane. A waiting item with neither says `Waiting on a prompt in its window` and names the tmux session, or `No live window` when no pane is left. The tab opens on the pipeline line from `/api/pipeline` (`src/pipeline.rs`, hub-core `pipeline::read`, the reader the hub TUI's Queue tab shares, cached 30s): the same words, a `graph` link to Grafana's Agents / Overview (`kb-agents-overview`) when `CC_GRAFANA_URL` is set, and `pipeline -` when fleet-bench's `agent_chain_*` gauges are absent. The tiles still count from the items |
| Projects tab | `/api/projects` (`src/projects.rs`) is hub-core's `projects::build`, the cards the hub TUI's Projects tab draws, each with the same `summary` line; it takes the table's `q`, `s`, `sort` and `dir` and answers the cards the view keeps with `table` (hub-core `impl table::Row for projects::Card`). The list is one table on `static/table.js`, a row per lab project: stage, version, prio, open, done, percent, pace (`pace`, rows closed in 28 days over 4), ETA, running, waiting, queued, in flight first, with chips all, in flight and waiting and dropdowns for profile and stage; the queue items no card claims fold under it. The list and the rows share the tab's URL query: the list owns it when nothing is open, the rows when a project is, so a click or Back clears it and a deep link keeps its own, and with a project open every card is read. A click on a row opens its card over that project's rows: it reads `/api/projects/{name}/page` (hub-core `page::named`, the page the hub TUI's opened card prints), then shows the goal, the Flow line, Needs you, and Build by system, Next stage, Shipped, In flight (running sessions with their phase, the queue counts) and Agent note (the dated status) as folds with their counts; All rows in the list's head shows every project's. `#board` lands here; `#projects/<name>` (or `<profile>/<name>`, or `all`) opens that project's rows, which is where a `#p:` link on Daily goes. The rows: every project's open rows from `notes board --json` (`src/board.rs`, read through hub-core `tasks::feed`, the reader the hub TUI shares): the human sheet, the agent board and playtest of every profile. A profile's Focus rows are not listed: `tasks::feed` counts them, and All shows `Focus: <profile> <n> open` linking to Daily. `GET /api/board` takes `scope` (`<profile>/<project>`, as Jobs takes `name`) and the table's `q`, `s`, `sort` and `dir`, and answers the rows the view keeps with `table` (hub-core `impl table::Row for tasks::Row`, the same view the hub's rows use): one table on `static/table.js`, most urgent first, with chips all, in progress, filed today (a row's `filed` date equal to the feed's `today`, so the CLI's clock decides), urgent and requested, dropdowns for project, lane and priority, and `tag:` and `profile:` terms in the search. A click opens a row under itself with its whole text and actions. `POST /api/board` takes `{verb: add|start|done|drop|move|promote|demote|edit|tag, profile, project, lane, ...}` and runs the command hub-core `tasks::argv` builds, `notes ptask`, or for start `fleet-dispatch promote`, which queues the row as an item that waits for the human to be away (add carries priority, an optional version `--to` or playtest `--game`; done needs a proof or an unverified reason, drop needs `why` or the `dup` id; start, move, promote, demote and edit are refused on playtest; move names its target as `dest` and/or a version `to`; edit replaces the text and keeps the tags; tag takes space-separated `add` and `remove` words (Tags... on a row); an add to the human lane whose text is not yet `type(area): title` goes to that sheet's `## Inbox`, for the inbox triager). The table's head line counts the rows still waiting in the inboxes (each project's `inbox`). The page has no open-sheet action: a browser cannot open a local editor (the hub's `o` does). Every write but add passes the row's exact line (`--exact`), so a row changed on disk since the page read it matches nothing and writes nothing: notes' message comes back as a 409 and the page re-reads. A malformed write is a 400. Nothing watches the notes vault, so the tab reads when shown, after each write, on resync and on Refresh |
| Agent list | hub-core `session_actions::gather`: `agent_panel::chooser::collect_all()` (the live agents plus a row per `claude-acct park` ledger in `~/.agent/parked`, the sessions you are attached to first), each with its account (the claude's `CLAUDE_CONFIG_DIR` named by `~/.config/claude-acct/accounts`), plan slug, pending ask, and the agent-queue item that started it (`agent-queue list --json`) |
| Session actions | `POST /api/session/<target>/<action>` (target URL-encoded, body `{"account": "..."}` for move) runs hub-core `session_actions`, which maps each action to the command that owns it: interrupt is Escape into the pane, park/unpark/move are `claude-acct park`/`unpark`/`move --to`, stop types `/exit` and then kills the window, cancel is `agent-queue cancel <slug>` (offered only for a session a queue item started), approve-plan presses the digit of "Yes, auto-accept edits" (offered only while the pane, captured for sessions in plan mode, shows the plan dialog; a permission prompt also offers "1. Yes", so only a digit below the plan dialog's "Would you like to proceed?" line counts). It refuses a target that is not a live or parked session and an account not in the accounts file; the command's stderr comes back as the 400. `GET /api/session-options` gives the page each action's confirm text and the account names. Every button arms a confirm in the page first; a parked row offers only unpark and reads only its transcript |

| Live screen | `tmux capture-pane` on the agent's own pane id |
| Typing | `load-buffer` + `paste-buffer -p` (bracketed paste, so a newline does not submit early), then `Enter` once the pane has drawn the paste, since Claude Code drops an Enter sent right behind one |
| Keys | a fixed list: Enter, Escape, arrows, Tab, Space, 1-9. No `C-c`/`C-d` |
| Answer cards (Home) | each `waiting` or `idle` session's open question, read from the end of its transcript (`transcript::pending_question`): an AskUserQuestion dialog with its options, an ExitPlanMode dialog with its plan and an Approve plan button (the approve-plan session action), a tool waiting on permission, or its last message. A session with a `## Phases` checklist shows `done/total phases, next: <name>` from `state.json` (hub-core `boards::phases`), on its Sessions row, its Home card and its Queue row. A plan shows whole, with its buttons above it. Answers go through Typing/Keys into that session's pane, so they land in the conversation that asked; a typed reply to a dialog sends Escape first. The chat is the shepherd's session, a row opened like any other (its Chat button opens it); an answer it gives there is also kept as a rundown. The lines a pass skipped on purpose are a button that opens Log's Actions section filtered to the shepherd's skips |
| Log: ranked sessions | `/api/outcomes` and `/api/outcomes/card?sid=` (`src/outcomes.rs` over `hub_core::outcomes`, drawn by `static/watch.js` `renderLogRanked`): the week's sessions worst first by `agentctl-session-outcomes worst --json`, Log's Ranked sessions section (`#sec-ranked`). The list is read when the fold opens and a session's full card (`agentctl-session-outcomes card`) when its row is clicked; neither re-reads on its own, since the rows change once a night |
| Log: actions | Log's Actions section (`#sec-actions`; `#actions` lands there). `/api/actions?hours=N` (`src/feed.rs`; default 24, 1 to 168) is hub-core's `actions::gather`, the same reader as `hub actions` and the briefing's digest. The page (`src/index.html`) is markup only; everything else is a file under `static/`, compiled in with `include_bytes!` and served at `/static/<name>` behind sign-in (`src/assets.rs`). The scripts share one global scope and load in order: `ui.js` (the shared helpers every tab uses: `api`, `post`, `coalesce`, the formatters `clock`, `when`, `dur`, `pct`, `secs`, `tile`, `paint` for a keep-your-place render, `poll` for a tab whose source pushes nothing and `pushed` for one whose files do), `md.js` (the markdown renderer: it escapes everything before adding markup, allows only http(s) links, and renders transcript text, plans, asks and rundowns), `charts.js` (swimlanes, column charts, the hover tooltip, meters, bucket and series colours), `app.js` (the Sessions tab, the tab switch and the event stream), `waiting.js` (the answer cards), then one file per board tab, `home.js` and `outbox.js` first. Each tab registers `TABS.<name> = { show(), onEvent(ev) }`; the page calls `show` when the tab opens and passes every SSE message to `onEvent`. A tab can be opened directly with its name as the hash, e.g. `#sessions`, `#actions` or `#jobs`; a retired name (`#watch`, `#shepherd`, `#board`, `#waiting`) lands on its new tab.

Every asset is linked as `?v=<version>`, a hash of the page and every asset, so a browser keeps it for a year (`immutable`) and a new build is a new URL; the page itself is `no-cache`. Pages carry a CSP that allows no inline script and nothing from another origin, and every response gets `nosniff` and `Referrer-Policy: same-origin`. The fonts are Inter and JetBrains Mono, self-hosted as latin-subset woff2 in `static/fonts/` with their OFL licences beside them; the sign-in page keeps the system fonts, since the font files are behind sign-in.

Load: while the browser tab is hidden, SSE messages and poll ticks only mark the page behind, and it refetches once (a resync) when it comes back into view. Sessions and Log refetch their fleet-state and shepherd files on events only while open, and once on opening after a change. Infra, Jobs and Fleet re-read on their timer only while open and visible.

Only a target that is a live agent right now accepts input, so the API cannot be aimed at an arbitrary pane.

## Auth

The page can type into live sessions, so a network allowlist is not enough. A signed-out visit shows one button, Sign in with Forgejo. It starts the OAuth2 authorization-code flow against your Forgejo; if the browser already has a Forgejo session there is nothing to type, otherwise Forgejo shows its own login form (which Bitwarden already fills).

On return agent-web exchanges the code for the user's Forgejo login and checks it against an allowlist (`AGENT_WEB_ALLOWED_USERS`, default `kblack0610`). A match gets an opaque session id in an HttpOnly cookie, valid 90 days. Sessions are stored in `~/.config/agent-web/sessions.json` (0600), so a restart signs nobody out. `POST /logout` revokes the session. `/healthz` is the only route that needs no session.

| Setting | Where | Default |
|---|---|---|
| OAuth client id and secret | `~/.config/agent-web/oauth.json` (0600), also kept in the Bitwarden vault | none, agent-web will not start without it |
| `AGENT_WEB_FORGEJO_URL` | env, Forgejo base URL | required |
| `AGENT_WEB_BASE_URL` | env, the URL agent-web is served at; the OAuth callback is `<base>/oauth/callback` | required |
| `AGENT_WEB_ALLOWED_USERS` | env, comma separated Forgejo logins | `kblack0610` |

To recreate the OAuth app: Forgejo -> Settings -> Applications -> OAuth2, confidential client, redirect URI `<base>/oauth/callback`, then write `{"client_id": ..., "client_secret": ...}` to `oauth.json`.

The two Forgejo calls (token exchange, `GET /api/v1/user`) run through `curl` with the secret on stdin, so no HTTP client library is linked in.

## Run

```sh
cargo build --release      # the dotfiles installer does this (build_local_rust_tools)
systemctl --user enable --now agent-web   # unit lives in the private overlay
```

`AGENT_WEB_ADDR` sets the listen address (default `0.0.0.0:8790`). The cluster ingress that fronts it is defined in home-config `apps/agents`.

To look at a change without touching the live service, run a second instance against a throwaway config dir with a hand-made session, then open `http://127.0.0.1:8799/#sessions` with the cookie `agent_web=dev`:

```sh
d=$(mktemp -d); mkdir -p $d/agent-web
echo '{"client_id":"x","client_secret":"x"}' > $d/agent-web/oauth.json
echo '{"dev":{"user":"me","expires":4102444800}}' > $d/agent-web/sessions.json
XDG_CONFIG_HOME=$d AGENT_WEB_ADDR=127.0.0.1:8799 AGENT_WEB_FORGEJO_URL=http://x AGENT_WEB_BASE_URL=http://127.0.0.1:8799 ./target/debug/agent-web
curl -s -b agent_web=dev 127.0.0.1:8799/api/watch | jq '.state.sessions | length'
```

To render Sessions from a chosen `state.json`, also set `HOME=$d` and put the file at `$d/.local/state/fleet/state.json`. agent-web then watches under that home; without `$d/.claude/sessions` and `$d/.claude/projects` it logs "cannot watch" and the header says live updates are off.

The static files are compiled in, so restart the instance after editing one.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Header says "live updates off"; the log has `cannot watch ...: OS file watch limit reached` | The user's inotify watches (`fs.inotify.max_user_watches`) are used up by another program. On 2026-11-03 it was Unity's ILPP runner watching a Unity project checkout whose `.git` held 1.5M empty LFS dirs. Raising the limit does not help: a recursive watcher takes the new room too | Find the holder: for each pid, count the `inotify` lines in `/proc/<pid>/fdinfo/<fd>` of its `anon_inode:inotify` fds. Free watches at the source; agent-web picks them up on its next retry, no restart |
