# agent-web

A web view of the Claude agents running in tmux on this machine. From a phone or another computer you can read any session's transcript or live screen, type into it, press the keys a permission prompt needs, and answer the headless `agent-ask` queue. The board tabs show the tabs of the tmux hub board (`hub:board`, `Prefix+i`) with charts: the same tabs in the same order (`hub_core::layout`), from the same hub-core readers.

It reuses agent-panel's library (the pane x `~/.claude/sessions` join, the tmux wrappers), so the web list and the `Prefix+g` chooser always agree on what an agent is.

A new tab or section follows `../docs/dashboards.md` (the dashboard standards; the tab layout is `hub_core::layout`).

## How it works

| Piece | Source |
|---|---|
| Daily's outbox (`#daily/outbox`) | `/api/outbox` (`src/outbox.rs`). GET is hub-core's `outbox::read`, the reader the hub TUI's Daily outbox view (`o`) shares: `notes outbox show --json` (the `## Outbox` items as text, their hash, how many wait, and the intake tag table) and today's intake steps from `notes log --day <today> --json` (filed, dup, planned, left, refused; newest first, counted). PUT `{base, text}` pipes the text through `src/cli.rs` (the one place agent-web spawns `notes` with stdin) to `notes outbox put --base <hash>`, the one writer: it replaces the items under the outbox lock if the hash still matches, else exits 3 and the handler answers 409 with the current doc (a CLI error is a 502; a control character or over 64 KB is a 400). The view (`static/outbox.js`, drawn in the note's place on Daily, reached from Daily's nav; the retired `#outbox` lands here) is one textarea that saves 1.5s after you stop typing; the line the cursor is on is held back while it is new, until Enter, Send (Ctrl+Enter) or leaving the box, so the sweep never files half a sentence. The sweep (`agentctl-inbox-triage --watch`, 30s after the last write) takes the lines it files out of the file; a write of `outbox.md` or `ingest.jsonl` is an SSE `outbox` event, the page re-reads, and `mergeLines` drops from the box only the lines the sweep took, keeping what you typed since. Reads and writes run one at a time, and a 409 merges and saves again. Handled today lists each step with its time, row id and project link, a left or refused line with its why. A folded Tags list under the box is that tag table (`notes outbox tags`), so the page lists no tag of its own |
| Home tab | `/api/home` (`main.rs` `home_board`) is hub-core's `home::build`, the join the hub TUI's Home draws, over `state.json` (its asks read live through the one typed `hub_core::boards::Ask` reader, `boards::state`, and each ask row carries its whole record as `need.ask`), agent-queue and the Infra tab's cached Prometheus answer: the card grid first (`/api/home/cards`: the Needs you card, then a card per tab), VITALS under it, then NEEDS YOU (asks, sessions waiting on you, waiting queue items, human-sheet rows, red nightlies, `cc:red_now`, a stopped dispatch; one row per tmux session, in `hub_core::home::needs` rank) and PROPOSALS, one row per stream (`hub_core::proposals::by_stream`: stream, project, newest, oldest, count; a click searches `stream:=<name>` and opens that stream's records under it, a second click clears it). There is no Running list: the Queue tab holds every running item (`#home/running` lands on it, `layout::MOVED`), and a card's zero-count chips are dropped by `Card::drawn`. Home is a glance, so each list sends `hub_core::home::SHOWN` rows: Needs you and Proposals, which no other tab lists whole, a page under the shared pager (`npg` and `pg`), and `/api/home` keeps each row named in `nopen` (the opened Needs you rows, `<kind>:<id>` by commas) under the page it sends, so a rerank never takes an answer being typed off the page. Needs you is the shared table (`impl Row for Need`, `static/table.js`): rank, kind, project, waited (exact, the time in ISO on hover), holds and what, with `q`, `s`, `sort` and `dir` in the URL and on `/api/home`, which answers the filtered `needs` with `table`, its controls and whole-list count; nothing else that reads Home's needs is filtered. A row's kind is `home::NeedKind` (a session's from the `dialog` that `boards::state` reads from its transcript), the `kind:` term by its slug (`kind:ask`, `kind:turn`) and a chip by its label; a chip with no rows is left out. `NEED_KINDS` in `static/waiting.js` labels a kind and its stripe (categorical hues for the dialog kinds; amber and red only for blocked and failing, dashboards rule 5). A click on a row opens its record under it: an ask or an open dialog its answer card (`static/waiting.js`), answered in place, anything else a plain card with a way to it. `#home/ask/<id>`, the link an `ask:<id>` page carries, opens that ask's card and scrolls to it; an ask no longer waiting says it was answered or withdrawn. A typed reply survives a refresh (`keepTyping`), and a refresh repaints around the search box or a dropdown in use. It re-reads on the fleet state, queue and asks events and every 60s while open (Prometheus has no push). A search keystroke or sort in Proposals reads `GET /api/home/proposals` instead (`proposals::list`: agent-propose alone, the rows, heading and table controls under the same keys, laid over the Home the page holds), because `/api/home` took about 1.6s at load 20 and agent-queue's `list` (0.45s) and `stats` (1.0s) are most of it; if that read fails the page falls back to the full one, which shows the error. `#waiting` and `#asks`, the retired Waiting tab, land here. A Needs you To do row from a human sheet closes on its card (`static/home.js` `sheetClose`): done with a proof or why it is unverified, or dropped with why, the same kinds as the Board form (`CLOSE_HOW` in `ui.js`), read fresh off `/api/board` by its row id and written through the Board's `POST /api/board`; a row with no id opens the Board instead. |
| Home cards | `/api/home/cards` (`src/cards.rs` `page`) is the cards of `hub_core::cards::ORDER` but Main red (`PAGE_SKIPS`: its repos are Needs you's red rows, and the grid keeps to the first phone screen): Needs you over Home's read (`cards::needs`), then hub-core's `cards::grid`, one card per tab, each from that tab's own reader (done today from the phone section's count, health over the Infra read, ci from `ci.glance`, sessions, queue with the pipeline gauges, the board Home keeps, alerts, costs, releases, schedules, projects) run together; a read that fails gives its card no data and the error, never an all-clear. Its own read beside `/api/home`, because eleven readers and a second Home build (`home_read`) would slow the page's main answer, so the Needs you card and the table under it are two reads and can differ by an event; `static/cards.js` `cardHtml` draws each card for Home's grid, and `packCards` packs the grid so each card starts one gap under the card above it in its column, not under the tallest card of a row; two across and compact on a phone (`app.css`), checked by `tests/agent-web/phone/render.mjs`. |
| Widget document | `/widget.json` (`src/widget.rs` over `hub_core::widget_doc`): Home's cards (`src/cards.rs` `read`: Needs you and Main red, `cards::needs` and `cards::main_red` over Home's read, then the grid Home draws) as a [Tilecast](https://git.kennethblack.me/kblack0610/tilecast) widget document (its `docs/format.md`), for the native widget app. One section per card, in `?cards=` order, or with no `?cards=` every card in Home's order (Needs you, Main red, then the grid: done, health, ci, sessions, queue, board, alerts, costs, releases, schedules, projects; `?cards=infra` still names Health): `big` and `unit` a metric, `bar` a bar, `parts` pills, `first` rows, a failed reader a `bad` section saying NO DATA. Taps open the card's tab under `AGENT_WEB_BASE_URL`. `tests/agent-web/tilecast-schema.sh` checks it against the format's schema at a pinned commit, in the CI rust job. |
| Widget push | `src/push.rs`: with an https `AGENT_WEB_BASE_URL` the document names `<base>/widget/push-register`, where the app POSTs its UnifiedPush endpoint (DELETE when its widget goes). `agent-mqtt-publish` pokes `POST /widget/push-send` after every status write and watch change; a poke sends "fetch now" to every endpoint only when what the cards draw changed (`widget_doc::Document::content_key`), at most once every 30 s. A 429 or 5xx from a distributor holds sends for its Retry-After seconds, else 60 s doubling to 1 h, reset by a send no distributor throttled; `push.json` then carries `retry_after` and `next_at`, and the `agent-web-push-ok` watch trips on a failure that lasts. See Home-screen widget below. |
| Widget setup | `/widget/setup` (`src/setup.rs`, `src/setup.html`), behind the session sign-in, never the widget key; a signed-out visit goes to `/`. An Add to Tilecast link, `tilecast://add?url=<base>/widget.json&auth=bearer&key=<key>`, the same link as a QR (qrcodegen, drawn as inline SVG) for setting up from a computer, and New key: `POST /widget/setup/new-key` (same-origin `Origin` only) writes a fresh 48-hex key to `widget.token` (0600, created when missing), so every phone on the old key stops until it is added again. The nav's Phone widget link opens it. |
| Queue tab | agent-queue, the one intake for agent work (`~/.config/agentctl/QUEUE.md`), and the only writer of `~/.agent/queue`, so every route shells out to it with plain arguments (`src/queue.rs`): `GET /api/queue` is the kept `agent-queue list --json --state all --since <6 days ago>` (every active item plus the last week's finished ones, filtered in process for every other view of it: today's, the tab's, the active ones), `POST /api/queue` is `add --from human` with the task on stdin (an urgent or high plan item starts its session at once, inside agent-queue), `/api/queue/cancel` and `/api/queue/bump` are `cancel` and `bump`, and `/api/queue/projects` is the names in `project-map.json`. agent-queue's stderr comes back as the 400 the page shows. `/api/queue/stats` is `agent-queue stats --json` worded by hub-core (`Stats::line`, one line: finished since the window began, the typical wait and time to a PR), shown above the sections under at most three of the verdict's banners (`queue_verdict::worst_first`, red over amber, each with an open link to the section or page it names). `/api/queue/candidates` is `hub_core::queue::candidates`, which reads the snapshot each real `fleet-dispatch run` pass writes (`~/.local/state/agentctl/dispatch/candidates.jsonl`, the pass's `suggest --json`): every ranked row on the shared table (`Candidate` is a `table::Row`; its view keys are `cq`, `cs`, `csort`, `cdir`, `cpg`, so it sits under the queue's own), searched, faceted by project and by each reason a row is blocked, and sorted over every row; the table pages at 30 (`candidates` in hub-core `layout::PAGE_ROWS`), and `as_of` is the file's time, worded per answer so it names the day once old. The rows are read only while its fold is open (on opening it with no rows held, on showing the tab with it open, on a view change, on the snapshot's `candidates` event and after a promote, which drops its own row from the file); shut drops the rows. `?counts=1` answers the heading's counts only (total, auto, urgent blocked, as of), read once the table has painted on show, on the `candidates` event (the snapshot's directory is watched) and after a promote, never on a queue event; both share one parse, kept per write of the file (its mtime and inode), so a keystroke re-reads nothing, a failed read is a 400 with hub-core's words and a dead parse task a 500, and the heading says the error, shut or open; Promote finds its row by its rank (unique in a snapshot) and posts the board's Start to `POST /api/board` (`fleet-dispatch promote`). Each card names its harness and model alias (`Item::harness_label`: the item's `agent`, else claude). The items are one shared table per state (hub-core `QueueRow`, `queue::Section`), drawn as sections in this order: Needs you, Stuck, Running, On a PR, Up next (`QueueRow::section()` puts each item in exactly one; a stuck item leaves the section of its state for Stuck). `GET /api/queue` answers `{table, sections:[{id, title, pre, items, table}], needs_you, done_today, cancelled_today, sel}`: the top `table` is the bar (the project and other facets and the one search `q`, `s`, shared by every section), and each section's own `table` is its view under the key prefix `nd`, `sk`, `rn`, `pr`, `nx` (`sort`, `dir`, `pg`), so sorting or paging one section moves no other. Each section shows only its own columns (`Q_COLS` in `static/queue.js`, every key a `QueueRow::COLUMNS` name; `assets.rs` checks that): Needs you title, project, waited, pr; Stuck title, project, why, for; Running title, project, run, pr; On a PR title, project, age, pr, waiting on; Up next #, title, project, priority, waited. A section pages at its `layout::PAGE_ROWS` entry (`queue/needs` and `queue/stuck` 8; `queue/running`, `queue/pr` and `queue/next` 6), the search and facets still reaching every row on the server, and a link to an item (`#queue/<slug>`) asks with `sel` for the page of its section that holds it. Finished and cancelled items are not on this tab: a line links to `#log/work` with today's counts, and a link to a finished item opens it as an Opened card from `sel`. The old ids keep working through `layout::MOVED` (`queue/table` and `queue/waiting` -> `queue/needs`, `queue/review` -> `queue/pr`, `queue/queued` -> `queue/next`, `queue/done` -> `log/work`, `home/running` -> `queue/running`) and `?s=<chip>` still narrows. The title cell is a record cell (ui.md rule 9, `rec2`): the title on line one over a muted line with the state's reason, the no-proof flag and the note (the slug when there is none), each one line cut with an ellipsis, the whole on hover and in the opened row. The opened row ends with a History fold, shut at first: opening it reads `/api/queue/history?slug=` (`queue::history`, hub-core `item_history` over `notes log --item <slug> --days 30 --json`), the summary says the attempts (each move to running) and steps, and the body the last 20 steps, one line each; shutting drops the read. Candidates follow, shut, so the page builds none of their rows, their heading from the counts read; each `/api/agents` row carries `items`, the queue items in that pane (hub-core `with_items`, fleet-sessions' `item_of` rule: an item whose `sessions` holds the pane's Claude session id, as an item added by hand records, or whose `session` names its tmux session, narrowed to the `window` it recorded), and that is how a card finds its panes. Open session shows when that is one pane; an item from before `window` existed can share `hub:dotfiles` and find several. A card carries what its session needs: the dialogs open in its panes and the pending asks they filed, answered as on the Waiting tab. An item with several panes shows every dialog and ask from them, each labelled with its pane. A waiting item with neither says `Waiting on a prompt in its window` and names the tmux session, or `No live window` when no pane is left. The tab opens on the flow strip from `/api/flow`, read only while the strip shows (the tab open and, on a phone, its Pipeline fold open: rule 10) (`flow.js` draws it; `hub_core::flow::Strip`, the one the hub TUI draws, over the live queue and the 30s-cached `agent_chain_*` gauges in `src/pipeline.rs`): inbox, agent backlog, queued, running, needs you, done 24h and drain, each chip a link to the Queue's section for it (agent backlog to Board), the step past its age bound amber, a `graph` link to Grafana's Agents / Overview (`kb-agents-overview`) when `CC_GRAFANA_URL` is set, and `-`, never 0, for a count the gauges did not return. A chip opens the section it counts (`#queue/<section>`, `flow::Target.section`), except done 24h, which opens Log; a pick opens its detail with at most five of its problems, each with an open link. Home draws the same strip from `flow` in `/api/home`. |

## Auth

The page can type into live sessions, so a network allowlist is not enough. A signed-out visit shows the button Sign in with Forgejo, plus a key form when `login.key` exists (below). The button starts the OAuth2 authorization-code flow against your Forgejo; if the browser already has a Forgejo session there is nothing to type, otherwise Forgejo shows its own login form (which Bitwarden already fills).

On return agent-web exchanges the code for the user's Forgejo login and checks it against an allowlist (`AGENT_WEB_ALLOWED_USERS`, default `kblack0610`). A match gets an opaque session id in an HttpOnly cookie, valid 90 days. Sessions are stored in `~/.config/agent-web/sessions.json` (0600), so a restart signs nobody out. `POST /logout` revokes the session. `/healthz` and the assets under `/static/` need no session, and `/widget.json` and the two push routes also open with the widget key; every other route needs one.

The OAuth button needs Forgejo up, so the sign-in key is the way in when it is down. `POST /login/key` compares the typed key with `~/.config/agent-web/login.key` in constant time and, on a match, starts the same 90-day session for the first name in `AGENT_WEB_ALLOWED_USERS`: whoever holds the key is that user, so keep the list order. There is no lockout on wrong keys, because a key of 32 or more characters cannot be guessed and a lock any visitor could trip would shut the owner out during the outage the key exists for. The audit log records `signin.started` and `signin.refused` with `method: key` (a refusal has the actor `login-key`).

### Input at the boundary

- Every write must come from these pages. `same_origin` in `main.rs` refuses a POST, PUT or DELETE whose `Origin` is not `AGENT_WEB_BASE_URL`, and one that carries the session cookie with no `Origin` at all. A write with neither (the Tilecast app, `agent-mqtt-publish`) goes on to its route's key check.
- A JSON body is a `#[serde(deny_unknown_fields)]` struct, so a mistyped field gets a 422 instead of falling back to its default. Query structs stay lenient.
- Free text that reaches a pane, an ask or a note goes through `cli::plain_text`: newlines and tabs only, no other control bytes, and a size cap (`MAX_SEND` 64 KB, `MAX_ANSWER` 8 KB, `outbox::MAX_TEXT`, `focus::MAX_NOTE`). Ids, slugs, keys and names are checked against an allowlist or the live state before any command runs, and a command gets them as argv, never through a shell; free text goes after `--` wherever the CLI takes one. `guard_writes` pins `DefaultBodyLimit` to `audit::BODY_MAX`, the same 2 MiB as axum's default, so the two stay one constant.
- A new field goes through the validator in the hub-core argv builder for its CLI (`tasks::argv`, `queue::add_argv`). Those validators are the pattern; there is no derive-validation crate.

## Home-screen widget

The phone's home-screen widget is the Tilecast app, which reads `/widget.json`; the HA Companion Template widget (dashboards.md, Phone widget) is the maintained second option.

For the Tilecast app, no key is copied by hand: on the phone open `<base>`, sign in, tap Phone widget in the menu (`/widget/setup`), then Add to Tilecast; from a computer, scan its QR with the phone. Lost a phone: New key on the same page, then Add to Tilecast again on each phone you keep.

Each hit the key opens rewrites `~/.local/state/agent-web/widget.json` (`at` in epoch seconds, the card ids shown, `"client": "tilecast"`, the user agent and the app version from its `Tilecast/<version>` user agent); a signed-in browser that opens `/widget.json` without the key is not recorded, so it cannot hide a dead widget, but any client using the key URL is. The Sentinel watch `agent-web-widget-fresh` trips when that file is missing or older than 2 hours.

Each such hit is also appended as one JSON line to `~/.local/state/agent-web/widget-hits.jsonl`, the same fields plus `route` and `ip`: Cloudflare's `CF-Connecting-IP`, else the first `X-Forwarded-For` entry, else `-`. A hit through the tunnel logs the client's public address, which Cloudflare's edge sets; a LAN hit through the ingress logs Traefik's service load balancer pod (10.42.x), the same address for every LAN client; a direct hit on port 8790 logs `-`. At the app's refresh of about 35 seconds (measured 2026-11-18) the log grows about 450 KB a day, so logrotate rotates it past 2 MB, about four days of hits, and keeps five: `widget-hits.jsonl.1` plain, the older ones gzipped (`~/.config/agentctl/logrotate.conf`, run nightly by the `log-rotate` step of the `gc` runner). The Sentinel watch `agent-web-widget-foreign` pages while any hit in the last 24 hours comes from a public address with a user agent that does not start with `Tilecast/`, the phone widget app's, so a leaked key shows up the first time another client uses it through the tunnel. LAN and local hits never trip it: they are our own machines, and an agent's curl test from the LAN tripped it on 2026-11-18. So a leaked key used from the home LAN goes unpaged; the log still has it. It catches only a careless client: whoever holds the key can send a `Tilecast/` user agent, and off the tunnel can write both address headers, so a hit's `ip` is only as true as the hop that set it. The watch reads `widget-hits.jsonl.1` and the live file, so a rotation never hides the last day.

Push: the Tilecast app registers for pushes on its own when the document names `push.register` and a UnifiedPush distributor (the ntfy app) is on the phone; nothing is set up here. The push routes open with the widget key only, never a session cookie, so no other site can register an endpoint through a signed-in browser. `~/.local/state/agent-web/push-endpoints.json` holds the endpoints (https on a DNS name, never an IP address, `localhost` or `.local`; at most 16, the oldest dropped first), written only by agent-web. Each send rewrites `~/.local/state/agent-web/push.json`: `at` and how many `endpoints` there were and were `sent`, `failed` or `dropped` (the distributor answered 404 or 410, so the endpoint is removed), with the first failure's `error`. A send POSTs `1` to each endpoint through `curl` with the URL on stdin, 10 s each. A change no endpoint took goes again on the next poke, 30 s later at the soonest; past that the app's 15 min backstop covers a missed push. With no endpoint registered a poke reads nothing.

| Problem | Fix |
|---|---|
| The widget shows `unauthorized` | The app holds a key that is not the one in `widget.token`: tap Add to Tilecast again on `/widget/setup`. |
| The widget waits for its 15 min refresh after a change | `jq . ~/.local/state/agent-web/push-endpoints.json`: no endpoint means the app never registered (no distributor linked on the phone; `adb logcat -s TilecastPush` says why). An endpoint but an old `push.json` `at` means no poke came: `curl -X POST -H "Authorization: Bearer $(cat ~/.config/agent-web/widget.token)" localhost:8790/widget/push-send` should answer 202. A `push.json` with `failed` says the distributor's answer in `error`; `journalctl --user -u agent-web | grep push` has each failure. |
| A card says NO DATA | That card's reader failed; the error is on the card, and the same card on Home shows it too. |
| `agent-web-widget-fresh` tripped | No hit with the key in 2 hours: `jq . ~/.local/state/agent-web/widget.json` says when the last one was. Tap the widget; if that writes a new `at`, the app's timer stopped (battery optimization on the widget app is the usual cause), and if it does not, `journalctl --user -u agent-web | grep 'widget refused'` says why: `key does not match` (the app holds an old key: Add to Tilecast again), `no key in the URL` (the request carried no `?t=` and no bearer header), `no key set on the server` (`widget.token` is missing or empty), and no line at the tap means the app cannot reach the base URL. A healthy widget with a stale file means the write failed: `journalctl --user -u agent-web | grep 'widget hit not recorded'`. |
| `agent-web-widget-foreign` tripped | Something other than the Tilecast app used the key from off the LAN. `jq -c 'select(.ua \| test("^Tilecast/") \| not)' ~/.local/state/agent-web/widget-hits.jsonl` lists each hit with its time, route, IP and user agent, LAN ones too. A test from the LAN never trips it; your own test from off the LAN is harmless and clears a day later. A public address or app you do not know means the key leaked: rotate it (Widget key, above) and give the app the new one. To trust another app, widen the `test()` pattern in `~/.agent/watches/agent-web-widget-foreign.yaml`. |

The two Forgejo calls (token exchange, `GET /api/v1/user`) run through `curl` with the secret on stdin, so no HTTP client library is linked in.

## Run

```sh
cargo build --release      # the dotfiles installer does this (build_local_rust_tools)
systemctl --user enable --now agent-web   # unit lives in the private overlay
```

`AGENT_WEB_ADDR` sets the listen address (default `0.0.0.0:8790`). The cluster ingress that fronts it is defined in home-config `apps/agents`.

A stop (SIGTERM, so every rebuild's restart) takes no new connection, ends the live-update streams and answers the requests in flight for up to 30s before it exits. The journal gets one `agent-web: <METHOD> <path> ua=...` line for each request that failed (with the error), took over 2s (`slow`), or was dropped before its handler answered (the client went away or a restart cut it); the time is to the answer's head, so a body cut while it streams is not logged, and a request that answered in time logs nothing.

To see it, `agent-web-shot --base http://127.0.0.1:8799 --out <dir> releases releases/apps/binks` saves each page as a PNG from a headless scratch Firefox (`--width 390` for a phone, `--scheme dark` or `light` for one color scheme). ## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Every save or action fails with `cross-origin request refused` (403); the journal has `agent-web: POST /api/... refused: origin ...` | The page was opened at a URL other than `AGENT_WEB_BASE_URL` (a LAN address, another hostname), or a proxy rewrote `Origin` | Open it at the base URL, or set `AGENT_WEB_BASE_URL` to the URL it is served at and restart |
| The sign-in page has no key form | `login.key` is missing, empty or under 32 characters | Mint it as in the Auth table; no restart |
| A tab says `agent-web did not answer /api/...` | No answer came back: agent-web was restarting or down, or the connection broke | `journalctl --user -u agent-web -n 200 \| grep 'agent-web: '`: a `dropped before it answered` line with the browser's `ua` says the request was cut, a `failed` line carries the handler's error, a `slow` line the time; no line at all means the request never reached agent-web (check the ingress logs in home-config `apps/agents`) |
| A tab sits on "Loading..." for seconds; the journal has `GET /api/<path> ... slow` lines (the `agent-web-slow` watch trips) | That handler runs a CLI on every request instead of a kept read: on 2026-11-18 `/api/board` ran agent-queue twice (14 to 19 s) and `/api/fleet` ran judge-eval (6 to 12 s) | Put the read behind `src/cache.rs` (a `ReadCache`, or an `EventCache` its file events outdate) and add it to `warm`; prove it with `agent-web-shot --time --budget 1000 --every-tab` on a dev instance of the old and the new binary |
| Header says "offline since HH:MM" with Retry | The browser's event stream to `/api/events` dropped at that time: agent-web restarted or stopped, or the network or proxy cut it. The page shows what it last read. EventSource reconnects by itself after a drop but not after an error answer such as a proxy's 502 | `systemctl --user status agent-web`; once it is up, press Retry. The pill says "catching up" until the sessions read lands, then clears |
| Header says "live updates off"; the log has `cannot watch ...: OS file watch limit reached` | The user's inotify watches (`fs.inotify.max_user_watches`) are used up by another program. On 2026-11-03 it was Unity's ILPP runner watching a Unity project checkout whose `.git` held 1.5M empty LFS dirs. Raising the limit does not help: a recursive watcher takes the new room too | Find the holder: for each pid, count the `inotify` lines in `/proc/<pid>/fdinfo/<fd>` of its `anon_inode:inotify` fds. Free watches at the source; agent-web picks them up on its next retry, no restart |
| Header says "live updates off" for every path; the log has `cannot start the file watcher: Too many open files` | The user's inotify instances are used up (`sysctl fs.inotify.max_user_instances` shows the limit): each process that watches files holds one or more | Count them: `find /proc/*/fd -lname anon_inode:inotify 2>/dev/null \| cut -d/ -f3 \| sort \| uniq -c \| sort -rn \| head`. Stop the holder; agent-web makes its watcher on the next retry, adds any project made meanwhile and refreshes open pages, no restart |
| `render.mjs` fails with `fixture columns [...] match no hub-core table; nearest (lead X) lacks [...]` | A hub-core table gained or lost a column and `tests/agent-web/phone/fixtures.mjs` still has the old list, so its rows get no phone roles (the lead check would read `widest-text`) | Add the named columns to that fixture's `table(...)` list in hub-core's COLUMNS order, and the row field the page draws for each (an `undefined` cell names a missing one) |
