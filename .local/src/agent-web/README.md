# agent-web

A web view of the Claude agents running in tmux on this machine. From a phone or another computer you can read any session's transcript or live screen, type into it, press the keys a permission prompt needs, and answer the headless `agent-ask` queue. The board tabs show the tabs of the tmux hub board (`hub:board`, `Prefix+i`) with charts: the same tabs in the same order (`hub_core::layout`), from the same hub-core readers.

It reuses agent-panel's library (the pane x `~/.claude/sessions` join, the tmux wrappers), so the web list and the `Prefix+g` chooser always agree on what an agent is.

A new tab or section follows `../docs/dashboards.md` (the dashboard standards, and the layout both hub surfaces are moving to).

## How it works

| Piece | Source |
|---|---|
| Daily's outbox (`#daily/outbox`) | `/api/outbox` (`src/outbox.rs`). GET is hub-core's `outbox::read`, the reader the hub TUI's Daily outbox view (`o`) shares: `notes outbox show --json` (the `## Outbox` items as text, their hash, how many wait) and today's intake steps from `notes log --day <today> --json` (filed, dup, planned, left, refused; newest first, counted). PUT `{base, text}` pipes the text through `src/cli.rs` (the one place agent-web spawns `notes` with stdin) to `notes outbox put --base <hash>`, the one writer: it replaces the items under the outbox lock if the hash still matches, else exits 3 and the handler answers 409 with the current doc (a CLI error is a 502; a control character or over 64 KB is a 400). The view (`static/outbox.js`, drawn in the note's place on Daily, reached from Daily's nav; the retired `#outbox` lands here) is one textarea that saves 1.5s after you stop typing; the line the cursor is on is held back while it is new, until Enter, Send (Ctrl+Enter) or leaving the box, so the sweep never files half a sentence. The sweep (`agentctl-inbox-triage --watch`, 30s after the last write) takes the lines it files out of the file; a write of `outbox.md` or `ingest.jsonl` is an SSE `outbox` event, the page re-reads, and `mergeLines` drops from the box only the lines the sweep took, keeping what you typed since. Reads and writes run one at a time, and a 409 merges and saves again. Handled today lists each step with its time, row id and project link, a left or refused line with its why |
| Home tab | `/api/home` (`main.rs` `home_board`) is hub-core's `home::build`, the join the hub TUI's Home draws, over `state.json` (its asks read live from `agent-ask list`, `hub_core::boards::state`, so Home matches the questions panel), agent-queue and the Infra tab's cached Prometheus answer: VITALS first, under the card grid, then NEEDS YOU (asks, sessions waiting on you, waiting queue items, human-sheet rows, red nightlies, `cc:red_now`, a stopped dispatch; one row per tmux session, in `hub_core::home::needs` rank) and RUNNING (the queue's running items, the shared table `impl Row for Running` under keys `rq`, `rs`, `rsort` and `rdir`: item, project, board row, epic from the row's `#of/` tag, plan phase, ETA, PR and CI from the session's `state.json` row with `<pr>/checks` as the CI link, since; each cell links its home and a row opens its session page, else the queue item at `#queue/<slug>`). Each list shows its first `shown` rows (`hub_core::home::SHOWN`, sent in the answer); Running folds the rest under `+N more`, Needs you offers them on a `+N more` button and keeps an opened row on the page past the cap. Needs you is the shared table (`impl Row for Need`, `static/table.js`): rank, kind, project, waited (exact, the time in ISO on hover), holds and what, with `q`, `s`, `sort` and `dir` in the URL and on `/api/home`, which answers the filtered `needs` with `table`, its controls and whole-list count; nothing else that reads Home's needs is filtered. A row's kind is `home::NeedKind` (a session's from the `dialog` that `boards::state` reads from its transcript), the `kind:` term by its slug (`kind:ask`, `kind:turn`) and a chip by its label; a chip with no rows is left out. `NEED_KINDS` in `static/waiting.js` labels a kind and its stripe (categorical hues for the dialog kinds; amber and red only for blocked and failing, dashboards rule 5). A click on a row opens its record under it: an ask or an open dialog its answer card (`static/waiting.js`), answered in place, anything else a plain card with a way to it. `#home/ask/<id>`, the link an `ask:<id>` page carries, opens that ask's card and scrolls to it; an ask no longer waiting says it was answered or withdrawn. A typed reply survives a refresh (`keepTyping`), and a refresh repaints around the search box or a dropdown in use. It re-reads on the fleet state, queue and asks events and every 60s while open (Prometheus has no push). A search keystroke or sort in Proposals reads `GET /api/home/proposals` instead (`proposals::list`: agent-propose alone, the rows, heading and table controls under the same keys, laid over the Home the page holds), because `/api/home` took about 1.6s at load 20 and agent-queue's `list` (0.45s) and `stats` (1.0s) are most of it; if that read fails the page falls back to the full one, which shows the error. `#waiting` and `#asks`, the retired Waiting tab, land here. A Needs you To do row from a human sheet closes on its card (`static/home.js` `sheetClose`): done with a proof or why it is unverified, or dropped with why, the same kinds as the Board form (`CLOSE_HOW` in `ui.js`), read fresh off `/api/board` by its row id and written through the Board's `POST /api/board`; a row with no id opens the Board instead. |
| Home cards | `/api/home/cards` (`src/cards.rs`) is hub-core's `cards::grid`, one card per tab in a fixed order, each from that tab's own reader (sessions, queue with the pipeline gauges, alerts, infra, costs, releases, schedules, projects) run together; a read that fails gives its card no data and the error, never an all-clear. Its own read beside `/api/home`, because eight readers would slow the page's main answer; `static/home.js` `cardsHtml` draws it and `cardsLine` is the phone's one status line. |
| Queue tab | agent-queue, the one intake for agent work (`~/.config/agentctl/QUEUE.md`), and the only writer of `~/.agent/queue`, so every route shells out to it with plain arguments (`src/queue.rs`): `GET /api/queue` is `agent-queue list --json --state all` (active items plus today's finished ones), `POST /api/queue` is `add --from human` with the task on stdin (an urgent or high plan item starts its session at once, inside agent-queue), `/api/queue/cancel` and `/api/queue/bump` are `cancel` and `bump`, and `/api/queue/projects` is the names in `project-map.json`. agent-queue's stderr comes back as the 400 the page shows. `/api/queue/stats` is `agent-queue stats --json` worded by hub-core (`Stats::week` and `sitting_line`, the hub Queue tab's two lines), shown above the sections. `/api/queue/candidates` is `hub_core::queue::candidates`, which reads the snapshot each real `fleet-dispatch run` pass writes (`~/.local/state/agentctl/dispatch/candidates.jsonl`, the pass's `suggest --json`): every ranked row on the shared table (`Candidate` is a `table::Row`; its view keys are `cq`, `cs`, `csort`, `cdir`, so it sits under the queue's own), searched, faceted by project and by each reason a row is blocked, and sorted over every row; the page gets the first 30 with `more`, `call=1` asks for the rest, and `as_of` is the file's time, worded per answer so it names the day once old. The rows are read only while its fold is open (on opening it with no rows held, on showing the tab with it open, on a view change, on the snapshot's `candidates` event and after a promote, which drops its own row from the file); shut drops the rows. `?counts=1` answers the heading's counts only (total, auto, urgent blocked, as of), read once the table has painted on show, on the `candidates` event (the snapshot's directory is watched) and after a promote, never on a queue event; both share one parse, kept per write of the file (its mtime and inode), so a keystroke re-reads nothing, a failed read is a 400 with hub-core's words and a dead parse task a 500, and the heading says the error, shut or open; Promote finds its row by its rank (unique in a snapshot) and posts the board's Start to `POST /api/board` (`fleet-dispatch promote`). Each card names its harness and model alias (`Item::harness_label`: the item's `agent`, else claude). The items are one shared table (hub-core `QueueRow`, the hub Queue tab's columns): `#` (start order among ready items), title, project, priority, state, hold (an `after <slug>` hold links that item), from, in, wait, run, pr, row (the board row, linked), kind, size, acct, mode, plan, with a dropdown per facet; it opens on `active` (every item not done), with chips for needs you, running, on a PR, ready, held, done and all, and `GET /api/queue` carries `dispatch`, the line above the table saying whether dispatch is held and what it could start. The table draws the first `open_rows` rows (`TABLE_OPEN_ROWS` in `src/queue.rs`, 25) and a `+N more` button, the chips, search and filters still reaching every row on the server; the title cell is a record cell (ui.md rule 9, `rec2`): the title on line one over a muted line with the no-proof flag and the note (the slug when there is none), each one line cut with an ellipsis, the whole on hover and in the opened row. The opened row ends with a History fold, shut at first: opening it reads `/api/queue/history?slug=` (`queue::history`, hub-core `item_history` over `notes log --item <slug> --days 30 --json`), the summary says the attempts (each move to running) and steps, and the body the last 20 steps, one line each; shutting drops the read. Candidates follow, shut, so the page builds none of their rows, their heading from the counts read; each `/api/agents` row carries `items`, the queue items in that pane (hub-core `with_items`, fleet-sessions' `item_of` rule: an item whose `sessions` holds the pane's Claude session id, as an item added by hand records, or whose `session` names its tmux session, narrowed to the `window` it recorded), and that is how a card finds its panes. Open session shows when that is one pane; an item from before `window` existed can share `hub:dotfiles` and find several. A card carries what its session needs: the dialogs open in its panes and the pending asks they filed, answered as on the Waiting tab. An item with several panes shows every dialog and ask from them, each labelled with its pane. A waiting item with neither says `Waiting on a prompt in its window` and names the tmux session, or `No live window` when no pane is left. The tab opens on the flow strip from `/api/flow`, read only while the strip shows (the tab open and, on a phone, its Pipeline fold open: rule 10) (`flow.js` draws it; `hub_core::flow::Strip`, the one the hub TUI draws, over the live queue and the 30s-cached `agent_chain_*` gauges in `src/pipeline.rs`): inbox, board, queued, running, needs you, done 24h and drain, each chip a link to the Queue on that filter (board to Projects), the step past its age bound amber, a `graph` link to Grafana's Agents / Overview (`kb-agents-overview`) when `CC_GRAFANA_URL` is set, and `-`, never 0, for a count the gauges did not return. Home draws the same strip from `flow` in `/api/home`. The tiles still count from the items |
| Projects tab | Three inner tabs, Projects (the list), All rows (`#projects/all`, every project's rows) and Deliverables (`#projects/deliverables`), each label with its table's total once that tab is read; a bare inner id or section after `#projects/` is that inner tab, never a project, so a project named `all` opens as `#projects/<profile>/all`. Deliverables: `GET /api/deliverables` (`src/deliverables.rs`) is `hub_core::deliverables::build` over the one kept `fleet-bench epics --json` read (`src/epics.rs`: every project, kept 2 minutes because its forecast makes a read about 9s whatever project is asked for; the project pages share it), one row per open feature epic and a coverage line, taking `scope` (`<profile>/<project>`) and the table's `dq`, `ds`, `dsort` and `ddir` (a `d` prefix so it does not share the list's view keys); a click on a row opens the epic's project on its Build tab searched to that epic; a failed read shows its error. `/api/projects` (`src/projects.rs`) is hub-core's `projects::build`, the cards the hub TUI's Projects tab draws, each with the same `summary` line; it takes the table's `q`, `s`, `sort` and `dir` and answers the cards the view keeps with `table` (hub-core `impl table::Row for projects::Card`). The list is one table on `static/table.js`, a row per lab project: stage, version, prio, open, done, percent, pace (`pace`, rows closed in 28 days over 4), ETA, running, waiting, queued, in flight first, with state tiles in flight and waiting and dropdowns for profile and stage; the queue items no card claims fold under it. The list and the rows share the tab's URL query: the list owns it when nothing is open, the rows when a project is, so a click or Back clears it and a deep link keeps its own, and with a project open every card is read. A click on a row opens its project page: it reads `/api/projects/{name}/page` (hub-core `page::named_with`, the page the hub TUI's opened card prints, its chain taken from the kept epics read while the page's own CLIs run), then shows a header (the card, goal, Flow line, releases, alerts and a link to the next stage's checks) over an inner tab strip from hub-core `layout::PROJECT_PAGE` (mirrored as `PROJECT_PAGE` in `static/app.js`, checked by `assets.rs`): Overview (Needs you as shut folds by kind with a count, each linking where it is fixed; In flight; Systems as one table, a row per system with its percent, features, `standard` criteria, open rows and epics behind, a click opening Build filtered to it), Rows (that project's rows), Build (the Deliverables table scoped to the project), Stage (the next stage's checks, failing first) and Activity (Shipped, Timeline, Agent note). Task lines are never drawn on the page: they are Rows. `#projects/<name>` (or `<profile>/<name>`) opens Overview and `#projects/<name>/<inner>` that inner tab, so a `#p:` link on Daily still lands; every section has a `sec-p-*` id, so the sidebar outline lists them. All rows (`#board` and `#board?q=...` land there, the query kept) is the same rows view over every project; one DOM subtree moves between it and an opened project. Each inner tab keeps its own search across a strip click, and a link reaching All rows from an opened project leaves that project's search behind. A table draws its first 30 rows (`B_OPEN` in `static/board.js`) and the rest on its `+N more` button; a search reads every row on the server. The rows: every project's rows from `notes board --json` (`src/board.rs`, read through hub-core `sheet_view::feed`, the reader the hub TUI and `hub board --json` share), open in the sheet's sections then Done newest first, each with its section `label` on the first row of a run and its `when` (queue state and forecast day, or a closed row's day and PR); a closed row has no actions, and a join that failed shows in `errors`: the human sheet, the agent board and playtest of every profile. A profile's Focus rows are not listed: `tasks::feed` counts them, and All rows shows `Focus: <profile> <n> open` linking to Daily. `GET /api/board` takes `scope` (`<profile>/<project>`, as Jobs takes `name`) and the table's `q`, `s`, `sort` and `dir`, and answers the rows the view keeps with `table` (hub-core `impl table::Row for tasks::Row`, the same view the hub's rows use): one table on `static/table.js`, each row drawn as section, title with its area tag and the summary under it (hub-core `text::title`, what the title leaves out, with any id it led with), epic (its parent's title, a link to that row; `no epic` when it has none), priority, state, when, project, lane and id, at up to 1600px wide; with state tiles in progress, filed today (a row's `filed` date equal to the feed's `today`, so the CLI's clock decides), urgent, requested and done (closed rows only, by day and project, with their PR; a closed row's run is its day: `DONE 11-07 (12)`), dropdowns for section, epic, project, lane, priority and state, and `tag:` and `profile:` terms in the search. A click opens a row under itself with its whole text and actions. `POST /api/board` takes `{verb: add|start|done|drop|move|promote|demote|edit|tag, profile, project, lane, ...}` and runs the command hub-core `tasks::argv` builds, `notes ptask`, or for start `fleet-dispatch promote`, which queues the row as an item that waits for the human to be away (add carries priority, an optional version `--to` or playtest `--game`; done needs a proof or an unverified reason, drop needs `why` or the `dup` id; start, move, promote, demote and edit are refused on playtest; move names its target as `dest` and/or a version `to`; edit replaces the text and keeps the tags; tag takes space-separated `add` and `remove` words (Tags... on a row); an add to the human lane whose text is not yet `type(area): title` goes to that sheet's `## Inbox`, for the inbox triager). The table's head line counts the rows still waiting in the inboxes (each project's `inbox`). The page has no open-sheet action: a browser cannot open a local editor (the hub's `o` does). Every write but add passes the row's exact line (`--exact`), so a row changed on disk since the page read it matches nothing and writes nothing: notes' message comes back as a 409 and the page re-reads. A malformed write is a 400. Nothing watches the notes vault, so the tab reads when shown, after each write, on resync and on Refresh |

| Live updates | inotify on `~/.claude/sessions`, `~/.claude/projects` and each project dir (not below it), `~/.agent/asks`, `~/.agent/queue` (recursive, created if missing), `~/.local/state/fleet`, `~/.agent/shepherd` (its `.due`, `.lease`, `.pass` and `passes.tsv` refresh the Sessions shepherd line and overview, its `log.md` Log's Actions section), `~/.agent/shepherd/rundowns` (created if missing), `~/.agent/daylog`, agentctl's state dir (its `runs.jsonl`), `~/.agent/dispatch` and agent-notify's ledger dir `~/.local/state/agent-notify` and `~/.agent/audit` (created if missing; their `log` and `actions.jsonl` refresh Log's Actions section), pushed over SSE. Nothing polls. A path it cannot watch is logged and retried (10 s, doubling to 5 min); until then the header says "live updates off" |

The page (`src/index.html`) is markup only; everything else is a file under `static/`, compiled in with `include_bytes!` and served at `/static/<name>` behind sign-in (`src/assets.rs`). The scripts share one global scope and load in order: `ui.js` (the shared helpers every tab uses: `api`, `post`, `coalesce`, the formatters `clock`, `when`, `dur`, `pct`, `secs`, `tile`, `paint` for a keep-your-place render, `poll` for a tab whose source pushes nothing and `pushed` for one whose files do), `md.js` (the markdown renderer: it escapes everything before adding markup, allows only http(s) links, and renders transcript text, plans, asks and rundowns), `charts.js` (swimlanes, column charts, the hover tooltip, meters, bucket and series colours), `app.js` (the Sessions tab, the tab switch and the event stream), `waiting.js` (the answer cards), then one file per board tab, `home.js` and `outbox.js` first. Each tab registers `TABS.<name> = { show(), onEvent(ev) }`; the page calls `show` when the tab opens and passes every SSE message to `onEvent`. A tab can be opened directly with its name as the hash, e.g. `#sessions`, `#actions` or `#jobs`; a retired name (`#watch`, `#shepherd`, `#board`, `#waiting`) lands on its new tab.

Every asset is linked as `?v=<version>`, a hash of the page and every asset, so a browser keeps it for a year (`immutable`) and a new build is a new URL; the page itself is `no-cache`. Pages carry a CSP that allows no inline script and nothing from another origin, and every response gets `nosniff` and `Referrer-Policy: same-origin`. The fonts are Inter and JetBrains Mono, self-hosted as latin-subset woff2 in `../web-kit/` with their OFL licences beside them, served flat under `/static/` with the kit's `tokens.css`, `shell.css` and `kb-shell.js` (the shared site shell, see `../web-kit/README.md`); the sign-in page keeps the system fonts, since the font files are behind sign-in.

Load: while the browser tab is hidden, SSE messages and poll ticks only mark the page behind, and it refetches once (a resync) when it comes back into view. Sessions and Log refetch their fleet-state and shepherd files on events only while open, and once on opening after a change. Infra, Jobs and Sessions' Runners re-read on their timer only while open and visible.

Only a target that is a live agent right now accepts input, so the API cannot be aimed at an arbitrary pane.

## Auth

The page can type into live sessions, so a network allowlist is not enough. A signed-out visit shows one button, Sign in with Forgejo. It starts the OAuth2 authorization-code flow against your Forgejo; if the browser already has a Forgejo session there is nothing to type, otherwise Forgejo shows its own login form (which Bitwarden already fills).

On return agent-web exchanges the code for the user's Forgejo login and checks it against an allowlist (`AGENT_WEB_ALLOWED_USERS`, default `kblack0610`). A match gets an opaque session id in an HttpOnly cookie, valid 90 days. Sessions are stored in `~/.config/agent-web/sessions.json` (0600), so a restart signs nobody out. `POST /logout` revokes the session. `/healthz` is the only route that needs no session.

| Setting | Where | Default |
|---|---|---|
| OAuth client id and secret | `~/.config/agent-web/oauth.json` (0600), also kept in the Bitwarden vault | none, agent-web will not start without it |
| `AGENT_WEB_FORGEJO_URL` | env, Forgejo base URL | required |
| `AGENT_WEB_BASE_URL` | env, the URL agent-web is served at; the OAuth callback is `<base>/oauth/callback`. The unit reads it from `~/.config/agent-web/env`, which agent-notify also reads to link a page's `tmux:` and `ask:` refs here | required |
| `AGENT_WEB_ALLOWED_USERS` | env, comma separated Forgejo logins | `kblack0610` |

To recreate the OAuth app: Forgejo -> Settings -> Applications -> OAuth2, confidential client, redirect URI `<base>/oauth/callback`, then write `{"client_id": ..., "client_secret": ...}` to `oauth.json`.

The two Forgejo calls (token exchange, `GET /api/v1/user`) run through `curl` with the secret on stdin, so no HTTP client library is linked in.

## Run

```sh
cargo build --release      # the dotfiles installer does this (build_local_rust_tools)
systemctl --user enable --now agent-web   # unit lives in the private overlay
```

`AGENT_WEB_ADDR` sets the listen address (default `0.0.0.0:8790`). The cluster ingress that fronts it is defined in home-config `apps/agents`.

A stop (SIGTERM, so every rebuild's restart) takes no new connection, ends the live-update streams and answers the requests in flight for up to 30s before it exits. The journal gets one `agent-web: <METHOD> <path> ua=...` line for each request that failed (with the error), took over 2s (`slow`), or was dropped before its handler answered (the client went away or a restart cut it); the time is to the answer's head, so a body cut while it streams is not logged, and a request that answered in time logs nothing.

To look at a change without touching the live service, run a second instance against a throwaway config dir with a hand-made session, then open `http://127.0.0.1:8799/#sessions` with the cookie `agent_web=dev`:

```sh
d=$(mktemp -d); mkdir -p $d/agent-web
echo '{"client_id":"x","client_secret":"x"}' > $d/agent-web/oauth.json
echo '{"dev":{"user":"me","expires":4102444800}}' > $d/agent-web/sessions.json

```

To render Sessions from a chosen `state.json`, also set `HOME=$d` and put the file at `$d/.local/state/fleet/state.json`. agent-web then watches under that home; without `$d/.claude/sessions` and `$d/.claude/projects` it logs "cannot watch" and the header says live updates are off.

The static files are compiled in, so restart the instance after editing one.

To see it, `agent-web-shot --base http://127.0.0.1:8799 --out <dir> releases releases/apps/binks` saves each page as a PNG from a headless scratch Firefox (`--width 390` for a phone, `--scheme dark` or `light` for one color scheme). With a signed-in cookie (`--cookie agent_web=<value>`) and the site's base it shoots the live site, the proof `docs/dashboards.md` rule 14 asks for. `tests/agent-web/phone/render.mjs` is the other one: fixtures only, no server, and the checks CI runs.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| A tab says `agent-web did not answer /api/...` | No answer came back: agent-web was restarting or down, or the connection broke | `journalctl --user -u agent-web -n 200 \| grep 'agent-web: '`: a `dropped before it answered` line with the browser's `ua` says the request was cut, a `failed` line carries the handler's error, a `slow` line the time; no line at all means the request never reached agent-web (check the ingress logs in home-config `apps/agents`) |
| Header says "offline since HH:MM" with Retry | The browser's event stream to `/api/events` dropped at that time: agent-web restarted or stopped, or the network or proxy cut it. The page shows what it last read. EventSource reconnects by itself after a drop but not after an error answer such as a proxy's 502 | `systemctl --user status agent-web`; once it is up, press Retry. The pill says "catching up" until the sessions read lands, then clears |
| Header says "live updates off"; the log has `cannot watch ...: OS file watch limit reached` | The user's inotify watches (`fs.inotify.max_user_watches`) are used up by another program. On 2026-11-03 it was Unity's ILPP runner watching a Unity project checkout whose `.git` held 1.5M empty LFS dirs. Raising the limit does not help: a recursive watcher takes the new room too | Find the holder: for each pid, count the `inotify` lines in `/proc/<pid>/fdinfo/<fd>` of its `anon_inode:inotify` fds. Free watches at the source; agent-web picks them up on its next retry, no restart |
| `render.mjs` fails with `fixture columns [...] match no hub-core table; nearest (lead X) lacks [...]` | A hub-core table gained or lost a column and `tests/agent-web/phone/fixtures.mjs` still has the old list, so its rows get no phone roles (the lead check would read `widest-text`) | Add the named columns to that fixture's `table(...)` list in hub-core's COLUMNS order, and the row field the page draws for each (an `undefined` cell names a missing one) |
