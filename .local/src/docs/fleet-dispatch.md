# fleet-dispatch

`fleet-dispatch` (`.local/bin/fleet-dispatch`, tests `tests/unit/fleet_dispatch.bats`) starts, places and reaps the sessions that run queue items. This doc is its behaviour reference, kept beside the code so a change to the code and to this page is one PR. The queue's design, the item's fields, Admission, the harnesses, the fleet lease and the store sync are in `~/.config/agentctl/QUEUE.md` (the private overlay), which this page cites by section name. The writer of the queue: [agent-queue.md](agent-queue.md). The operator path: the `fleet-dispatch` skill.

`fleet-dispatch` keeps its gates (`claude-acct room`, load, holds) and `cmd_start`'s launch through `wt new` on the agent world (`tmux-world agents`, today `lab`), and reads the queue instead of the board.

- `run` starts the queue head before it looks at any board row, as many starts a pass as the gates allow (`DISPATCH_PER_PASS` caps it when above 0), reading the gates again before each start after the first. No gate reads presence. Items `from: human` start while the human is at the desk because they asked for them (the shepherd files a `#requested` board row instead, see QUEUE.md "Admission", which ranks first and then runs as a board item); items `from: board:` start under the same gates, here or away; presence only picks the pace target. A gate that holds the head item ends the pass: board rows never jump the queue.
- `start --item <slug>` launches by `mode`: oneshot runs its kind's entry skill (kinds.json `entry`, `/one-shot` when the kind names none) in bypass mode (`--pr-only` for a tier-3 item that is not `cleanup`; a kind whose `exit` is doc+ask or proof, and a `verify` item, open no PR), plan runs `claude --permission-mode plan '<task>'`. Both get `AGENT_QUEUE_ITEM=<slug>` in their environment and a brief that tells the session to land with `agent-land <N>`, which closes the item (a tier-3 PR item, which stops at its PR, parks it: `agent-queue set <slug> pr=<owner>/<repo>#<N>`, `agent-queue move <slug> review`, and reap closes it on the merge). The item gets `session: <server>:<tmux session>`, `account:`, `origin:` and `model:` and moves to `running/`. `start --brief` (a row by hand, or perf-round) claims the row, promotes it to an item and starts that, so every launch goes through an item. `start --resume <id> [--item <slug>]` re-attaches a running or waiting item to the restored session and puts `AGENT_QUEUE_ITEM` in its environment; `restore` passes the item whose `sessions:` lists the conversation (`agent-queue mine --sid`). A window joined into a live session records no `session:`, so reap goes by its `sessions:` ids.
- `session:` is the one record of a session: reap, the unit count (items whose `by` is `dispatch`; the pace target, `DISPATCH_TARGET_PRESENT` or `DISPATCH_TARGET_AWAY`, is also a budget of run units, a heavy item holds 2 and a light one 1, and a pass skips an item too heavy for the units left; when every runnable item is, the pass is NOOP), `fleet-sessions` and `cancel` read it. A bare name means the agent world (`tmux-world agents`, `lab`). There is no separate ledger.
- Urgent items and the human's asks run now (the human's rules, 2026-11-10 and 2026-11-18): critical work, and what the human asked for in the last day (an item from a `#requested` row, `DISPATCH_ASK_FRESH_H`), never waits behind a full fleet or the weekly pace; reserve no slots for them, since priority plus a turn-end park keeps every slot busy. A parked session (a `claude-acct park` ledger in `~/.agent/parked/`) holds no run unit. The first urgent item or fresh ask waiting only on this machine's units reserves the free ones (an item placed on a fleet worker still starts), and when they fall short the pass preempts: it parks one runner session for it (`why=preempt`) and a later pass unparks it. Budget (`why=budget`), agent (`why=park`) and the human's (`why=human`) parks are never touched. Victim order, retries, when it starts and unparks, the run log lines and `DISPATCH_PREEMPT`: fleet-dispatch skill, "Starting a session by hand"; code and tests: dotfiles #1727 (`preempt_for`, `unpark_preempted`; `tests/unit/fleet_dispatch.bats` "preempt:", "unpark:").
- `fill` runs inside `run` while fewer than `DISPATCH_LOW_WATER` (20) queue items are runnable (only when none are, at 0) and every gate passes; it promotes enough rows to reach the mark, whether or not the human is here, and the same pass starts what the gates allow. The judge and picks choose the top board rows in one rank (an AI-system cleanup row first, then project `#prio/`, then the board's own rank: due date, priority, `#requested`, age; then worker, kind and stage; each pick names it in `why`), each is started on its board and promoted with `AGENT_QUEUE_PULL=dispatch agent-queue add --priority <row> --from board:<project>:<id> --slug <id>`, the row text as the task, and the same pass starts the head. The id is the join: `ptask start` stamps one on a row with none, a row left without one (its project has no `code`) is refused, and the priority is the row's, high on a bare row. A tier-3 cleanup row (kinds.json `cleanup`) merges at any hour behind the red-fix gate; every other tier-3 row is promoted with the `tier3` tag and its brief stops at an open PR, under the same room, gates and `DISPATCH_PER_PASS` as any day row. An active item holds its area against new picks until reap closes it. By hand, `fleet-dispatch fill` promotes with no gate, and `fill --dry-run [--json]` lists what a pass would promote, by id with its priority (it was `fleet-dispatch queue`, #740).
- Every item's brief has the PR body carry `Item: <slug>`, and `agent-land` adds that line before the checks when the body lacks it (a stale one is rewritten), so a reader holding only a PR finds its item (#1069). A board item's brief also has it carry `Task: <id>`, the row id, and `agent-land` closes the row by id, so editing the row's text while the item runs breaks nothing; a tier-3 PR item stops at the open PR and leaves the row to the human's merge. A board item that ends `failed` or `cancelled` (reaped, or cancelled while queued) has its row un-started and a `failed` verdict recorded, so the next pass judges it again; `DISPATCH_FIX_TRIES` (2) failures since its last `cleared` hold it, and reap then files one approval ask for an agent-lane row and gates it on the answer (fleet-dispatch skill, Reap).
- `reap` closes an item whose session is gone and that the session did not close, by its PR's state read from gh: merged is `status: ok` with `merged:` (a board row still started closes on merge proof), open moves it to `review/` (an item an older pass parked in `waiting/` on its open PR moves too), closed is `failed` and hands the row back, no PR and no report is `failed` with the reason in `note:` (a run blocked by the usage limit or a partial landing goes back to `queued/`, one blocked by a pending ask or an unfinished `after:` goes back to its board row behind that gate, as `requeue --ask` and `return` send it, and a waiting or review item stays parked), and a state gh cannot read leaves it for the next pass. A Claude missing from agent-panel, while its tmux session lives or for a hub item with no session, is one witness: the item is left as it is until a reap at least `DISPATCH_REAP_CONFIRM` seconds (120) later misses it too (`~/.agent/dispatch/reap-miss/`). A reap that does not read it gone (listed, parked, inside its start grace, or the panel unreadable) clears the miss, and so does the close. A false `failed` close goes back with `reopen`; a false move to `waiting/` needs nothing, since the next reap that lists the Claude moves it back to `running/`. A started item recording no session at all, tmux or Claude (added from a plain shell), has no witness, so past the start grace only its PR or report decides: merged, closed and a report settle as above and open parks it in `review/`. An item still active after that, parked on an open PR or with a PR gh cannot read included, is flagged once, in `note:` (ahead of any note it had) and the log; having no PR never fails it, and `ownerless_running` (`fleet-bench chain`, the board-chain watch) counts and names it until `agent-queue claim` gives it a session or it is closed. Every reap move is `--if` the state it read, so an item requeued or closed meanwhile is left as it is; `note:` is written after the move, and `merged:` before it, since an ok close of an item with a PR needs one. An agent-lane row started with no active item naming it is an orphan. If an item done ok in the last `DISPATCH_ORPHAN_HOURS` plus a day names it, its PR decides first: merged closes the row on merge proof, open leaves it started with no first sighting. Otherwise, once reap has seen it orphaned for `DISPATCH_ORPHAN_HOURS` (72) it un-starts it with a `failed` verdict, so it is judged again or, at `DISPATCH_FIX_TRIES` failures, asked about (first sightings: `~/.agent/dispatch/orphans.tsv`). A live session's item moves to `waiting/` while its Claude waits on the human (agent-panel status `waiting`, which an open plan or dialog is) or owns a pending `agent-ask`, and back to `running/` once it does not. When agent-panel or agent-ask cannot be read, the pass moves nothing.
- `validate <slug> --pr <owner>/<repo>#<N> --head <sha> --why <text>` is agent-land's hand-off of critical work (`validate_gate`; critical is `judge_work_level` in `.local/lib/judge.sh`): it queues `validate-<slug>-<sha8>`, tagged `validate`, high, `from: auto:validate` (admission never holds it), `after:` the author item, so its worktree is cut from the PR head (stacked). Its brief (`validate_task`) has a second agent review the PR, record `verdict`, `verdict_head` and `note` on its own item, and run `agent-land <N> --item <slug>`, which merges on a pass and sends the author item back to the queue on a fail. `start` refuses a validate item whose `after:` is empty or itself, or a resume into a conversation or session that worked the author item (`validate_self_why`); the ladder never takes one, and reap gives a green parked PR no lander while its validate item is live (`own_parked_pr`). Tests: `tests/unit/agent_land.bats` "validate:", `tests/unit/fleet_dispatch_start.bats`, `tests/unit/fleet_dispatch_reap.bats`.
- Fleet workers: a pass can place an item on a home host in the home-config inventory group `fleet_workers` (`fleet-dispatch hosts` lists them as a pass reads them; roster and ssh in `~/.dotfiles/.local/lib/fleet-hosts.sh`, provisioning and sign-in in home-config `docs/runbooks/fleet-worker.md`). Only a light item with no plan, no `#cloud-ok` and no `red` tag (a red's watch state, logs and probe environment, such as the NAS mount and kubeconfig, are the lease holder's), in a repo the worker lists in `fleet_repos`, is placed, on a harness whose launcher the worker has (`fleet-dispatch kit` there, read by the same probe: claude when every Claude account is signed in, codex, opencode, and srt when srt can hold a run), past claude only one the worker lists in `fleet_harnesses` (`fleet_harnesses: [nim, ocfree, opencode-go, codex]`) and its probe finds ready (`fleet-dispatch harness-ready` there: a sandboxed opencode harness whose map entry, eval config, key file, lane sandbox and srt it holds, or codex on the worker's own login; a codex item that resumes a thread from this machine's `~/.codex` stays here; `start --host` makes the run's srt settings on the worker with `harness-prep`, and a trainee batch review fetches the patch a worker's run left; the batch review itself runs here), and only when this machine's gates hold it: a pass starts here first, except that a canary (`from: canary`) goes first to a worker whose `fleet_first` names that class (`fleet_first: [canary]`, one inventory line to opt a machine in). A worker takes it when it has `fleet_place: true`, answers one ssh probe, is under its own `fleet_max_live` and the `MAX_LOAD` pace on its own cores, has at least `DISPATCH_HOST_MEM_MIN_PCT` (20) percent of its memory available (`MemAvailable`, read by the same probe), has `wt` and a store that is a peer clone (`store-sync join`), and reports a kit (an older fleet-dispatch with no `kit` verb reports none and takes nothing). Under `DISPATCH_SANDBOX_PROFILE` a worker takes a session only when its kit has srt (a pass skips one without, and `start --host` refuses it). `start --item <slug> --host <name>` opens it there, and the session's `agent-queue` and `agent-ask` calls write the worker's own clone, which pushes each write at once (QUEUE.md "The store: every machine a peer"); the item records `host:`, and `reap` asks that host whether the session lives, leaving the item alone while the host does not answer, until it has gone unanswered on every reap for `DISPATCH_HOST_DEAD` (1800s) while this machine still syncs the store (`store-sync-age`, so a dispatcher cut off reads no worker lost): then the item goes back to `queued/` with `lost:` and `salvage:` (QUEUE.md "The item") and a pass places it on a node that answers. The worker's outcomes and Stop-hook writes stay on the worker. A worker's `fleet_ssh_host`, when set (a cloud box's tailnet name), is where ssh goes in place of its `ansible_host`.
