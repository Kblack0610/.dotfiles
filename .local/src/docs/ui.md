# UI look standards

How every UI we build looks: agent-web, every web-kit site (trader and the next one), the hub TUI where a rule applies to a terminal, and any new web UI in any repo. `dashboards.md` beside this file says what a dashboard shows; this file says how it looks. Games have their own look doc (`systems.md`, the `look` row). A client's repo follows the client's own design system.

## Taste

The target is a calm, dense operator console: a white page, quiet greys, one accent, colour only where something needs a look, and a table you can scan 50 rows of without reading every word. A reference that meets it: the device list of a fleet admin console (light page; page title with its primary action on the right; one row of KPI cards; one filter line; a dense table with uppercase muted headers, a link over a grey second line in each record cell, and small soft status pills with a dot). Ask of every screen: would a staff designer at a good devtools company ship this? Busy, warm, heavy, shouty or decorated means no.

## Rules

Each rule has its why. A rule a test checks names the test.

1. One visual system. Every web UI loads web-kit's `tokens.css` (`../web-kit`) and takes its colour, type, spacing, radius and status tints from it; a site adds tokens only for what is its own, and never a second palette, font or scale. A value the kit lacks is added to the kit, never hard-coded in a site. A React or other framework site maps its theme to the same token values. Why: agent-web and trader drifted in fonts and greys before web-kit existed, and a copied value never follows a change.
2. Light, flat surface. The page and panels are white, the greys are cool neutrals, borders are 1px hairlines, and there is no shadow, gradient or texture; a border marks elevation. One radius for controls and one for cards. Dark mode is the same system inverted, every token with a dark value. Why: the warm beige page and heavy borders read muddy next to a clean console (2026-11-12).
3. One accent. The accent (blue) marks links, the primary button and the selected item, nothing else; text that does nothing is never accent-coloured. Every other hue means what `dashboards.md` rule 5 says. Why: a colour that also decorates teaches the reader to ignore it.
4. Status is a soft pill. A state word is a small pill in its hue's light tint, with a dot and the word in the hue, in sentence case, on every row, broken ones included; a red or amber section shows its hue on its head (`dashboards.md` rule 4), never as solid badges down the rows. Why: a page of solid WORKING, STALLED badges shouts, and the one real red drowns in it.
5. Type: one sans, one mono, one scale. Inter for every word of UI, including headers, labels and buttons. JetBrains Mono only for code, ids, hashes, paths and columns of numbers that must align. Sizes come from the token scale, never a literal. Numbers in a table are tabular and right-aligned. Why: mono headers and labels mixed with sans made agent-web's tables read as a debug dump.
6. Case. Titles, buttons, tabs and pills are sentence case. Small uppercase letterspaced muted text is for exactly two things: table column headers and KPI tile labels. Why: one job per style is what lets the eye find a header without reading it.
7. Every page has a head: its title on the left, its one primary action (and a scope switch like Active / Archived) on the right, and no subtitle prose. The question a tab answers (`dashboards.md` rule 1) stays in `hub_core::layout` and is not drawn on the page. Why: a page with no title made the reader work out where they were; a subtitle under every title was noise (2026-11-12).
8. KPI row, then filter line, then table. What the controls do is `dashboards.md` rules 6 and 7; this rule is their order and look. A list page leads with one row of equal KPI cards (label, one big number in its state hue, its unit or split inline in muted text), then one line of controls flush on top of the table, then the table with its header filter row. Why: the human scans state, narrows, then reads, in that order.
9. Dense tables with two-line record cells. A row is one height; a cell is at most two lines, and longer text is clamped with its full text on the opened row. A cell naming a record is the record's name as a link over a muted second line (where, which, whose). Padding is tight, separators are hairlines, there is no zebra striping. Why: a cell that wrapped to four lines set the row height and halved what fit on the screen.
10. Spacing on a grid. Spacing is a multiple of 4px from the tokens. Content sits left, next to the sidebar, up to a max width; it is never centred in a wide gutter. Related things are close and groups are apart; whitespace does the grouping, and a box never sits inside a box. Why: a card around the search inside a card around the table looked dirty (2026-11-12).
11. Restraint. No emoji, no decorative stripes or icons, an icon only beside its label or as a universal glyph (search, close, external link, menu), transitions only for state changes and at most 150ms, no auto-playing motion. Why: decoration costs attention that the data needs.
12. Words. Labels are short nouns ("Devices", "Added"), empty states say what is missing and what to do, numbers carry their unit, times show the zone or are relative. UI text follows the `comms-standard` skill. Why: a label that needs reading twice is a bug in the UI.
13. The terminal follows the same system where a terminal can: rule 4's soft state words, rule 6's case and rule 9's density, in the terminal's own palette. Why: the TUI and the web show the same data, so they should read the same.
14. Proof is a screenshot at 1280px and 390px, in light and dark, beside the before; done is `dashboards.md` rule 14. `tests/agent-web/phone/render.mjs` takes agent-web's light shots at both widths; dark and before-and-after are not in it yet. A reference screenshot from a client's product is described here, never committed. Why: a look can only be reviewed by looking, and client data stays out of our repos.
