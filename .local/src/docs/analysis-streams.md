# Analysis streams

The method every analysis stream and cleanup pass follows: tokens (`usage-cleanup`), pipeline time (`pipeline-eval`), CI (`ci-failures`, `ci-cost`, `ci-cleanup`), docs (`docs-cleanup`), fixed context (`context-trim`), the agent boards (`board-cleanup`) and, for what to route where, runtime reds (last rule). A stream's skill names its sources, its metrics, its fixes and where its report lives, says which rules here it skips, and links here for the rest. A rule that a skill used to copy lives only here.

## A finding

One line: the claim, its number, the window, the command that printed it this session, the file or behaviour behind it, and its owner or route. A finding missing any of these is a guess and goes back to measuring.

## The pass

A pass runs these in order; a stream's Steps add its own sources and checks to each.

- In flight first: `agent-queue list`, `gh pr list` on the repos the stream touches, and the board rows for its area. A lever another session owns is theirs; send what you found with `fleet-comms`. Never edit a file another session has dirty or on an open branch; leave it for the next pass. Why: two sessions fixing one cause land two fixes and no measurement.
- The baseline comes from deterministic sources, saved with the window the skill names (an ISO time for anything under a day: a bare date means midnight). Name every source you could not read cleanly and leave it out of the totals. Pass 2 onward, the last report is the baseline, but re-read its windows (the original baseline's and the last pass's) with today's tools and never copy a number from it, so a counting change (a new bucket) is not read as an improvement and data that landed after the report counts. Why: a window that moves between passes makes the columns incomparable.
- Quote only a number the owning tool printed this session, or one read from the stream's own dated log. When the tool lacks one, extend it with a fixture test; never count by hand or score a transcript with a model. Why: a number only one session can reproduce cannot be re-measured.
- Put every unit (token, minute, red) in one bucket, name the file or behaviour behind it, and write down what you ruled out with its number. Why: the next pass starts from what is already excluded.
- Rank levers deletion first, then by saved per day: a lever that removes a mechanism, a wait or a repeat run beats one that adds a guard. Why: each added guard is paid on every later run.
- One lever per PR, with a test and a negative control for a script change. A pass with several PRs is one queue item (the session's `$AGENT_QUEUE_ITEM`, which every agent it briefs lands on too): land each earlier PR with `agent-land <N> --item <slug> --partial`, and only the last, usually the report's, without `--partial`; a pass that needed no PR closes with `agent-queue move <slug> done --status ok`. Why: a bundled PR measures nothing, a `--partial` landing records the PR and leaves the item open, and a PR merged any other way is credited to no item.
- A cause another stream owns goes to that stream as a proposal or board row, not fixed in place. Why: it is measured there and nowhere else.
- Re-measure the same way and over the same window length, after the merge is in the main checkout (stow serves `~/.dotfiles`: `git -C ~/.dotfiles log -1`). Say which lever moved a number only when that lever was measured alone. If only the measuring waits on new data, queue it as an `at:` item naming the plan file, close the pass's item and wind down.
- The report names the causes with their numbers, what was fixed (PR and measured saving), what was kept and why, what looks fine, and what is left. Its table has a row for every baseline metric and one column per measured point (the baseline, then each pass), so a later pass adds a column and no table. A stream that publishes its report puts it on an Artifact page and pages the human with the link, `agent-notify -p normal -t <skill> '<link>'`; with no Artifact tool (off by default, on in a session started with `CLAUDE_CODE_ARTIFACT=1`) it pages the report's path. Why: a pass that cannot say what it saved did not change anything.
- Each lever left undone is one proposal: `agent-propose add --stream <skill> --project <p> --verb queue --arg "<the lever as one task>" --why "<its number>" --evidence <report path> "<the lever>"`. Accept queues it, reject does nothing. List the stream first (`agent-propose list --stream <skill> --status all`): a lever already proposed is not posted again and a rejected one is not worked on. An add refused at the cap goes in the report instead. Why: Home is where the human decides, and the store dedupes.
- Queue the next pass from the session that writes the report, when "left" names a lever with a number, before the last `agent-land`: `agent-queue add --project <p> --priority low --tags "at:<date +7 days>T09:00" --slug <skill>-p<N+1> "<skill> pass <N+1>: run the <skill> skill; the baseline is <report path>"`, after `agent-queue show <slug>` finds nothing (it finds a finished item too). The `at:` rule is in `~/.config/agentctl/QUEUE.md`; the human ends a series with `agent-queue cancel <slug>`. Why: passes recur without a runner.
- A tripped watch or red runner reaches `triage-routes` (`~/.config/agentctl/triage-routes`) with one route: `agent` when its answer is a pass of one of these streams, `alert` when its answer is a decision (spend, pace, money). Why: pace and spend are the human's call, drift is a measured pass; `fleet-bench triage --coverage` fails a watch with no line, and `TRIAGE_FIX_CAP` bounds the sessions a day.
- Never restate this file, another skill or a doc a skill links in a stream's skill; name it. Why: a copy drifts, and `skill-drift --dups` lists the verbatim ones.
