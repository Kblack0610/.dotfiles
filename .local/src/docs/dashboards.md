# Dashboard standards

How we build and change a dashboard: the `hub` TUI (`../hub-tui`), agent-web (`../agent-web`), the waybar chips, Grafana boards in home-config, and any new one in any repo. Read this before adding a tab, a section, a tile or a new dashboard. How it looks (surface, type, pills, table density) is `ui.md` beside this file. The agent runtime's own invariants are in `standards.md` beside this file.

## Rules

Each rule has its why. A rule a test checks names the test.

1. One tab per question the human asks, never one tab per data source. Each tab title answers a question ("what needs me?", "where is each project?"). A new data source joins the tab whose question it answers. Why: tabs grouped by source left the same session on four tabs and the reader assembling the answer in their head.
2. Each fact has one home. Anywhere else it shows only as a count or badge that links to that home. Why: pending asks had six homes on agent-web and three in the TUI, and they disagreed whenever one lagged.
3. Summary first, details on demand. The summary goes at the top. Detail opens when a row is opened. Logs and audit trails sit behind a click or in a folded section, and trends live in Grafana (`o` on a TUI tab, a link on the web). Why: a 1000-row ledger at top level buries the three rows that need action.
4. Exceptions first, everything open. Red and amber sections come first and wear their hue; every section starts open, the reader may fold it, and the fold is remembered. Overflow ("+N more", settled rows, a green list shown as its count) and per-row detail, including a fold nested inside a section, stay one line until opened. Why: the human asked for full, clear views (2026-11-10); folded green sections hid what the page had, and opening the nested folds too made the project page 33,558 px (2026-11-12). `tests/agent-web/phone/render.mjs` holds every tab under three screens at 1400x900.
5. Green, amber and red mean ok, needs attention and broken, and nothing else uses those hues. Categorical series take the chart palette in agent-web `static/charts.js`. Anything past its slots folds into "Other"; a hue is never generated. Why: a red that means "category 3" teaches the reader to ignore red.
6. Every number is counted; no model writes a tile or a card. A percent, ETA or status comes from a deterministic function over files, CLIs or metrics, and the card says what it counted. Why: the agent-written "where we are" note did not help the human (2026-11-05), and a model score cannot be checked.
7. A list is a data table, and a card is only the record you opened. The hub and agent-web are the developer console the human triages every system from. Any list of records is a table on the shared table component: every header sorts (descending, then ascending, then the default order), state tiles filter by state (the hub's chip line), a filter row under the headers gives each faceted column a multi-pick dropdown with counts (ticks on one column OR, columns AND, the pill tinted while it filters; a facet whose column is not drawn sits in the bar), and the search takes several filters at once: terms are ANDed, `key:value` matches a column by prefix and `key:=value` the whole value (a link to one record by id), a repeated key ORs, `-key:value` excludes, a bare word matches the text (`project:playground kind:fix -acct:k1 nightly`). The whole view lives in the URL, so a filtered view is a link. The component is `hub_core::table` (`Row` per table, one `View` that filters, sorts and counts); agent-web applies it on the server and `static/table.js` only draws its summary, the hub's `datatable.rs` maps keys to it (`/` query, `f` state, `s` sort column, `S` direction, `x` clear). What a tick does is hub-core's too: each `Facet` value carries the whole query its tick gives. Times and ids are exact (`1h05`, `#1688`, the ISO time on hover), never "a while ago". An opened record's first line says what it is, its state and since when, what it needs from the human, and when it will be done. Why: card lists hid the metadata the human triages by, and `agent-queue list` in a terminal told them more than the Queue tab did (2026-11-06); slug-headed cards with a comma-separated meta line were unreadable (agent-web #920).
8. Both hub surfaces show the same tabs in the same order with the same section names, from one reader in hub-core. A view that needs data the reader lacks adds it to hub-core; the view never reads a store's files itself. Why: two readers of one store drift; `hub-core` exists so the terminal and the browser cannot disagree.
9. Update on the store's own event and poll only what has none. Agent-web pushes on file change. Prometheus-backed tabs poll at one named cadence with a server-side cache. A hidden tab refetches only when it is shown again. Why: the global no-sleep-and-hope rule, and a phone on the web view.
10. Load heavy detail only when it is opened. Transcripts, logs and screens are fetched on select, never for every row up front. Why: the human asked that sessions not all load until clicked (2026-11-03).
11. It works at phone width and in an 80-column terminal. The page never scrolls sideways. A table on a phone reflows: each row leads with its `Row::LEAD` column, wrapping, with `GLANCE` under it and the rest on a tap (`static/table.js`, one stamp for every table). A part of a tab that is not what needs attention folds to one line on a phone with `pfold` (`static/ui.js`), its summary saying the part's state; a hand-written table joins the shared row with `data-role` on its `th` (`tests/agent-web/table.test.mjs`), and `data-named` on a number that means nothing without its column name; only a grid (a blank corner cell) and an opened run's job list, a block per job, keep their columns. Why: agent-web is mostly read from a phone, and the hub runs in a tmux pane.
12. Mock it up before you build it. A new tab or a reshaped one starts as an ASCII mockup the human approves, in the plan. Why: lesson 2026-10-15, where a board built without one missed what the human pictured.
13. A layout change says what moved, where to, and why. A PR that removes, merges, moves or renames a tab or section carries a "Moved and removed" table in its body: old place, new home, why. It updates the "Retired names" table below in the same PR, and the old name keeps working as an alias: `#old` on the web and `hub --tab old`. The table also lists every key and shortcut whose meaning changes (TUI digits, tmux bindings, waybar clicks). TUI digits follow the layout order, so moving a tab renumbers the ones after it. Why: a view that disappears without a note looks like a regression, and waybar, tmux and bookmarks still point at the old name.
14. Done means the human can see it. A dashboard change is done when it shows on the live surface (the agent-web site after the stowed main checkout rebuilds, `hub` in its tmux window), checked with a screenshot (`agent-web-shot` for the site). Passing tests are not enough. Why: lesson 2026-10-15, and the 2026-11-03 note "does not close till I can see it".

## Patterns

- Tile: a label, one big number or word, and its colour by rule 5. Clicking it opens the section that explains it. A table's state counts are its tiles (`tblTiles`): one per state, hued by the word's tone in `hub_core::vocab::tone` (the TUI chip line uses the same tone), its meaning on hover; a tap filters, a tap on the one in force clears it, and a table whose only state is all draws none. The search bar (`.tqbar`) sits under them, fused to the table's top edge.
- Section head: its title, a plain noun in sentence case, and its count, never a sentence beside or under it (`secHead` in agent-web `static/ui.js`; `tests/agent-web/heads.test.mjs` fails a hand-written one). What a head would add goes elsewhere: a problem is a line under the head only while it holds, and its level hues the title so a shut fold still shows it (rule 4); a glance figure is a tile or a fact inside the section's own box; a diagnostic is a shut fold at the bottom (rule 3); what the section is for is its question in `hub_core::layout`, not drawn.
- Progress bar: counted done over total, with the raw counts beside the percent and the unit named ("17/25 rows, weighted by size"). An ETA is shown only when its rate is above zero, and it says which window it used.
- Needs-you list: one table on the shared component, ranked by what each row holds and how long it waited, every live wait only the human can answer (an ask, a session, a queue item) above every human-sheet to-do, since only a live wait stops running work (`hub_core::home::needs`); every surface keeps that order until a sort is asked for. Each row is its rank, a kind (`home::NeedKind`, decided in the reader, so its chips and `kind:` terms are counted there), its project, its exact wait, what it holds and what to do; the web opens the record under the row, where an ask or a dialog is answered in place. A view narrows only that table: waybar, the phone, the pager and Running's session counts keep the whole list.
- Folded section: open by rule 4 until the reader folds it. On the web, `<details data-k>` whose state `static/ui.js` keeps across repaints (`paint` records it; `secOpen` reads a key with no record as open, so a remembered close stays closed). In the TUI, a section head with a `+`/`-` marker and its key; the fold flag starts open. A folded head shows its count.
- Sidebar (web): every kblab site draws its nav with web-kit's `<kb-shell>` (`~/.local/src/web-kit/`, markup contract in its README), never its own: tabs under group headings as a fixed sidebar from 900px, and under 900px a menu button that opens the same list and names the open tab. agent-web renders its groups from `hub_core::layout` (each group is one run of `TABS`, so a heading never changes the order; the TUI bar does not draw them), and the open tab lists its sections beneath it, read from the board's `sec-` anchors by `static/nav.js`, so a section gets an entry by having an anchor and a heading.
- Inner tabs: a tab with more than one question's worth of sections groups them as `hub_core::layout::Inner` (a strip, the tab's first row on every path, loading and error included, with a count beside one whose sections are amber, only above zero). Every section is in exactly one group and the groups list them in the tab's section order (`groups_check`, and a section id still opens its group); nothing sits above the strip. A missing, unknown or hidden inner tab opens the first. TUI: Left/Right, the open one bold and reversed; web: the `.istrip` buttons and ARIA tab keys, `#costs/models`, a flush row with one bottom rule and an accent underline on the open one, scrolling inside itself at phone width. Costs (Limits, Spend, Models, Budget), Infra (Machines, CI, Jobs) and Releases (Apps, Builds, Tests) have one, and so does an opened record with more than three parts, Overview first (the project page, `layout::PROJECT_PAGE`, `#projects/<profile>/<name>/<inner>`); the TUI strip is `hub-tui/src/innertabs.rs`, web `INNER_TABS` is checked by `assets.rs inner_tabs_are_the_layout`.
- Link: a record is a kind plus an id with one page, and every cell, part or row that names one links there through `hub_core::links` (`Link::href` for the web hash or a URL, `Link::tab_args` for `hub tab`). A table row says what its cells name with `Row::link`; the summary sends that as `table.links` beside the rows, agent-web draws it with `tblLink` in `static/table.js`, and the TUI opens it on Enter (`DataTable::opens`, `App::follow`). Nothing builds a `#...` string for a record by hand. A linked cell (`tblLink`, class `tl`) reads as its text, in the cell's own colour and font, and shows the link (accent, underline) on hover or keyboard focus, with a dotted underline kept on a touch screen; monospace is for ids, numbers and code, never task or title text. Why: after #1883 linked every cell, 850 blue underlined cells on one page hid the values a reader scans for (`tests/agent-web/*.test.mjs` match the class). A page inside an inner tab (`#infra/machines/<host>`, `#infra/pools/<pool>`, `#infra/ci/<repo>/<run>`, `#infra/jobs/<name>`) is a row of `links::PAGES`, which app.js mirrors as `ENTITY_PAGES` so its router keeps the id (`entity_pages_are_the_links`); its `tab_args` is the same word and id (`hub tab 'infra ci/<repo>/<run>'`). A PR's CI runs are `Kind::PrRuns` (`owner/repo#N`): the runs table under `pr:=` on both surfaces.
- Long list: capped, with a "+N older" control ("+N more" when the list is not ordered by time). It is never unbounded at top level.

## Phone widget

The Companion app's Template widget is the main mobile view: Home, shortened to what fits at 4x4. `hub phone --json` (`hub_core::phone`) gives its rows from the same `home::build` join, `agent-mqtt-publish` sends them as `sensor.agent_overview`, and home-config's `phone_widget.jinja` lays them out, the only place with HTML or colours. The System block is read in the cluster, so it still shows with the workstation off. The widget clips at the bottom, so sections run most important first, a green section is one line and reds cap at 6. Row lengths are the `phone` channel in `channels.toml`.

### Log

- Merges by hour are per project, on both surfaces: one row (TUI) or one stacked colour (web) per project, the busiest first, with the hourly total last. Both draw `hub_core::boards::merges_by_hour` over the server's local hours; the web gets it in `/api/log` (`hours`, `projects`).
- Log opens with the Work table on both surfaces: `hub_core::worklog`, one row per queue item plus one per PR no item claims, every project, attention first until a header says otherwise. A window (Today, 7d, 30d, All, or one date) narrows finished rows only; unfinished rows stay, because something stuck five days ago is still not done, and a single past day shows only what finished that day. On the web the window is `wday` in Log's URL, and the stepper, `[` `]` and the chart bars write the same key.
- A table with a time window takes it from `tblDays` in `table.js` (Work's days, Actions' hours), so no tab draws its own window buttons.
- A PR's project is its repo's name in `project-map.json` (`project_of_repos_json` in `project-name.sh`); a record written before day-log stamped `project` falls back to the repo name without its leading dot.
