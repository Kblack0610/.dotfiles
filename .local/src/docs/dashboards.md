# Dashboard standards

How we build and change a dashboard: the `hub` TUI (`../hub-tui`), agent-web (`../agent-web`), the waybar chips, Grafana boards in home-config, and any new one in any repo. Read this before adding a tab, a section, a tile or a new dashboard. How it looks (surface, type, pills, table density) is `ui.md` beside this file. The agent runtime's own invariants are in `standards.md` beside this file.

## Rules

Each rule has its why. A rule a test checks names the test.

1. One tab per question the human asks, never one tab per data source. Each tab title answers a question ("what needs me?", "where is each project?"). A new data source joins the tab whose question it answers. Why: tabs grouped by source left the same session on four tabs and the reader assembling the answer in their head.
2. Each fact has one home. Anywhere else it shows only as a count or badge that links to that home. A headline figure's home is its hub-core `Card` part, one label with its unit and one function: the hub grid, agent-web, the phone, the Tilecast document, the publisher's `summary/cards` (`hub cards --json --figures`), Home Assistant and the waybar chips show that value and count none themselves. `phone::tests::every_card_figure_reads_the_same_on_every_surface` fails when a card, its document section, its figure or a phone head disagree on one fixture, and `tests/integ/agent_mqtt_publish.bats` when the publisher's payload is not hub's document unchanged. Why: pending asks had six homes on agent-web and three in the TUI, and on 2026-11-21 "done today" read 84, 280, 266 and 267 on four surfaces at once.
3. Summary first, details on demand. The summary goes at the top. Detail opens when a row is opened. Logs and audit trails sit behind a click or in a folded section, and trends live in Grafana (`o` on a TUI tab, a link on the web). Why: a 1000-row ledger at top level buries the three rows that need action.
4. Exceptions first, everything open. Red and amber sections come first and wear their hue; every section starts open, the reader may fold it, and the fold is remembered. Overflow ("+N more", settled rows, a green list shown as its count) and per-row detail, including a fold nested inside a section, stay one line until opened. Why: the human asked for full, clear views (2026-11-10); folded green sections hid what the page had, and opening the nested folds too made the project page 33,558 px (2026-11-12). `tests/agent-web/phone/render.mjs` holds every tab under three screens at 1400x900.
5. Green, amber and red mean ok, needs attention and broken, and nothing else uses those hues. Categorical series take the chart palette in agent-web `static/charts.js`. Anything past its slots folds into "Other"; a hue is never generated. Why: a red that means "category 3" teaches the reader to ignore red.
6. Every number is counted, and absence is never a verdict. No model writes a tile or a card: a percent, ETA or status comes from a deterministic function over files, CLIs or metrics, and the card says what it counted. A source that is off, has never reported, could not be read or stopped reporting says which, in `hub_core::reading`'s words (`State`, `NOT_READ`, `NO_DATA`), never as a blank, a zero, a shorter list or green; `reading::tests::empty_state_words_come_from_one_place` fails on a file that spells those words by hand. Why: the agent-written "where we are" note did not help the human (2026-11-05), and a model score cannot be checked; an old state.json read as now and an asleep worker's sessions simply vanished (2026-11-12).
7. A list is a data table, and a card is only the record you opened. The hub and agent-web are the developer console the human triages every system from. Any list of records is a table on the shared table component: every header sorts (descending, then ascending, then the default order), state tiles filter by state (the hub's chip line), a filter row under the headers gives each faceted column a multi-pick dropdown with counts (ticks on one column OR, columns AND, the pill tinted while it filters; a facet whose column is not drawn sits in the bar), and the search takes several filters at once: terms are ANDed, `key:value` matches a column by prefix and `key:=value` the whole value (a link to one record by id), a repeated key ORs, `-key:value` excludes, a bare word matches the text (`project:playground kind:fix -acct:k1 nightly`). The whole view lives in the URL, so a filtered view is a link. The component is `hub_core::table` (`Row` per table, one `View` that filters, sorts and counts); agent-web applies it on the server and `static/table.js` only draws its summary, the hub's `datatable.rs` maps keys to it (`/` query, `f` state, `s` sort column, `S` direction, `x` clear). What a tick does is hub-core's too: each `Facet` value carries the whole query its tick gives. Times and ids are exact (`1h05`, `#1688`, the ISO time on hover), never "a while ago". An opened record's first line says what it is, its state and since when, what it needs from the human, and when it will be done. Why: card lists hid the metadata the human triages by, and `agent-queue list` in a terminal told them more than the Queue tab did (2026-11-06); slug-headed cards with a comma-separated meta line were unreadable (agent-web #920). The words in a row are `hub_core::display` roles (`ui.md` rule 16); the tests that hold that are hub-core's `display.rs` and `tests/agent-web/text.test.mjs`.
8. Every surface reads hub-core, the one reader. Both hub surfaces show the same tabs in the same order with the same section names; agent-web, the waybar chips, `agent-mqtt-publish` and the Home Assistant templates that read its topics take their figures from hub-core output (`hub <verb> --json`, the published `figures`). A view that needs data the reader lacks adds it to hub-core; the view never reads a store's files or counts its records itself. `tests/agent-web/readers.test.mjs` fails when `agent-web/src` shells out, reads a file or parses JSON outside its allowlist of plumbing, actions and the sites the agent-web one-reader chain (board row ar-3369) still removes, and `tests/agent-web/chips.test.mjs` when a waybar chip or the publisher counts records (jq `select | length`, `group_by`, `add`, shell increments, `wc -l`, `grep -c`) outside its allowlist; each entry carries its site count, and each list only shrinks. Why: two readers of one store drift; `hub-core` exists so the terminal, the browser, the bar and the phone cannot disagree.
9. Update on the store's own event and poll only what has none. Agent-web pushes on file change. Prometheus-backed tabs poll at one named cadence with a server-side cache. A hidden tab refetches only when it is shown again. Why: the global no-sleep-and-hope rule, and a phone on the web view.
10. Load heavy detail only when it is opened. Transcripts, logs and screens are fetched on select, never for every row up front. Why: the human asked that sessions not all load until clicked (2026-11-03).
11. It works at phone width and in an 80-column terminal. The page never scrolls sideways. A table on a phone reflows: each row leads with its `Row::LEAD` column, wrapping, with `GLANCE` under it and the rest on a tap (`static/table.js`, one stamp for every table). A part of a tab that is not what needs attention folds to one line on a phone with `pfold` (`static/ui.js`), its summary saying the part's state; a hand-written table joins the shared row with `data-role` on its `th` (`tests/agent-web/table.test.mjs`), and `data-named` on a number that means nothing without its column name; only a grid (a blank corner cell) and an opened run's job list, a block per job, keep their columns. Why: agent-web is mostly read from a phone, and the hub runs in a tmux pane.
12. Mock it up before you build it. A new tab or a reshaped one starts as an ASCII mockup the human approves, in the plan. Why: lesson 2026-10-15, where a board built without one missed what the human pictured.
13. A layout change says what moved, where to, and why. A PR that removes, merges, moves or renames a tab or section carries a "Moved and removed" table in its body: old place, new home, why. It adds the old name to `RETIRED` (or `PROJECT_RETIRED`, `cards::ALIASES`) in `hub-core/src/layout.rs` in the same PR, and the old name keeps working as an alias: `#old` on the web and `hub --tab old`. The table also lists every key and shortcut whose meaning changes (TUI digits, tmux bindings, waybar clicks). TUI digits follow the layout order, so moving a tab renumbers the ones after it. Why: a view that disappears without a note looks like a regression, and waybar, tmux and bookmarks still point at the old name.
14. Done means the human can see it. A dashboard change is done when it shows on the live surface (the agent-web site after the stowed main checkout rebuilds, `hub` in its tmux window), checked with a screenshot (`agent-web-shot` for the site). Passing tests are not enough. Why: lesson 2026-10-15, and the 2026-11-03 note "does not close till I can see it".

## Patterns

- Tile: a label, one big number or word, and its colour by rule 5. Clicking it opens the section that explains it. A table's state counts are its tiles (`tblTiles`): one per state, hued by the word's tone in `hub_core::vocab::tone` (the TUI chip line uses the same tone), its meaning on hover; a tap filters, a tap on the one in force clears it, and a table whose only state is all draws none. The search bar (`.tqbar`) sits under them, fused to the table's top edge.
- Section head: its title, a plain noun in sentence case, and its count, never a sentence beside or under it (`secHead` in web-kit `kb-ui.js`, styled by `ui.css`; `tests/agent-web/heads.test.mjs` fails a hand-written one). What a head would add goes elsewhere: a problem is a line under the head only while it holds, and its level hues the title so a shut fold still shows it (rule 4); a glance figure is a tile or a fact inside the section's own box; a diagnostic is a shut fold at the bottom (rule 3); what the section is for is its question in `hub_core::layout`, not drawn.
- Progress bar: counted done over total, with the raw counts beside the percent and the unit named ("17/25 rows, weighted by size"). An ETA is shown only when its rate is above zero, and it says which window it used.
- Needs-you list: one table on the shared component, ranked by what each row holds and how long it waited, every live wait only the human can answer (an ask, a session, a queue item) above every human-sheet to-do, since only a live wait stops running work (`hub_core::home::needs`); every surface keeps that order until a sort is asked for. The list holds only what the human can do: `hub_core::home::Kind::owner` says per kind whether a row is theirs or agent work, and agent work (a failed Tier-3 task, a red-now item, a red nightly, a stopped dispatch) is routed to the tab that owns it (`Home.routed`), never listed. There is one count and one kind split (`Home::waiting`, `Home::split`); the badge, the card, the phone and the briefing show those and keep no subset of their own. Each row is its rank, a kind (`home::NeedKind`, decided in the reader, so its chips and `kind:` terms are counted there), its project, its exact wait, what it holds and what to do; the web opens the record under the row, where an ask or a dialog is answered in place. A view narrows only that table: waybar, the phone, the pager and Running's session counts keep the whole list.
- Owned red: the overview (Home's Alerts card, and the phone widget's with it) shows a red to the human only when nobody fixes it on time: no owner, a fix that did not hold, a fix that waits or is in review, or one past its due or with no due (too few merged fixes to judge by). A red whose fix is in hand and on time reads "being fixed by <session>" in green (`hub_core::alerts::Alert::unfixed`; tests `a_red_is_being_fixed_only_while_its_fix_is_in_hand_and_on_time` and `an_owned_red_on_time_is_being_fixed_and_only_the_rest_turn_the_card_red`). The Alerts tab, the detail, lists and hues every red, and Needs you lists no red at all (Kind::Red is routed). Why: 22 tripped watches read as 22 reds the day triage already owned most of their fixes (2026-11-20).
- Needs you figure: Home's Needs you card (`hub_core::cards::needs`, parts from `Home::parts`: Question, Your turn, Blocked, To do, and `Only you`, the rows no machine can answer) is the only count of what waits on the human. A shell reader takes it from `hub-figure <figure>` (`needs_headline`, `needs_question`, `needs_only_you`; `hub needs --json` `figures`, cached with a stale-while-revalidate TTL so a 3 s status bar starts no hub), which prints `?` and exits 1 when Home cannot be read, never 0. The tmux bar `!N` (`claude-status.sh`), `questions.sh count`, `agent-ask count --all`, the shepherd's settle page and day-log read it; the Prefix y panel's header still counts the rows it lists. Why: the bar said 4 while Home said 54, and a figure the reader could not get showed as 0 (ar-4395, ar-4474).
- Folded section: open by rule 4 until the reader folds it. On the web, `<details data-k>` whose state `static/ui.js` keeps across repaints (`paint` records it; `secOpen` reads a key with no record as open, so a remembered close stays closed). In the TUI, a section head with a `+`/`-` marker and its key; the fold flag starts open. A folded head shows its count.
- Sidebar (web): every kblab site draws its nav with web-kit's `<kb-shell>` (`~/.local/src/web-kit/`, markup contract in its README), never its own: tabs under group headings as a fixed sidebar from 900px, and under 900px a menu button that opens the same list and names the open tab. agent-web renders its groups from `hub_core::layout` (each group is one run of `TABS`, so a heading never changes the order; the TUI bar does not draw them), and the open tab lists its sections beneath it, read from the board's `sec-` anchors by `static/nav.js`, so a section gets an entry by having an anchor and a heading; a section in a hidden pane of a record page (a product's Legal) is left to that page's strip.
- Inner tabs: a tab with more than one question's worth of sections groups them as `hub_core::layout::Inner` (a strip, the tab's first row on every path, loading and error included, with a count beside one whose sections are amber, only above zero). Every section is in exactly one group and the groups list them in the tab's section order (`groups_check`, and a section id still opens its group); nothing sits above the strip. A missing, unknown or hidden inner tab opens the first. TUI: Left/Right, the open one bold and reversed; web: the `.istrip` buttons and ARIA tab keys, `#costs/models`, a flush row with one bottom rule and an accent underline on the open one, scrolling inside itself at phone width. Projects (Projects, Board, Deliverables), Costs (Limits, Spend, Models, Budget), Infra (Machines, CI, Jobs) and Releases (Apps, Builds, Tests) have one, and so does an opened record with more than three parts, Overview first (the project page, `layout::PROJECT_PAGE`, `#projects/<profile>/<name>/<inner>`); its department views are one Departments tab holding a chip per department the project's type gets (`layout::PROJECT_DEPTS`, `#projects/<profile>/<name>/departments/<dept>`, `[` and `]` step the chip in the TUI), and an old department id such as `#.../legal` still lands on its chip through `PROJECT_RETIRED`; the TUI strip is `hub-tui/src/innertabs.rs`, web `INNER_TABS` is checked by `assets.rs inner_tabs_are_the_layout`.
- Link: a record is a kind plus an id with one page, and every cell, part or row that names one links there through `hub_core::links` (`Link::href` for the web hash or a URL, `Link::tab_args` for `hub tab`). A table row says what its cells name with `Row::link`; the summary sends that as `table.links` beside the rows, agent-web draws it with `tblLink` in `static/table.js`, and the TUI opens it on Enter (`DataTable::opens`, `App::follow`). Nothing builds a `#...` string for a record by hand (`tests/agent-web/links.test.mjs` counts the sites in `static/*.js` against an allowlist that only shrinks). A linked cell (`tblLink`, class `tl`) reads as its text, in the cell's own colour and font, and shows the link (accent, underline) on hover or keyboard focus, with a dotted underline kept on a touch screen; monospace is for ids, numbers and code, never task or title text. Why: after #1883 linked every cell, 850 blue underlined cells on one page hid the values a reader scans for (`tests/agent-web/*.test.mjs` match the class). A page inside an inner tab (`#infra/machines/<host>`, `#infra/pools/<pool>`, `#infra/ci/<repo>/<run>`, `#infra/jobs/<name>`) is a row of `links::PAGES`, which app.js mirrors as `ENTITY_PAGES` so its router keeps the id (`entity_pages_are_the_links`); its `tab_args` is the same word and id (`hub tab 'infra ci/<repo>/<run>'`). A PR's CI runs are `Kind::PrRuns` (`owner/repo#N`): the runs table under `pr:=` on both surfaces.
- Run page: one CI run's record, on agent-web (`#infra/runs/<repo>/<id>`, and the table's opened row) and the hub's Runs row, six sections in this order from the one `RunDetail` read (`hub_core::builds::open_detail`, its `page` from `hub_core::run_page`). Summary: what ran, for whom, on what and how long. Changes: the commits since the last run of that workflow on that branch (`git log` in the repo's clone, each with the PR that merged it). Tests: the failed tests with their assertion text and which are new against the last green run on main (quarantine applied), or one folded line when green. Jobs: a graph of columns by `needs:` depth (the columns wrap, and stack on a phone) from the workflow file at the run's sha, read live from GitHub when the archive has not reached the run (kept 30 s, rule 9), each job a box that opens its log when it has ended (rule 10), the steps and coverage under it; a Forgejo run's jobs are archived by `schedules-sync` from the run page's JSON (a public repo: steps and their times, the log on open; a private one, whose pages answer 404 to every token, the tasks list alone: names and results, no steps, no log). Artifacts: for a workflow the repo declares in `buildWorkflows` (`project-map.json`, next to `testWorkflows`), what the run built, one row per artifact with its size, where it is kept (`github`, or `store` for the home artifact store when the repo names an `artifactStore` lister) and when it goes, an expired one listed as `expired`; read once on open (`gh api` and the lister) and kept for good once the run is done; any other workflow says `no declared builds`. Chain: the run that triggered it, the release it built and where that has reached, and a link to Releases > Flow. A section with nothing says why in its own words (rule 6), and a surface adds no section, source or order of its own.
- Release page: one version of an app across every cut of it, on agent-web (`#releases/apps/<app>/<version>`) and atop the hub's app pane, from `hub_core::release_page`. The cut on show is a pipeline, left to right: the tag, the runs it started, the runs those started, the channels it reached or what is live there instead; each run box links its run page, so the stage graph of one run stays on the run page. Under it, one row per cut with each workflow's result. A release tag, wherever it is drawn, links here. A version has a handful of cuts, so Cuts is one unpaged table: the Long list rule does not reach it.
- Version page: one version of a project across every app it owns, on agent-web (`#releases/versions/<project>/<version>`) and atop the hub's pane of any of those apps, from `hub_core::version_page`. A tracker's release page in shape: the header says released, cut, unreleased or legacy with the newest cut and the window's opened and due days; a bar counts the rows aimed at the version by state; one row per row (from `notes board --json --version`) with its state, who works it (the queue item naming the row, its tmux session while live) and its PRs; then each app's cut drawn as its release page, a red one naming who fixes it. A release page links up here, so every RELEASE cell, history row and Chain hop is one click away. A version holds tens of rows, so Rows is one unpaged table.
- Project Releases tab: an opened project's Releases inner tab, on agent-web (`#projects/<profile>/<name>/releases`) and the hub's project page, from `hub_core::project_releases` (read with the page). Versions on the release line lead, newest first, each linking to its version page with its status (`version_page::verdict` on the lab mark from `version_page::mark_of`, the rule and inputs the version page uses too, so the two agree), its line mark (a cut outside the flow is amber) and its rows done; then the project's apps that declare a `releaseFrom`, in the words Releases > Apps gives them. Everything before the line sits in one shut Legacy fold: the versions marked legacy and the apps with no `releaseFrom`. An app whose name matches the project but is owned by another says where it releases. A failed release-state read, or a lab whose versions did not read, is said on the tab; a host with no snapshot yet says nothing.
- Long list: paged on the shared table. The server sends one page (`hub_core::table::page`, its size the section's `hub_core::layout::PAGE_ROWS` entry) and the shared table draws the pager under it (prev, pages, next, "rows 31-60 of 120"), with the page in the URL (`pg`, prefixed per table). A view change opens page 1. A tab never caps its own rows, and a list is never unbounded at top level. The TUI scrolls every row instead. A runner page's short lists (20 rows or fewer, listed nowhere else) end in a `+N more` that draws the rest the reader kept, and three lists still cap by hand until they page: Log Changes, Alerts' settled fixes and Costs' day sessions.

## Phone widget

The Tilecast app (git.kennethblack.me/kblack0610/tilecast) is the main mobile view, a native widget: it fetches agent-web's `/widget.json` (`hub_core::widget_doc`), refreshes on a push from the server as well as a timer, and draws colour and bars at every size. With no `?cards=` the document carries every card in Home's one order (`hub_core::cards::ORDER`, which the web and TUI grids follow; `cards.rs` tests hold the grid to it): Needs you, Main red, then the grid (done, health, sessions, queue, board, alerts, costs, releases, schedules, projects). Done today is the phone section's count (`phone::Done`, one read, so the card and the section never disagree), and Health is the Infra tab's machines with CI from `ci.glance` and the vitals head; a `?cards=infra` still names it (`cards::ALIASES`). The app decides what fits; the order stays most important first. Each card is one section with what the web card has: its unit whole (a card's unit is a fixed word of 16 characters or fewer, the format's cap, and a count beside it is a part; `widget_doc::tests::every_card_unit_fits_the_widget_whole`), each headed list of its rows (the Queue card lists Running, On a PR and Up next, then Flow), and what it counted last; a reader that answered in part keeps its data at warn (bad when its big number could not be read) with the reason as a warn row, and only one that answered nothing says NO DATA.

The Companion app's Template widget is the maintained second option: Home, shortened to what fits at 4x4. `hub phone --json` (`hub_core::phone`) gives its rows from the same `home::build` join, `agent-mqtt-publish` sends them as `sensor.agent_overview`, and home-config's `phone_widget.jinja` lays them out, the only place with HTML or colours. The System block is read in the cluster, so it still shows with the workstation off. The widget clips at the bottom, so sections run most important first, a green section is one line and reds cap at 6. Row lengths are the `phone` channel in `channels.toml`.

To set Tilecast up on a phone: open agent-web on the phone, sign in with Forgejo, tap Phone widget in the menu (`/widget/setup`) and tap Add to Tilecast. Only after losing a phone or leaking the key, tap New key there: it stops every phone on the old key, so tap Add to Tilecast again on each phone you keep (agent-web README, Widget setup).

## Hub layout

The tabs, their groups and order, the retired names that still resolve (`RETIRED`, `PROJECT_RETIRED`) and the card aliases (`hub_core::cards::ALIASES`) are in `hub-core/src/layout.rs`, which owns them. The TUI's `the_tabs_are_the_layout_and_each_digit_its_place`, agent-web's `tab_names_are_the_layout` and each surface's `log_folds_are_the_layout` fail when a surface drifts from it. What a tab shows is its hub-core reader; why one moved is in `git log`. TUI digits follow the bar, which is the order less Daily: 1 for the first, 0 for the tenth; a tab past the tenth has no digit.

### Projects

- Sprints are two inner tabs, never Board's: Projects > Sprints (every project's open and queued windows, then each project's last score) and an opened project's Sprint tab (its open window with its tasks, the ones queued behind it, then its scored past, newest first, one row per `sprints/vX.Y.Z.md`). Both surfaces draw `hub_core::tasks::SprintRow` (the windows, read from the board feed) and `hub_core::project_sprints` (the past, from `notes projects --sprints`, carried on the page as `sprint_past`). agent-web gets the windows from `/api/sprints`; Board shows rows only. Why: a window is a question of its own (what ships by when), and a project's history belongs on its page, not under a table of rows.

### Log

- Merges by hour are per project, on both surfaces: one row (TUI) or one stacked colour (web) per project, the busiest first, with the hourly total last. Both draw `hub_core::boards::merges_by_hour` over the server's local hours; the web gets it in `/api/log` (`hours`, `projects`).
- Log opens with the Work table on both surfaces: `hub_core::worklog`, one row per queue item plus one per PR no item claims, every project, attention first until a header says otherwise. A window (Today, 7d, 30d, All, or one date) narrows finished rows only; unfinished rows stay, because something stuck five days ago is still not done, and a single past day shows only what finished that day. On the web the window is `wday` in Log's URL, and the stepper, `[` `]` and the chart bars write the same key.
- A table with a time window takes it from `tblDays` in `table.js` (Work's days, Actions' hours), so no tab draws its own window buttons.
- A PR's project is its repo's name in `project-map.json` (`project_of_repos_json` in `project-name.sh`); a record written before day-log stamped `project` falls back to the repo name without its leading dot.
