# Project stages

How mature a project is, what it must have at each stage, and which check proves it. One ladder for every project type and for every game inside the playground.

- The stage is a hashtag on the lab sheet's `Version:` line, for example `Version: v0.3.0 #alpha`. Its one writer is `notes projects --stage <name> --set <stage>`; a hand edit works too, and the nightly `project-map-doctor` catches a sheet that drifts.
- The ladder itself has one definition, `STAGES` in `.local/src/notes-cli/src/projects.rs`. Shell readers get it from `notes projects --stages` (or `lab_stages` and `lab_stage_at_least` in `.local/lib/lab-feed.sh`) and never keep a copy.
- The project type (`game`, `app`, `infra`) comes from `type` in `project-map.json`, the same field `planning.md` reads.
- A project's type standard is its systems and their criteria, base plus its type's overlay, in `systems.md`; `project-system-check <name>` reports met/total per system.

## The ladder

The deploy pipeline is built at the dev -> alpha gate. An alpha project already deploys itself to a private target on every merge, so the beta step only changes who uses it and on which channel. The stage says what a project must have, never where it may deploy: a deploy is not the app being live, so a draft or dev project with a prod target is fine (the human, 2026-11-12). Each registry target's `channel` maps to the rung it serves in the `project-map.json` `channels` map (the Registry channels column); `release-state` turns that into each project's served rungs, and the Requirements rows below read them.

| Stage | Means | Who uses it | Where it runs | Registry channels | What the tooling does |
| --- | --- | --- | --- | --- | --- |
| `draft` | A concept with its type standard and target load named, already scaffolded on the shared stack | the human | CI only | none | Hidden behind `d` in the `Prefix+p` popup; fleet-dispatch skips it |
| `dev` | Built to its type standard, CI green, the core loop or flow being built | the human and agents | CI artifacts | none | fleet-dispatch starts agent sessions on its rows |
| `alpha` | Works start to finish and deploys itself to a private target on every merge | the human and the team | home-k3s preview, Play internal, Steam `development`, TestFlight internal, Forgejo registry, Quest sideload | `alpha`, `preview`, `internal` | Releases on its cadence (see Versions) |
| `beta` | Versioned releases to outside testers, rollback proven, load tested | testers | TestFlight external, Play closed, Steam `beta`, a public preview URL | `beta` | As alpha; STATUS goes STALE after 14 days |
| `prod` | Public, watched, with runbooks | the public | stores, Steam `default`, the prod cluster | `prod` | As beta, plus the doctor FAILs it without a shipped tag |

A project with no stage sorts between dev and draft and is dispatched like a draft. The doctor WARNs on it.

## Requirements

Entering a stage means meeting its rows and every row of the stages below it. In `Applies`, `base` means every type, and `store` means a project that ships through a store: every game, and a project with a `steam`, `play` or `testflight` target in its `project-map.json` `targets` (a web app or service on k8s only is not one). `project-stage-check <name> [--stage s] [--json]` runs the rows (`--json` gives met, total, fail, human, todo, the gate and each row, for a page to read): `notes projects --stage <name> --set <s>` runs it on a move up and refuses to move the tag on a blocking FAIL (a move down is never gated), and `project-map-doctor` runs it for every staged project each night.

A gap becomes work with `--file`, a reconcile: the FAIL rows of a stage go on one agent-board row under the open epic for its target, `chore(stage): meet the <target> stage standard #size/m`, whose brief lists one `#<stage>: <requirement>, check: <check>` line per gap. Each run rewrites that list in place (`notes ptask edit --brief`), so a row that passes leaves it and a new gap joins it, and the row closes with the check as its proof once nothing is left to list; it is `#high` once the gate blocks, else `#low`. A row this check filed for one gap on its own is folded into it (`drop --dup`, undone by `reopen`); a gap held by a row it cannot fold (in progress, a parent, on the human sheet, or with no `from project-stage-check` line) stays off the list. Each open agent row of a row that now PASSes is closed with the check as its proof. The target is `--stage s`, else the highest of the stage after the declared one (prod checks itself) and the stages open `epic(stage): <stage> to standard` rows name, so an epic opened for a later stage keeps its work coming and a leftover one for a passed stage holds nothing back. A row whose title both passes and fails (two rows sharing a text) counts as failing. With no open stage epic it files `epic(stage): <target> to standard` on the human sheet first; with `--systems` each FAIL row is a `#size/s` story of its own, through `notes ptask add`, which links its system's standing epic. A gap whose row the human closed or dropped, matched by title or by its `from` line (which a reworded row keeps), is never filed again, unless it was dropped as a dup of another row this check matches for that gap (or of the rollup), which then holds it; neither is a rollup closed by hand for its stage. It runs when `notes projects --stage <p> --set <s>` moves a project up, and each night in the `project-index` pass for every project at dev or later; what runs first is dispatch's job, by `#prio`. With `--json` its report goes to stderr and stdout carries the check of its target plus `filed_open` and `filed_closed`, the gaps the agent sheet holds open (a rollup line or a row of its own) and the agent rows of its rows closed; the nightly pass writes that to `stages.json` for the hub's Projects ladder.

Enforced from: 2026-11-19

Before that date a FAIL is reported and blocks nothing, so a row that turns out too strict can be fixed before it stops real work.

The `Check` cell is one of three things:
- a backticked shell predicate, run in a subshell from the project's root with `NAME`, `TYPE`, `REPO`, `ROOT`, `LAB` and `STAGE` (the stage being checked, so a row judges a move up the same as today's stage) set, and `project-name.sh` and `lab-feed.sh` loaded. `ROOT` is the project's folder in its repo (`trackers.<name>.path`, as `apps/<app>` in a monorepo), else the repo; with no project folder it runs from an empty directory, so a project file reads as missing rather than matching a repo-root or lab file. A repo the map names but this machine has not cloned is not judged (exit 2). A missing project folder inside an available repo reports criteria gaps; predicates can still read `REPO` and `LAB`, and `ROOT` keeps its mapped path. Exit 0 is PASS. It reads local files, git and the `release-state` snapshot only, never the network, so a night run is quick and repeatable. Write a literal pipe as `\|`.
- A doc predicate reads the project's docs through four helpers, so it judges the remote default branch (`origin/HEAD`, as of the clone's last fetch; nothing here fetches) rather than a working tree that can be weeks behind, and a doc on an unmerged branch is not met until it merges: `doc <path>...` (each file exists), `doc_text <path>` (prints it) `doc_files` (lists every tracked file) and `doc_grep <pattern> <path>...` (a case-insensitive match in the `.md` files of those paths), all relative to `ROOT`. A repo with no `origin` remote reads its working tree; one with an `origin` but no `origin/HEAD` says so on stderr (`git remote set-head origin -a` fixes it) and reads its working tree.
- `human`: only the human can attest it, so the gate lists it and never fails on it.
- anything else: no predicate yet. The gate lists it as TODO with this text, which names what checks it today, if anything.

The `Dept` cell names the department that owns the row, one id from Departments below; the check exits 2 on any other word. `project-stage-check <name> --by-dept` prints a project's rows grouped by it, which is each department's list of what that project has and lacks.

## Departments

Every Requirements row belongs to one department. A project's docs and gaps for a department are its rows with that `Dept`, so there is no separate list of docs: a doc is required where a row requires it, and the row's text names the skill that writes it. Each doc has one home: the project's repo for what the code or the product depends on, the lab for the human's own notes (brief, ideas, playtest), and the marketing lab project for go-to-market. Infra projects take only the `base` rows, and show the engineering and ops tabs: a `base` row under product is still checked by `project-stage-check`, it has no tab.

| Id | Title | Question | Owns |
| --- | --- | --- | --- |
| product | Product | What is it, and is it the thing we meant? | the brief, `docs/overview.md`, the PRD, the status line, playtests |
| engineering | Engineering | Can someone build, change and test it? | README, `docs/architecture.md`, the docs index, standards, CI, CHANGELOG |
| ops | Ops | Does it deploy, stay up and come back? | the deploy doc and its rollback, the incident runbook, secrets, targets |
| design | Design | Does it look and feel like itself? | the brand sheet or taste, icons and splash, the UI pass |
| analytics | Analytics | Who uses it, and which features? | the event catalogue |
| marketing | Marketing | What did we plan and send, and how did it do? | the store listing, the go-to-market entry, the scorecard |
| legal | Legal | Can it ship at its stage? | privacy and terms, the compliance check, the content rating |
| support | Support | What are users telling us? | `docs/support.md`, the intake |
| money | Money | What does it earn and cost? | costs and revenue per product |

## Versions

A version is one release: what reached the project's users or target in one cut. Its number follows from what is in it, so nobody picks it.

- Minor: the release holds a feature epic closed on proof (`lifecycle.md`, "What an epic is"). Patch: anything else, fixes, stories toward open epics, standing-epic work. Major: only the human; a project starts at 0.x and v1.0.0 is its first public release (the `prod` stage), a project already past 1.0 keeps its line, and a later major is a break the human names (a save or API break, a relaunch).
- Cadence comes from the stage: every 7 days at draft, dev, alpha and beta, every 14 at prod, as `[release] cadence_days` in the notes config. One project can run shorter windows with `[release.windows.<project>]` (`days`, and optional `until = "YYYY-MM-DD"`, after which the stage cadence is back), for example a day for a game in playtest week; it sets the next window's due day and capacity and the sheet cadence cut, and a cut reads as a backlog for `--backfill` only once a week or more is owed, whatever the window length. A window with no closed rows cuts nothing.
- Target: the human may promise a version by a day with a `Target: vX.Y.Z YYYY-MM-DD` line under `Version:`, written by `notes projects --target <name> --set 'vX.Y.Z YYYY-MM-DD'` and emitted by `projects --stats --json` as `target_version` and `target_on`. It is the human's promise, not the cut rule: the cadence still decides when a version is cut. Only the human decides a target, and an agent sets one only on their ask; cutting the targeted version moves the line into that version's `versions/` note, so the next version starts with none. The on-time check reads it: `--stats --json` also emits `target_work`, the open weight of the open version and every later one up to the target with the weight closed and filed in 28 days, and the hub (card, Projects tab, lab-status line) turns that into an ETA at the net rate (closed minus filed weight per day) and says "on track", "late N days" or "never at this rate" against `target_on`. fleet-bench `release_overdue` counts a project a day past its target in place of its cadence, and the Sentinel `release-late` watch pages when a targeted version goes late.
- A project that ships builds is versioned by its git tag and the sheet follows (`project_release_version`, `.config/shared-hooks/project-name.sh`). A game in the playground has its own tag family, `<game>-vX.Y.Z`, registered as its `tagGlob`. A project with no build (agent-runtime, home-config) uses the sheet's counter and has no tag.
- For a project its tag owns, the sheet's `Version:` line is the next open version, never a record of what shipped, and only the roll (`agentctl-wave-roll`) moves it. Each tag gets its own lab note, `versions/<tag version>.md`, named from the tag (`projects --release --tag`): the first tag at or above the open version freezes that version's rows under its own number, and a tag below it (a hotfix nobody planned) gets a note marked as having no planned rows. The tag is the version record: a closed row freezes under the first release tag of the family that contains its `commit:` (`notes-roll` hands notes the family, `shipped.rs`), so a row closed after an earlier tag already shipped its merge goes to that tag's version (its agent note, under the sheet rows that rolled off before the freeze), and a merge the tag does not contain waits on the sheet, aimed at the next version, for its own tag. A row with no commit, or one of another repo, freezes with the version it closed in. Tags from 2026-11-11 on (`RELEASE_NOTES_SINCE`, `project-name.sh`) must each have a note, which `hub releases check` checks (`docs/operations/release-state.md`, Link facts); an older tag without one is history the notes never recorded.
- Tooling: `projects --release` derives the bump from the closed rows at any stage (`--patch`, `--minor`, `--major` override it). `agentctl-wave-roll` rolls a tagged project's sheet when its tag ships, and cuts a sheet-counter project once its cadence has passed with done rows, the `release` facts in `projects --stats --json`. A game with no `<game>-vX.Y.Z` tag yet is a sheet-counter project: the playground still tags builds `v<engine>-<game><N>` (history only, `buildTags`), so the sheet's cadence cuts it, and the game's first `<game>-vX.Y.Z` tag (queue item `systems-versions-p5-playground`) must be the sheet's open version, or the roll files it as a hotfix and `version_tag_drift` flags the gap. A project never cut, or a whole cadence past its due date, gets its history from `notes projects --backfill <name> --weekly [--repo <dir>]`: one version per ISO week of closed rows, dated by the notes git history, after a v0.1.0 baseline for older rows and commits. `fleet-bench chain` counts `release_overdue` and `version_tag_drift`.

## Release windows

The open version is the sprint: it commits its scope when it opens, takes new asks only through an interrupt lane, and is scored at the cut.

- Sprint: only a `#prio/focus` project's windows are sprints (`window::runs_sprints`): only they freeze new rows, list under `notes board --json .sprints` (the Sprints table on Projects > Board) and count in the tiers line's Sprint total. Every other project's window still opens, scores its cut and sets its state word. The human picks the focus project with `notes projects --prio <name> --set focus`. Test: `only_a_focus_project_shows_sprints`.

- Snapshot: a window commits only what fits it. The agent lane fills the window's capacity, its days (opened to due) of the agent rows' shipped weight, the way the agent board fills (pinned rows, then `#requested`, then sheet order, at least the board floor); the human lane has no measured pace, so only its pinned rows (in progress, `#urgent`, due soon) go in. The rest stay open on the version uncommitted and the cut carries them. A row still waiting at the window's end (an `#at/` gate that opens after its due day or cannot be read, or `#after/` a row still open) is left out of the snapshot, as a sprint lock leaves it out, so no wait holds a cut (`a_window_leaves_out_rows_that_wait_past_its_end`). It is written once to `## Committed` in `agent/versions/<v>.md` with its opened and due days. `projects --release` writes it for the version it opens (due one cadence on), and `notes projects --commit <name>` writes it for a version already open (due the last cut plus the cadence, or the version's `Target:` day when that is earlier); both print the capacity beside the count. A second snapshot is refused, so a mid-window add never reads as committed. The one exception is the human locking a sprint: `--commit <name> --hours <h>` replaces the snapshot with the rows that fit `h` hours of the agent lane's shipped weight (a week of it over 168 hours), pinned rows spending it too: `#urgent` first, then in progress, then `#requested`, then the rest, smallest first within each, with no floor; a row still waiting (`#after/` an open row, or an `#at/` gate) is left out, and the human lane, which has no measured pace, commits nothing. The head records the cut as `cut=YYYY-MM-DDTHH:MM`, and the due day is the cut's day.
- Queued: any number of sprints can be locked in a chain while the open one runs. `--commit <name> --hours <h> --queue` locks the patch after the last sprint already queued (the first time, the one the freeze sends new rows to), and `--queue vX.Y.Z` relocks that queued sprint in place. Each takes its rows tagged `#v<that version>` only, in its own `agent/versions/<v>.md`, with the same capacity and order as a sprint lock; it starts at the cut of the window before it (its `cut=`, else the end of its due day), recorded as `start=` in the head, and its cut is that start plus `h` hours. A row waiting `#after/` a row an earlier window committed is not waiting; a version past the chain's end is refused. Queued is derived, never stored: the window is queued while its version is past the sheet's `Version:`, so the roll opens it as it was locked (`--release` keeps a snapshot it finds) and rewrites nothing. `notes board --json .sprints` carries every queued sprint after the open window, soonest first, with `queued` and `start`, and the Sprints table on Projects > Board reads STARTED as the cut before it and LEFT as `queued`. Relocking the open window or a queued one moves every sprint queued behind it to start at the new cut before it, keeping its length and rows.
- Freeze: in a `#prio/focus` project with a snapshot, a new row (`ptask add`, inbox-triage filing) goes to the next patch version (`#vX.Y.Z`) unless it is an interrupt. Interrupts are: the human at a terminal, the human's inbox lines, a `--want` channel other than `outbox` or `ask`, a row tagged `#interrupt` or `#urgent`, or one aimed at the open version by hand. They are tagged `#interrupt` and go in now, except an `#urgent` row still waiting at the window's end, which goes to the next window at `#high`, with no `#interrupt`, unless aimed at the open one by hand: an open `#urgent` row holds the cut (`an_urgent_add_that_waits_past_the_window_goes_to_the_next_one`). `#requested` is not the signal: agent follow-ups and ask-sweep rows carry it too. Other projects take every add into the open version, as before.
- Score: committed, delivered (closed and not dropped), carried (still open at the cut, the rows `carry_open` stamps `carried:N`), dropped, and interrupted (an `#interrupt` row not in the snapshot), plus the cut against the due day and the human's target. `projects --stats --json` emits the open window as `window` and the last cut's line as `last_window`; the cut writes the line to `## Window` in the frozen `versions/<v>.md`, prints it with the next window's commit (`window <v>: ...`), and `agentctl-wave-roll` carries both lines into its log and the release page; fleet-bench prints both under "Release windows" in `LAB/bench/latest.md`, and each sample publishes the open window from `hub projects --json` as `agent_project_window_rows{project,version,kind}` (kind committed, delivered, carried, dropped, interrupted) and `agent_project_window_days_left`, with `agent_project_state{project,state}` beside them (`fleet_projects.prom`; Grafana Agents / Overview, "Release windows"). A closed window's say/do is the last sample of its version.
- Cut: for a project in `~/.config/release-cut/projects.json`, the `release-cut` lane (`agentctl-release-cut`) cuts the window, never an agent or a person. It cuts early once every committed row is closed and every epic row in it is verified; otherwise at its cut time (`cut=`, else the due day at the config's `cut_hour`), when its open rows carry to the next sprint through the roll the tag starts, and only an open `#urgent` row holds it until that row closes. A cut dispatches the project's cut workflow once per version (`-f version -f sha`) at the newest main commit with a green full Tests run; the workflow re-checks the gate and pushes the tag, and a tag already on origin or a cut run in flight is a no-op. Once the tag's beta deployment succeeds, the lane files the config's `promote` item once (Steam `default`, `release.md` "Who takes the public step"). Why: the human, 2026-11-19, "unless critical it shouldn't hold up release and we roll to next sprint".
- Changelog: the frozen note is the window's changelog for a sheet-counter project (its closed rows and `## PRs`); a tagged project's is the Releases tab's, `release-state changelog <project> <tag>`.

## Project state

Every project surface (hub Projects tab and its finder preview, agent-web, the phone, the waybar hover, the anchor's Lab block, the lab STATUS line) leads with one word for where the current release is, computed once by `hub_core::projects::state` and emitted as `state` and `state_level` in `hub projects --json`. The first row that matches wins; a backlog's open and done counts never set a state.

| State | Rule | Colour |
|---|---|---|
| `late` | rows are still open (or no window is), and the window's due day has passed or the human's target day has; a window with every row delivered waits on its cut and is not late | red |
| `at risk` | a window is open and the 28-day close rate (closed in 28 days, per day, times the days left) closes fewer rows than it has open; or the target's on-time check reads late or never | amber |
| `on track` | a window is open | green |
| `no window` | no window snapshot, but active: a row closed within `idle_days`, or a queue item is running or waiting | amber |
| `idle` | above `draft`, quiet | amber |
| `parked` | `draft`, quiet | grey |

`idle_days` is `[projects] idle_days` in the notes config (default 28). `state_words_are_the_stages_md_table` holds this table and the code to the same words in the same order.

## What stays with the human

These are never automated; each one is a `human` row, which the gate lists for the human to attest.

- Logins and 2FA on store consoles, payment, legal attestations, Apple and Play review, console dev-kit NDAs.
- A finished playtest before a game enters beta.
- The final public Publish or Submit click. The `store-console` skill fills a console up to it and stops. One exception: setting a beta-verified Steam build live on `default` is the agent's click (the person, 2026-11-06), in `store-console`'s standing permission. `stores.md` says which store steps are API, workflow, skill or person.

## Games: one ladder per game

A game in the playground carries the same ladder as its `status` field (`Draft`, `Dev`, `Alpha`, `Beta`, `Prod`). The rules for moving one game up live with the game code, in the playground's `docs/authoring/adding-a-game.md`; this doc does not repeat them.

A per-game row (a build profile, a play test) is judged on each game's own project, so the playground project, which is the whole repo, passes it. A game project's lab stage must equal its game's `status` on the default branch. `project-map-doctor` compares the two (check 6d) and FAILs on a mismatch, naming both places to fix.

## Changing this doc

A row that will be checked must name its check, and a new row must cite the failure it prevents, as `planning.md` requires. Changing the ladder itself means changing `STAGES`, the playground's `GameStatus` and the registry admin dropdown in the same change; the doctor's 6d check catches a game that is left behind.
