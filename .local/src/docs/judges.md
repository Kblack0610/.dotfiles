# Judge standard

A judge is a model call that decides something a human would otherwise decide: the answer judge (`ask-judge`, in `agent-ask`), the dispatch judge (`dispatch-judge`, in `fleet-dispatch`) and the ask sweep (`ask-sweep`). A scored runner is any other agent whose writes a counted outcome can grade: the inbox triager (`inbox-triage`), planner (`inbox-plan`) and priority pass (`inbox-priority`). Each is an agent with its own conf in `~/.config/agentctl/agents/` (what an agent is: `~/.config/agentctl/README.md`), and the conf's `SCORE=` names the truth source below that `judge-eval` scores it by. `judge-eval` is the one scorer; this file is what it holds a judge or a runner to. The fleet's other invariants are in `standards.md` beside this file.

## Ground truth per lane

| lane (`SCORE=`) | a verdict | right when | wrong when | not scored |
|---|---|---|---|---|
| ask-judge (`ask-answers`) | `judge` on the ask file, its rule and its `judge_call` | the human's answer is the option the judge would have given, or the human's review of a live answer named the judge's option (`judge_override: kept`) | the human answered another option, or overrode the live answer | live answers the human's next message did not review (`judge_override: none`, silence), gate asks, free text that names no option, `unclear-ask` deferrals, deferrals by a hard-stop type or rule or with no type, asks still pending |
| dispatch-judge (`dispatch-queue`) | the newest `dispatch` or `skip` line per row in `~/.agent/dispatch/verdicts.jsonl` | the started row's queue item ended `done ok`; a skip, when 48h pass from the first skip of its run with no hand start | its item ended failed or cancelled, or a later `failed` line names the row; a skip is a false-defer when a queue item for the row starts after it and fleet-dispatch's run did not start it (`origin` neither `run` nor `resume`) | rows still running, skips under 48h old |
| inbox-triage (`triage-untouched`) | each `filed` event in the notes ingest record (`notes log`) that no session or queue item wrote | 48h pass with no `edited`, `dropped`, `dup`, `rehomed` or `tagged` event on the row; the planner's own writes, the minute up to its `planned` record, do not count | one of those events inside the 48h; a re-tag that only changes the priority is the priority pass's, scored on its own row, and counts for neither side | rows filed under 48h ago. A hand edit in an editor never reaches the record, so the score is an upper bound |
| inbox-plan (`plan-dispatched`) | the first `planned` event per row in the ingest record | a queue item for the row, or for a row the same run split from it (`#of/<id>`), starts before any re-split | a re-split comes first: a later `planned` on the row, or a row split from it by anyone else (`#of/<id>` added or tagged) | planned rows nothing has started |
| inbox-priority (`priority-kept`) | each `tagged` event in the ingest record that sets a priority, written `by` inbox-priority (the pass names itself whoever runs it; before 2026-11-12, by inbox-triage on a priority-only re-tag) | 48h pass with no other writer changing the row's priority | another writer changes the priority inside the 48h | tags under 48h old, and a tag the pass itself replaces inside the 48h. Each priority (urgent, high, low) is its own rule, so precision shows per level. A hand edit in an editor never reaches the record, so the score is an upper bound |
| ask-sweep (`sweep-untouched`) | each `added` event in the ingest record whose text carries the quote the sweep model files (`; asked MM-DD "..."`), whoever ran the sweep | 48h pass with no `edited`, `dropped`, `dup`, `rehomed` or `tagged` event on the row | one of those events inside the 48h | rows under 48h old; its plan rows (`chore(plan): finish ...`), which no model wrote; and the lines it judged as no want, since nothing records a line it passed over, so a miss of the sweep is never counted |
| sentinel-diagnose (no `SCORE`) | not recorded | - | - | everything: its verdict is only the transition in the watch log, keyed by watch, and the truth (a rollback or hotfix after a healthy verdict) is in the release records, and the lane makes few calls. It needs a verdict line keyed by release before it can be counted |
| shepherd, dream (no `SCORE`) | not recorded | - | - | everything. The shepherd's per-session ledger keeps only the last nudge and `watch.log` is keyed by tmux window, so "progressed before the next pass" needs an append-only nudge log keyed by session. Dream's promotions are prose in `DREAMS.md`, so "still present 14d later" needs a per-entry promotions record; its mem0 proposals are decided in `agent-propose`, whose records keep each accept and reject |

## Rules

- Judges are scored only by `judge-eval`. A dashboard or report shows its numbers and never counts again. Why: `agent-ask judge-report` and hub-core's own count both scored the answer judge, and they disagreed on in-session answers. Tests: `tests/unit/judge_eval.bats`, hub-core `fleet::tests::the_answer_judge_tiles_are_judge_evals_numbers`.
- A verdict is scored against its lane's ground truth above, never against a model's opinion of it. Why: a model grading a model scored 78% of turns 10/10 (the per-Stop judge retired 2026-10-28). Test: `judge_eval.bats` "the confusion matrix" and "dispatch-judge: the newest verdict per row".
- Scores count only verdicts made under the judge's current prompt (the git blob of its conf's `PROMPT`, the `prompt_sha` agentctl-run writes on the call; a row the ingest record scores has no call, so it counts when written after the first call under that prompt since the last call under another). A changed policy starts the count again, and `--any-prompt` reads the history. Why: a score earned under an older policy says nothing about the one running now. Tests: `judge_eval.bats` "--any-prompt also counts", and "ask-sweep: a row its model filed" for a row with no call.
- A lane is scored only when its conf names a truth source in `SCORE=`: that is the list of lanes, and nothing else keeps one. Only a right or wrong rate is a score, never a volume. A runner's is the fleet-bench KPI `runner_score_<name>` (hyphens to underscores), its precision, shown only past the one bar below; the dispatch judge's skips add `dispatch_false_defer_pct` beside its precision, not a second dispatch score. Each lane's `score_7d` in `judge-eval --json` is that 7d value as a cell ("93% untouched", "n<30" under the bar, "-" with no counted outcome), which the Fleet Workers score column and the day-log runner rollup show. All are computed on read, with no store of scores. Why: a hard-coded lane list in judge-eval left every runner but the judges unscored (2026-11-05). Tests: `judge_eval.bats` "the lanes are the confs that name a SCORE", "inbox-triage negative control", `fleet_bench.bats` "kpi: a runner_score_ KPI", "kpi --check".
- A scorable deferral (the rule below says which are not) the human answered with the recommendation is a false-defer, and it is reported beside precision. Why: precision alone rewards a judge that defers everything. On 2026-11-05 the answer judge had 8 scored answers and 47 false-defers. Test: `judge_eval.bats` "the confusion matrix".
- A live answer is labelled by the human's review: `kept` (their next message named the judge's option) is right, an override is wrong, `none` (it named no option) is not scored, and no review yet is pending. Why: the human never answers a live ask, so the review is its only label, and silence is not agreement: on 2026-11-11, 59 of the 70 live answers scored right were silence. Test: `judge_eval.bats` "the confusion matrix"; how a review is recorded: `tests/integ/agent_ask.bats` "override: ...".
- An answer to an ask with options is scored by the one option it names (agent-ask's `named_option`): the option alone, the option with a note ("a (human: ...)"), or text typed in a session. A one-letter option counts only as the first word, because elsewhere "a" is the article. An answer naming no option, or more than one, is unscorable and never compared as text, and `judge-eval` prints the unscorable share with its causes under each lane. Why: a guessed label is an invented one, and on 2026-11-07 noted answers ("a (human: ...)") scored 11 needless deferrals as right and free text 9 more verdicts, while 41 of 90 were unscorable and the report never said so. Tests: `judge_eval.bats` "the confusion matrix", "an answer with a note"; `agent_ask.bats` "settle-session: a reply answers".
- A gate ask (rule `gate`, no call) is not a verdict, an `unclear-ask` deferral is the asker's fault, counted in `ask_unclear_pct`, and a deferral whose type or rule is a hard stop (`JUDGE_HARD_STOPS`), or that has no type, is unscorable. None of them counts as a false-defer. Why: the human gets all of them whatever the judge thinks, and no `DELAY_RULES` row can name a hard stop; a deferral by a human criterion such as `external` or `knowledge` goes to the human by policy, and the human takes the recommendation on about 90% of asks whatever the judge did, so labelling it by that answer read 83% for a judge following its policy (2026-11-10, ar-1559). A deferral from before the judge recorded a type (2026-11-06) cannot be checked. agent-ask defers only on a criterion, so no deferral of the current answer judge is scorable and it has no false-defer KPI; `ask_answered_pct` is its over-deferral alarm. Tests: `judge_eval.bats` "the confusion matrix" and "a deferral of a hard-stop type or rule, or of no type", `agent_ask.bats` "judge never sends a gate to the model".
- A failed call is an error: it is counted, left out of coverage's denominator, and never read as a deferral. Why: a timeout is not a judgement, and counting it as one would hide a broken judge behind a careful-looking one. Tests: `judge_eval.bats` "the confusion matrix", the `judge_errors` KPI. A call its caller kills (the post's `AGENT_ASK_JUDGE_TIMEOUT` guard) still writes its `calls.jsonl` line, with the signal's exit, so the lane's failed calls count it and name its account and duration. Test: `agent_run_agent.bats` "a call its caller kills".
- A type goes live, and how long it waits before its answer is assumed, on the human's call, by a PR to `DELAY_RULES`; a hard stop can never get a row. `judge-eval` shows each type against one bar, `AGENT_ASK_LIVE_BAR` (30) scored answers at `AGENT_ASK_LIVE_PRECISION` (90%), with the 95% interval beside it, to inform that call. Why: the human took the recommendation on 92% of the asks the judge deferred, and holding every type until it had 30 scored answers kept a queue of asks the judge already called right. Test: `judge_eval.bats` "precision carries its 95% Wilson interval".
- A live type demotes when precision over its last `AGENT_ASK_LIVE_BAR` (30) live answers falls under `AGENT_ASK_DEMOTE_PRECISION` (85%), counted once it has `AGENT_ASK_DEMOTE_MIN` (10). Why: at about 90% a type almost surely meets one override in 30, so a first-override rule pulled every type within days; a recent window brings back a type that drifts without ending one that is right 9 times in 10. Tests: `agent_ask.bats` "override: ... one miss does not demote" and "override: a type demotes when precision over its last live answers ...".
- The answer judge reads the human's disagreements decided before the ask was posted, and one covering the same decision sends the ask to the human (`against-precedent`). Why: a disagreement changes the next verdict the same day with no rule written, and a replayed ask can never read its own answer. Test: `agent_ask.bats` "precedents: a disagreement older than the ask ...".
- Each verdict names its call (`judge_call`, one `calls.jsonl` line), so latency and cost per verdict are the call's, shared across the rows one call judged. Why: estimated costs drift, and a dispatch call judges many rows at once. Test: `judge_eval.bats` "dispatch-judge: the newest verdict per row" (cost per verdict).
- The judge KPIs (`judge_errors`, `judge_precision`, `ask_answered_pct`, `ask_unclear_pct`, `dispatch_false_defer_pct`) are fleet-bench KPIs with thresholds in `~/.config/agentctl/kpi-thresholds`, so `fleet-bench retro` files a row when one trips, and the `runner-score` Sentinel watch pages on a judge error in 24h or a `runner_score_*` or `dispatch_false_defer_pct` KPI past (`fleet-bench kpi --check`). `judge_precision` is the lowest precision among rules with 10 or more scored answers. Why: a judge drifting wrong was visible only to someone who went looking. Test: `tests/unit/fleet_bench.bats` "kpi: the judge KPIs come from judge-eval kpi".

- Every answer verdict is listed, not only the misses, with its impact level and call: `judge-eval log` (`--level` keeps one), and `verdicts` in `--json`, which Log's Judges' verdicts section shows on both surfaces. The list and its 7-day line take any prompt, because they say what happened rather than score a policy. Why: the human could only see where the judge disagreed, never what it said yes to or why it passed (2026-11-05). `judge-eval cells` scores each type at each impact level, so a type is proven where a wrong answer reaches least before it answers where it reaches most. The answer judge's runner page draws those cells under its current prompt as one table on both surfaces (`#fleet/ask-judge`, `hub tab fleet ask-judge`), and each verdict's Langfuse score carries its level as `metadata.level` (a dispatch verdict's is its tier, `tier 2`), since a score takes no tags. Tests: `judge_eval.bats` "the verdict list", "cells:"; hub-tui `the_answer_judges_page_tables_each_type_at_each_level_as_judge_eval_scores_it`; `tests/agent-web/fleet.test.mjs` "a judge page carries"; `session_outcomes.bats` "langfuse: each judge verdict".

## Replay

`judge-eval replay` scores a changed policy before it earns live labels: the real `agent-ask judge` over blind copies of the asks the human answered with an option, as the agent `ask-judge-replay`, whose own budget keeps it off `ask-judge`'s. The copies are then scored like any other verdicts, so its numbers are a replay's, never counted into the KPIs, and a run that would leak an answer sends nothing. Test: `judge_eval.bats` "replay".

## How the numbers are computed

Each verdict is one of: TP (answered, right), FP (answered, wrong), FN (deferred, but the human took the recommendation), TN (deferred, rightly), pending, unscorable, or an error.

| number | formula |
|---|---|
| coverage | answered / (verdicts - errors) |
| precision | TP / (TP + FP), with its Wilson 95% interval |
| false-defer % | FN / (FN + TN); the dispatch judge's is `dispatch_false_defer_pct`, null under 10 scored skips |
| `runner_score_<name>` | the lane's precision, TP / (TP + FP), null under 30 scored |
| kappa | Cohen's kappa over the TP, FP, FN, TN table |
| p50, p95 | each scored verdict's call `duration_ms` |
| cost per verdict | each call's `cost_usd` divided by the verdicts it made, averaged |
| `ask_answered_pct` | asks the judge really answered (`answered_by: judge`) / (ask verdicts - errors); an armed ask counts once its wait fires, so the KPI dips while asks are armed |
| `ask_unclear_pct` | `unclear-ask` verdicts / (ask verdicts - errors) |
