# Judge standard

A judge is a model call that decides something a human would otherwise decide: the answer judge (`ask-judge`, in `agent-ask`), the dispatch judge (`dispatch-judge`, in `fleet-dispatch`) and the ask sweep (`ask-sweep`). A scored runner is any other agent whose writes a counted outcome can grade: the inbox triager (`inbox-triage`), planner (`inbox-plan`) and priority pass (`inbox-priority`). Each is an agent with its own conf in `~/.config/agentctl/agents/` (what an agent is: `~/.config/agentctl/README.md`), and the conf's `SCORE=` names the truth source below that `judge-eval` scores it by. `judge-eval` is the one scorer; this file is what it holds a judge or a runner to. The fleet's other invariants are in `standards.md` beside this file. A lane is a runner conf that names a `SCORE=` or a `PROMPT=`; judge-eval (`prompt_lanes`) and hub-core (`Conf::instructed`) both read that rule from here. What a lane is told and held to is never copied into a doc: `judge-eval prompts [lane|--all]` prints each lane's PROMPT files, schema and gates in full from its conf (test: `judge_eval.bats` "prompts"), and agent-web shows the same text, folded, on each lane's runner page (`#sessions/runners/<lane>`, linked from Log > Judges).

## Ground truth per lane

| lane (`SCORE=`) | a verdict | right when | wrong when | not scored |
|---|---|---|---|---|
| ask-judge (`ask-answers`) | `judge` on the ask file, its rule and its `judge_call` | the human's answer is the option the judge would have given, or the human's review of a live answer named the judge's option (`judge_override: kept`) | the human answered another option, or overrode the live answer | live answers the human's next message did not review (`judge_override: none`, silence), gate asks, free text that names no option, `unclear-ask` deferrals, deferrals by a hard-stop type or rule or with no type, asks still pending |
| dispatch-judge (`dispatch-queue`) | the newest `dispatch` or `skip` line per row in `~/.agent/dispatch/verdicts.jsonl` | the started row's queue item ended `done ok`; a skip, when 48h pass from the first skip of its run with no hand start | its item ended failed or cancelled, or a later `failed` line names the row; a skip is a false-defer when a queue item for the row starts after it and fleet-dispatch's run did not start it (`origin` neither `run` nor `resume`) | rows still running, skips under 48h old |
| inbox-triage (`triage-untouched`) | each `filed` event in the notes ingest record (`notes log`) that no session or queue item wrote | 48h pass with no `edited`, `dropped`, `rehomed` or `tagged` event on the row (a `dup`, a later line joined to the row, repeats it and is no touch); the planner's own writes, the minute up to its `planned` record, do not count | one of those events inside the 48h; a re-tag that only changes priority (the priority pass is scored on its own row), or one by a pass or session of only size (`#pts/N`, `#size/x`), `#plan`, `#go`, `#hold/..`, `#ask/..`, `#desk/..` or `#after/..`, is ignored by this lane (no lane scores sizing); a human re-tag always counts | rows filed under 48h ago, touched or not: a settle-window verdict (this lane, ask-sweep, inbox-priority and a dispatch skip) under 48h old is pending, wrong or right, since a miss counted early fills a young window (a fix watermark) with misses alone (runner-score read 21% on an 87% lane, 2026-11-22; tests `judge_eval.bats` "SENTINEL_SINCE: a window younger than the settle time" and "a priority a later pass superseded"). A hand edit in an editor never reaches the record, so the score is an upper bound |
| inbox-plan (`plan-dispatched`) | the first `planned` event per row in the ingest record | a queue item for the row, or for a row the same run split from it (`#of/<id>`), starts before any re-split | a re-split comes first: a later `planned` on the row, or a row split from it by anyone else after the plan (`#of/<id>` on an added row, `+#of/<id>` on a re-tag; a `-#of/<id>` moves a row away and splits nothing) | planned rows nothing has started |
| inbox-priority (`priority-kept`) | each `tagged` event in the ingest record that sets a priority, written `by` inbox-priority (the pass names itself whoever runs it; before 2026-11-12, by inbox-triage on a priority-only re-tag) | 48h pass with no other writer changing the row's priority | another writer changes the priority inside the 48h | tags under 48h old, wrong or right (a miss stays pending until 48h after its tag even once a later pass supersedes it), and a tag the pass itself replaces inside the 48h with no other change. Each priority (urgent, high, low) is its own rule, so precision shows per level. A hand edit in an editor never reaches the record, so the score is an upper bound |
| ask-sweep (`sweep-untouched`) | each `added` event in the ingest record whose text carries the quote the sweep model files (`; asked MM-DD "..."`), whoever ran the sweep | 48h pass with no `edited`, `dropped`, `rehomed` or `tagged` event on the row (a `dup`, a later line joined to the row, repeats it and is no touch) | one of those events inside the 48h, the nightly `--backlog --link` swap of its area to a system id included: the sweep is given the board's Systems (`systems_of`), so an area outside them is its miss, not a pass-only normalization (ar-4669) | rows under 48h old; its plan rows (`chore(plan): finish ...`), which no model wrote; and the lines it judged as no want, since nothing records a line it passed over, so a miss of the sweep is never counted |
| sentinel-diagnose (no `SCORE`) | not recorded | - | - | everything: its verdict is only the transition in the watch log, keyed by watch, and the truth (a rollback or hotfix after a healthy verdict) is in the release records, and the lane makes few calls. It needs a verdict line keyed by release before it can be counted |
| shepherd, dream (no `SCORE`) | the shepherd's: each nudge and close claim, one line in `~/.agent/shepherd/nudges.jsonl` (`fleet-sessions mark`: `at`, `sid`, `kind`, `fact`, and the row's `target`, `project`, `bucket` from the latest state document). A line is the claim, taken before the message goes out; a close nothing was typed into is given back with a `close-released` line. Dream's: not recorded | - | - | everything. The shepherd's verdicts are recorded but no conf names a truth for them yet (board row ar-57: what counts as a nudge that worked). Dream's promotions are edits to lessons and memory/ files (its `activity.log` keeps one summary line per sweep), so "still present 14d later" needs a per-entry promotions record; its mem0 proposals are decided in `agent-propose`, whose records keep each accept and reject |

## Rules

- Judges are scored only by `judge-eval`. A dashboard or report shows its numbers and never counts again. Why: `agent-ask judge-report` and hub-core's own count both scored the answer judge, and they disagreed on in-session answers. Tests: `tests/unit/judge_eval.bats`, hub-core `fleet::tests::the_answer_judge_tiles_are_judge_evals_numbers`.
- A verdict is scored against its lane's ground truth above, never against a model's opinion of it. Why: a model grading a model scored 78% of turns 10/10 (the per-Stop judge retired 2026-10-28). Test: `judge_eval.bats` "the confusion matrix" and "dispatch-judge: the newest verdict per row".
- Scores count only verdicts made under the judge's current prompt (the git blob of its conf's `PROMPT` with its includes in place, the `prompt_sha` agentctl-run writes on the call; a lane whose `PROMPT` names several files, one per pass, counts a call under any of them as current; a row the ingest record scores has no call, so it counts when written after the first call under that prompt since the last call under another). A changed policy starts the count again, and `--any-prompt` reads the history. Why: a score earned under an older policy says nothing about the one running now. Tests: `judge_eval.bats` "--any-prompt also counts" and "a lane with two PROMPT files", `agent_prompts.bats` (every scored conf names a `PROMPT`), and "ask-sweep: a row its model filed" for a row with no call.
- A lane is scored only when its conf names a truth source in `SCORE=`: that is the list of lanes, and nothing else keeps one. Only a right or wrong rate is a score, never a volume. A runner's is the fleet-bench KPI `runner_score_<name>` (hyphens to underscores), its precision, shown only once it has `AGENT_ASK_LIVE_BAR` (30) scored rows; the dispatch judge's skips add `dispatch_false_defer_pct` beside its precision, not a second dispatch score. Each lane's `score_7d` in `judge-eval --json` is that 7d value as a cell ("93% untouched", "n<30" under that count, "-" with no counted outcome), which the Fleet Workers score column and the day-log runner rollup show. All are computed on read, with no store of scores. Why: a hard-coded lane list in judge-eval left every runner but the judges unscored (2026-11-05). Tests: `judge_eval.bats` "the lanes are the confs that name a SCORE", "inbox-triage negative control", `fleet_bench.bats` "kpi: a runner_score_ KPI", "kpi --check".
- A scorable deferral (the rule below says which are not) the human answered with the recommendation is a false-defer, and it is reported beside precision. Why: precision alone rewards a judge that defers everything. On 2026-11-05 the answer judge had 8 scored answers and 47 false-defers. Test: `judge_eval.bats` "the confusion matrix".
- A live answer is labelled by the human's review: `kept` (their next message, or their answer to an audit posted before ar-4765, named the judge's option) is right, an override is wrong, `none` (it named no option) is not scored, and no review yet is pending. No answer is sampled back to the human as an audit (ar-4765): the human's override is the precision signal. Why: silence is not agreement (on 2026-11-11, 59 of the 70 live answers scored right were silence), and an audit routed work to the human that no rule of theirs asked for. Test: `judge_eval.bats` "the confusion matrix"; how a review is recorded: `tests/integ/agent_ask.bats` "override: ..." and "audit: ...".
- An answer to an ask with options is scored by the one option it names (agent-ask's `named_option`): the option alone, the option with a note ("a (human: ...)"), or text typed in a session. A one-letter option counts only as the first word, because elsewhere "a" is the article. An answer naming no option, or more than one, is unscorable and never compared as text, and `judge-eval` prints the unscorable share with its causes under each lane. Why: a guessed label is an invented one, and on 2026-11-07 noted answers ("a (human: ...)") scored 11 needless deferrals as right and free text 9 more verdicts, while 41 of 90 were unscorable and the report never said so. Tests: `judge_eval.bats` "the confusion matrix", "an answer with a note"; `agent_ask.bats` "settle-session: a reply answers".
- An approval ask (rule `gate`, no call) is not a verdict, an `unclear-ask` deferral is the asker's fault, counted in `ask_unclear_pct`, and a deferral whose type or rule is a hard stop (`JUDGE_HARD_STOPS`), or that has no type, is unscorable. None of them counts as a false-defer. Why: the human gets all of them whatever the judge thinks, and no `DELAY_RULES` row can name a hard stop; a deferral by a human criterion such as `external` or `knowledge` goes to the human by policy, and the human takes the recommendation on about 90% of asks whatever the judge did, so labelling it by that answer read 83% for a judge following its policy (2026-11-10, ar-1559). A deferral from before the judge recorded a type (2026-11-06) cannot be checked. agent-ask defers only on a criterion, so no deferral of the current answer judge is scorable and it has no false-defer KPI; `ask_answered_pct` is its over-deferral alarm. Tests: `judge_eval.bats` "the confusion matrix" and "a deferral of a hard-stop type or rule, or of no type", `agent_ask.bats` "judge never sends an approval to the model".
- A failed call is an error: it is counted, left out of coverage's denominator, and never read as a deferral. Why: a timeout is not a judgement, and counting it as one would hide a broken judge behind a careful-looking one. Tests: `judge_eval.bats` "the confusion matrix", the `judge_errors` KPI. A call its caller kills (the post's `AGENT_ASK_JUDGE_TIMEOUT` guard) still writes its `calls.jsonl` line, with the signal's exit, so the lane's failed calls count it and name its account and duration. Test: `agent_run_agent.bats` "a call its caller kills".
- A type goes live up to an impact level, and how long it waits before its answer is assumed, on the human's call, by a PR to `DELAY_RULES`: a row `<type>@<level>=<minutes>` answers that type at its level and every level under it, never above, and a type may carry one row per level band, lowest first, so a wider reach waits longer (`t@repo=0 t@fleet=240`; a second row that does not reach a higher level is refused) (an ask with no level is never live), the level is `self`, `repo` or `fleet` (an ask flagged `judge_human_only` always goes to the human, whatever its level), and a hard stop can never get a row. The PR that sets a ceiling names the `judge-eval cells` and replay numbers it rests on. A cell is weighed for promotion against the bar for its level, `PROMOTE_BARS` in `ask-judge.conf`: the Wilson 95% low bound of its shadow precision reaches 70% at self (9 straight agreements) or 85% at repo (22 straight); fleet has no bar, so it is only ever the human's call, and a hard stop is never a candidate (provisional, confidence low: revisit once four weeks of leveled cells exist, about 2026-12-10). A cell also waits while a narrower cell of its type is shadow and scored under its own bar, since a row opens every level under its own. `judge-eval promote` lists the cells against their bars, and on Mondays the briefing runs `judge-eval promote --ask`, which posts one approval ask per candidate (never sent to the judge) and asks a cell again only after `PROMOTE_QUIET_DAYS` (28) from its last answer or cancel. Why: the human took the recommendation on 92% of the asks the judge deferred, and holding every type until it had 30 scored answers kept a queue of asks the judge already called right; a type proven on asks about one repo is not proven on asks about the fleet, and one bar for every level stalls the cheap cells for months (10 of 10 agreements is a 72% low bound, 85% needs 22). Tests: `judge_eval.bats` "precision carries its 95% Wilson interval", "promote: the bar scales with level", "promote --ask", `agent_ask.bats` "live answers: a row answers its type at every level up to its own".
- A live cell (a type at one level) demotes when precision over its last `AGENT_ASK_LIVE_BAR` (30) reviewed live answers falls under `AGENT_ASK_DEMOTE_PRECISION` (85%), counted once it has `AGENT_ASK_DEMOTE_MIN` (10). Why: at about 90% a type almost surely meets one override in 30, so a first-override rule pulled every type within days; a recent window brings back a type that drifts without ending one that is right 9 times in 10; a demote per cell keeps the levels it is still right at. Tests: `agent_ask.bats` "override: ... one miss does not demote" and "override: a cell demotes when precision over its last live answers ...".
- The answer judge reads the human's disagreements decided before the ask was posted, and one covering the same decision sends the ask to the human (`against-precedent`). Why: a disagreement changes the next verdict the same day with no rule written, and a replayed ask can never read its own answer. Test: `agent_ask.bats` "precedents: a disagreement older than the ask ...".
- Each verdict names its call (`judge_call`, one `calls.jsonl` line), so latency and cost per verdict are the call's, shared across the rows one call judged. Why: estimated costs drift, and a dispatch call judges many rows at once. Test: `judge_eval.bats` "dispatch-judge: the newest verdict per row" (cost per verdict).
- The judge KPIs (`judge_errors`, `judge_precision`, `ask_answered_pct`, `ask_unclear_pct`, `judge_human_only_live_pct`, `ask_human_only_pct`, `dispatch_false_defer_pct`) are fleet-bench KPIs with thresholds in `~/.config/agentctl/kpi-thresholds`, so `fleet-bench retro` files a row when one trips, and the `runner-score` Sentinel watch pages on a judge error in 24h or a `runner_score_*`, `dispatch_false_defer_pct` or `judge_human_only_live_pct` KPI past (`fleet-bench kpi --check`); `judge_human_only_live_pct` has max 0, so one human-only ask the judge answered itself pages. `ask_human_only_pct` has no bar: it is the share the human-stop rules send to the human, read when the policy's external or reversible criteria change. `judge_precision` is the lowest precision among rules with 10 or more scored answers. Why: a judge drifting wrong was visible only to someone who went looking. Test: `tests/unit/fleet_bench.bats` "kpi: the judge KPIs come from judge-eval kpi" and "kpi --check: judge_human_only_live_pct trips", `judge_eval.bats` "kpi: judge_human_only_live_pct".
- `judge-eval kpi` scores both windows in one jq from one read of the sources. Why: each window passed to jq as an argument failed past 128 KB, the per-argument cap, and fleet-bench read no judge KPI (2026-11-27, ar-5953). Test: `judge_eval.bats` "kpi --json: both windows from one read of the sources" and "a 28-day window over 128 KB still scores".

- Every answer verdict is listed, not only the misses, with its impact level and call: `judge-eval log` (`--level` keeps one), and `verdicts` in `--json`, which Log's Judges' verdicts section shows on both surfaces. The list and its 7-day line take any prompt, because they say what happened rather than score a policy. Why: the human could only see where the judge disagreed, never what it said yes to or why it passed (2026-11-05). `judge-eval cells` scores each type at each impact level, so a type is proven where a wrong answer reaches least before it answers where it reaches most. The answer judge's runner page draws those cells under its current prompt as one table on both surfaces (`#sessions/runners/ask-judge`, `hub tab 'sessions runners/ask-judge'`), and each verdict's Langfuse score carries its level as `metadata.level` (a dispatch verdict's is its tier, `tier 2`), since a score takes no tags. Tests: `judge_eval.bats` "the verdict list", "cells:"; hub-tui `the_answer_judges_page_tables_each_type_at_each_level_as_judge_eval_scores_it`; `tests/agent-web/fleet.test.mjs` "a judge page carries"; `session_outcomes.bats` "langfuse: each judge verdict".

## How the numbers are computed

Each verdict is one of: TP (answered, right), FP (answered, wrong), FN (deferred, but the human took the recommendation), TN (deferred, rightly), pending, unscorable, or an error.

| number | formula |
|---|---|
| coverage | answered / (verdicts - errors) |
| precision | TP / (TP + FP), with its Wilson 95% interval |
| false-defer % | FN / (FN + TN); the dispatch judge's is `dispatch_false_defer_pct`, null under 10 scored skips |
| `runner_score_<name>` | the lane's precision, TP / (TP + FP), null under `AGENT_ASK_LIVE_BAR` (30) scored |
| kappa | Cohen's kappa over the TP, FP, FN, TN table |
| p50, p95 | each scored verdict's call `duration_ms` |
| cost per verdict | each call's `cost_usd` divided by the verdicts it made, averaged |
| `ask_answered_pct` | asks the judge really answered (`answered_by: judge`) / (ask verdicts - errors); an armed ask counts once its wait fires, so the KPI dips while asks are armed |
| `ask_unclear_pct` | `unclear-ask` verdicts / (ask verdicts - errors) |
| `judge_human_only_live_pct` | human-only verdicts (`judge_human_only`) the judge answered live / human-only verdicts; null with none |
| `ask_human_only_pct` | human-only verdicts / (ask verdicts - errors) |
